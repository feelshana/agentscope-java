# 图表渲染技能

把结果集转化为一张真正能说明问题的图表的标准化流程——基于 Vega-Lite spec 在聊天界面内渲染。

## 步骤

1. **先根据问题选对图表类型。** 画图之前先决定：

   | 问题形态 | chart_type |
   |---------|------------|
   | "X 随时间如何变化？" | `line`（单系列）或多折线 |
   | "构成 / 占比" | 堆叠 `bar`，或 100% 堆叠 `area` |
   | "少量类别之间的对比" | `bar`（标签较长时用水平条形图） |
   | "两个数值变量之间的关系" | `scatter` |
   | "累计总量" | `area` |

   如果都不匹配，先询问用户想要哪种视图——不要默认"随便画一张都行"。

2. **准备数据。** 来自 [[sql-analysis]] 技能的聚合结果应当已经是规整格式：每个数据点一行，每个维度一列，外加一个度量列。如果预览被截断或仍是原始明细，请改写 SQL 加上正确的 `GROUP BY` 重新执行，而不是用残缺数据画图。保持数据量小——几十个点，不是几百个。

3. **构建 Vega-Lite spec。** 一个 JSON 对象，包含：
   - **`mark`** — `"line"`、`"bar"`、`"area"`、`"point"`（散点）之一。
   - **`title`** — 一句话直接回答问题，不要写"未命名图表"。
   - **`encoding`** — `x` 和 `y` 通道，各自包含 `field`、`type`（`"temporal"`、`"ordinal"`、`"quantitative"`、`"nominal"`），以及带单位的 `title`（如"营收（元）"、"月份"）。
   - **`data.values`** — 行数据以内联 JSON 对象数组给出（`[{"month": "2025-01", "revenue": 1234.5}, ...]`）。绝不引用外部 URL。
   - 仅在多系列时才添加可选的 `color` 通道。

   示例骨架：

   ```json
   {
     "mark": "line",
     "title": "2025 年月度营收趋势（元）",
     "encoding": {
       "x": {"field": "month", "type": "temporal", "title": "月份"},
       "y": {"field": "revenue", "type": "quantitative", "title": "营收（元）"}
     },
     "data": {"values": [{"month": "2025-01-01", "revenue": 4200}]}
   }
   ```

4. **调用 `render_chart`。** 以 `render_chart(chart_type, vega_lite_spec)` 的形式调用，其中 chart_type 与 mark 对应，vega_lite_spec 是上面 JSON 对象的字符串形式。工具会确认收到 spec；界面随后在会话中就地渲染。不要声称图表"已保存为文件"——它是原地渲染的。

5. **展示并解读。** 在同一条回复中，用 **2-3 句话解读图表**——它展示了什么、用户最该关注的一个要点、以及任何注意事项（最新数据点不完整、已剔除退款订单等）。没有解读的图表等于没有回答。

6. **保持可复现。** 用户提出微调（"纵轴能用对数刻度吗？"、"改成按月汇总"）时，直接修改 spec（加 `"scale": {"type": "log"}`、调整 SQL 分组）并再次调用 `render_chart`——不要从头重做整个分析。

## 反模式

- ❌ 把成百上千行原始明细塞进 `data.values` —— 先在 SQL 里聚合。
- ❌ 超过 5 个扇区的饼图（而且没有 pie mark —— 用堆叠柱状图替代）。
- ❌ 用户实际想要占比时却画原始计数。
- ❌ 坐标轴没有标签或单位的图表。
- ❌ 调用 `render_chart` 却不写 2 句解读。
- ❌ 生成 PNG 文件或 matplotlib 脚本——渲染由前端基于 spec 完成，没有任何东西需要落盘。

## 何时委托

如果用户想要带叙述文字的多图仪表盘（例如"给我做一份每周产品健康简报"），**派生 `report-writer` 子代理**——本技能只负责单张图表。
