# spec 052：技术自动修复与一次业务方案确认

## 目标

避免用户确认不合格提案、点击修复技术错误及反复批准同一方案的配套文件。

## 方案

1. 在现有 write_file 上增加 files_json/base_revision；批量文件与单文件参数互斥。list_files 返回当前基准指纹。最多 100 个文件，总内容 1MB，路径走现有平台保护，拒绝重复规范化路径和符号链接。
2. 副本一次覆盖全部文件后进行 YAML、问题格式及资产覆盖校验，Wren validate/build/dry-plan 检查视图和完整问题 SQL。问题不得提交空 SQL 作为完成方案。
3. middleware 预检失败向原生上下文添加 ERROR 工具结果，不产生 DENIED 或 hitl_request，继续原生循环修复；有效提案进入 HITL。生产预检装配延迟获取 ModelingToolkitRegistrar，避免循环注入。
4. 批量审批只产生一个卡片，展示业务摘要及逐文件可读内容；执行时复验基准，校验通过后在工作区锁内写入，异常回滚。审批后变更不继承授权。
5. 同步提示词、ARCHITECTURE_zh.md 第 3/11 章。问题结果确认和发布确认独立保留。

## 验收与测试

- 重现空 SQL/空资产错误时，不出现人工修复卡片、不修改工作区，返回 ERROR；修复提案继续成功进入一次 HITL。
- 关系、视图双文件、问题四文件作为一次方案通过，真实写入前无草稿变化，审批后完整应用。
- 坏 YAML、失败编译、失效基准、平台路径和跨租户访问均不写入；补工具/middleware 单测和原生恢复回归。
- Maven 全量测试、Spotless、打包、前端构建通过。

## 实现边界

- 已接入现有文件工具和原生 ReAct/HITL，未新增独立工作流引擎。中间技术错误自动修复，业务方案确认、问题真实结果验收与发布保留。
- 批量方案执行时再次校验，失效基准拒绝写入；运行时写失败回滚已变更文件，不提供崩溃恢复日志。
- 主流程优先完整方案；用户独立处理关系候选或单文件修正时保留原生入口，独立业务动作仍分别确认。
- 自动检查使用官方 CLI 的校验、编译和 dry-plan；真实数据执行继续走 validate_modeling_question，不能用规划通过冒充数据正确。
