# spec 041: 知识库成员、问答权限与 BI 身份接入（待确认）

> 状态：待办。对应 ADR 0050；等待与同事确认待决问题后再实施。

## 用户场景

1. 创建者上传数据、维护语义模型，并指定哪些用户可问答或编辑。
2. QUERY 用户在自己的 DataAgent 页面看到获授权的知识库，可提问和回看自己的会话；编辑按钮不可操作，也不能通过直接调用接口编辑。
3. EDIT 用户能维护库内数据与模型；只有 MANAGE 可调整成员或删除知识库。
4. BI 用户点击工具进入 DataAgent 后沿用同一稳定身份，无须再次注册不同账户。

## 数据与 API 草案

- 新增 `knowledge_base_grant(group_id, user_id, role, granted_by, created_at, updated_at)`；`(group_id,user_id)` 唯一，按 `user_id` 建可见库索引。所有者不写重复 grant。删除库时清除 grant。
- `GET /api/dataset-groups` 返回当前用户自己和获授权的库，并含 `ownerId` 的可展示信息、`tierForCurrentUser`、可问答/可编辑状态。列表查询按权限过滤，分页与索引需求按实际数量确定。
- `GET /api/dataset-groups/{id}/grants`、`PUT /.../grants/{userId}`、`DELETE /.../grants/{userId}` 仅 MANAGE 可用，写入审计记录；管理界面通过用户目录选择已有用户，不允许自授权升权。
- 原始文件下载、数据预览、上传、删除、建模、发布、文档读取与修改、语义配置、图谱构建、计划任务等接口逐一标注最低角色。所有写入接口服务端至少 EDIT；仅 MANAGE 管理成员和删除库。定时任务按创建任务的用户复核权限。
- 仅 QUERY 的用户可读取问答所需的公开库元信息和已发布语义描述，不通过详情接口暴露原始文件清单、文件内容或源连接信息。
- Chat 的 `groupIds` 仅作请求；后端以可信用户身份逐个授权并构造不可由用户伪造的运行作用域。空选库默认仅当前用户可问答的已发布库。
- 数据读取工具按已授权的 `(ownerId, groupId)` 取数据，写入工具按 EDIT 再校验；原始 SQL/模型通道需覆盖 Wren、证据检索、概览和查询结果文件下载。

## 实施顺序

1. 与 BI 定义并验证身份交换、用户映射和租户/管理员边界；本地登录保留为开发环境路径。
2. 增加 grant 表、权限服务、成员 API 与审计，保持老库默认私有。
3. 收口知识库、文件、建模和计划任务的接口权限；再打通跨 owner 的问答作用域，避免出现 UI 已共享但工具仍只查提问人数据的半成品。
4. 前端按服务端返回的 tier 渲染入口及灰置状态，增加成员管理界面。文案解释 QUERY 可能读取结果明细。
5. 按下面验收矩阵联调，完成旧数据迁移和回滚方案后部署。

## 验收矩阵

| 身份与操作 | 预期 |
| --- | --- |
| 未获授权用户获取列表、详情或直接猜测 groupId | 既不列出，也无法读取数据、调用工具或下载源文件 |
| QUERY 用户问答已授权库 | 能获得回答；运行时查的是库所有者名下的数据，并保留提问者自己的会话 |
| QUERY 用户直接调用上传、建模、发布、原始预览与成员接口 | 服务端拒绝；前端编辑入口灰置或隐藏 |
| EDIT 用户维护库，尝试增删成员或删库 | 可维护；增删成员和删库被拒绝 |
| MANAGE 用户调整权限 | 即时生效，有审计记录；撤权后旧会话不能继续查该库 |
| 用户同时选两个不同 owner 的库 | 分别授权、分别限域；第一期不跨 owner JOIN |
| 伪造 ownerId、改 groupId、复用旧会话、调用低层工具 | 不能越权；模型返回的参数不提升权限 |
| 用户退出、身份禁用或 BI 令牌过期 | 新请求拒绝；不会以 URL 参数或前端状态恢复权限 |
| 历史附件归属 | 创建者及其他成员不能下载提问用户的私有附件 |

## 明确边界

- 不将 Agent `RUN/EDIT` 当作知识库授权。
- 不通过前端置灰、prompt 或模型自律保护数据。
- 不开放原始上传文件和数据源密钥给 QUERY 用户。
- 暂不设计跨所有者 SQL JOIN、公开链接、多租户管理员的全局越权能力。
- 撤权后的既有历史处理、CSV 导出权限、QUERY 可见的只读详情和跨库提问范围以 ADR 0050 的待确认问题为准。
