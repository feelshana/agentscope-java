# spec 153: 口径页分步工作台

> 状态：已确认（2026-11-26）；P1、P1.5 本地实现完成，待真实知识库体验；P2 未开始。原型：口径页交互原型（4 张画板：总览、逐条核对、问题验证、发布检查）。
> 依赖 spec149（口径清单、核查、验证、按表发布）与 spec152（建模导航，`asset=calibers`）。

## 背景与目标

合并新工作台后，口径页仍是一个面板：表说明、全部口径行、勾选核查、生成验证问题、判定都在同一块区域，表多、口径多时难以定位"下一步该做什么"，核查和验证互相挤占。目标是按"起草 → 核对 → 验证 → 发布"拆成分步页面，一次只处理一张表的一个阶段，规则不变（核查、判定只能由人点击；验证不执行查询）。

## 方案概述

页面仍在 `KnowledgeWorkspaceShell` 的"语义模型 → 口径"下，用路由参数区分视图：`asset=calibers`（总览）、`&table=<model>&step=review|verify`（单表分步）。发布检查是工作台发布按钮打开的右侧抽屉。

1. **总览**：每张表一张卡片，显示主题、业务 × 统计对象、文档、口径数、四阶段进度（起草状态、已核对/总数、已判定/总数、可否发布）与唯一的"下一步"按钮（起草/继续核对/开始验证/已就绪）。右侧是选表目录：由各表 `scenario` 的业务、统计对象、默认指标、时间粒度生成；无默认指标的表给琥珀提示。顶部四个计数：待起草、待核对、待验证、可发布。
2. **逐条核对**：左侧口径队列按 `group` 分组，筛选"待核对 / 有问题 / 已核对 / 全部"，状态标记 ○ ✓ ●(本次有改动或有问题)。中间一次显示一个口径：说法、来源、范围维度逐一列出（未提及的显示"全部"/汇总值）、指标与单位、月累计说明、"不能相加"说明、与上次发布的差异、取值检查（灰色，只提示不阻断）。右侧是来源文档中声明该口径的原文片段并高亮。表说明（scenario）作为队列第一项"表说明"核对。底部："让助手改这一条…"（复用 `onDraft` 发起口径对话，附口径名和用户说明）、"核对通过，下一个"；快捷键 J/K 上下、A 通过。冲突行（`conflicts`）不可通过，显示两个版本让人选。
3. **问题验证**：仅当该表全部口径与表说明已核对后可进入。左侧每口径一题，进度条显示符合/不符合/待判定；中间显示问题、平台生成的查询、条件对照表（口径要求 vs dry-plan 展开 SQL 中的条件，平台标出一致/不一致）、可展开的 segment 与 expanded SQL。**不执行查询、不显示结果数值**（修正原型第 3 张画板中的"返回结果"区块，规则见 ADR0128/ADR0132）。底部"不符合，退回核对…"（可填说明，行回到有问题）与"符合，下一题"。
4. **发布检查抽屉**：分三组——阻断（未核对、未判定、不符合、文档有更新未重新起草、清单错误）、提示（取值未在数据中找到、无默认指标、规则重复警告）、已就绪（选表目录无重叠、每张口径表都有清单）。有阻断时发布按钮不可用；每项带跳转到对应表与步骤。DraftBar 中合并时丢失的"口径清单未完成不能发布"提示由此抽屉承接。

后端只做四处补充，其余复用现有 `CaliberController` 四个接口：
- `CaliberService.Row` 增加 `documentExcerpt`（来源文档中声明该口径的原文行，复用 `BusinessDocumentService#declaringText`，最多 20 行）。
- `CaliberService.Row` 增加 `publishedDiff`（与已发布清单同名口径的字段差异：新增/删除/修改的 where 取值、指标；未发布为 null）。
- `verdict` 接受可选说明 `notes: {口径名: 文本}`，写入 review 记录并在行上返回 `problemNote`；"退回核对"后该行回到 `PROBLEM`，再次核查时清除。
- `Check` 增加 `conditions: [{dimension, expected, actual, matched}]`，由平台比较口径 where 与 dry-plan 展开 SQL 的条件。

同步 ARCHITECTURE_zh.md 第 14 章口径页描述。

## 验收标准

1. Given 口径知识库有两张表分别处于"待核对"和"待验证"，When 打开口径页，Then 总览显示两张卡片各自的四阶段进度，按钮分别为"继续核对""开始验证"，计数正确。
2. Given 进入某表核对，When 按 J/K/A，Then 依次切换口径与核对通过，队列标记与进度实时更新，刷新页面后保留在同一表、同一步骤。
3. Given 口径行来自文档，When 查看该行，Then 右侧显示文档中声明该口径的原文片段并高亮；取值未在数据中找到时只显示灰色提示，"核对通过"仍可用。
4. Given 已发布过清单且本次文档改了某口径的取值，When 查看该行，Then 显示差异（删除/新增取值），队列中标为有改动。
5. Given 表中仍有未核对口径，When 进入验证，Then 被引导回核对；全部核对后，验证页每口径一题，显示条件对照与 SQL，页面上没有任何查询结果数值，后端没有执行查询。
6. Given 某题判定"不符合"并填写说明，When 回到核对，Then 该口径标为有问题并显示说明，重新核对通过后需再次验证。
7. Given 有任一阻断项，When 打开发布检查，Then 发布按钮不可用，阻断项可跳转；只剩提示项时可以发布。
8. Given 普通问数知识库，When 打开语义模型，Then 不出现口径入口；无 MANAGE 的用户调用口径接口仍返回 403/404，看不到他人知识库的口径。

## 不做的事

- 不执行验证查询、不展示数据结果；核查、判定不提供批量"全部通过"。
- 不改口径清单格式、编译规则、问数门禁和发布规则（spec149 P7）。
- 编辑只做 P1.5 的口径行表单；不在页面编辑表说明（仍让助手改），不新增、删除、改名口径，不在页面处理冲突。
- 不改普通问数知识库的页面。

## 测试要求

- 后端：`CaliberService` 的 documentExcerpt、publishedDiff、条件对照、verdict note 单测；越权用例覆盖非 MANAGE 用户与他人知识库。
- 前端：`caliberPresentation` 进度、下一步、阻断/提示分组、路由参数解析的单测（`*.test.mjs`）；`npm run build`。
- 真实验收：用测试知识库（会员规模表、活跃表）在浏览器走完总览 → 核对 → 验证 → 发布，核查与判定由用户本人点击。

## 分期

- P1：前端拆页与路由、发布检查抽屉（只用现有字段；差异、原文片段、条件对照先隐藏）。
- P1.5（2026-11-26 实测后追加）：核对页内表单编辑口径行，替代跳到只读工程页的"直接编辑"。见下节。
- P2：后端四处补充与前端对应区块。

## P1.5 核对页表单编辑

- 背景：P1 的"直接编辑"跳到工程页，该页只读且不列口径清单，用户找不到编辑位置；改 YAML 也不该是业务人员的操作。
- 交互：核对页点"编辑"后，当前口径详情变为表单：所属、也叫（说法）、取数条件（每行一个列，左侧为模型列的中文显示名并附列名，右侧多选取值，候选来自平台统计的取值，可手填文档中有而当前数据没有的值，可设为"不限"，可增删条件列，列只能选清单已用到的列）、单位、说明、待业务确认。口径名不可改。保存后回到查看态。
- 后端：`POST /api/dataset-groups/{groupId}/calibers/row`（`CaliberService#edit`，要求 MANAGE，工作区锁内复核）只改已存在的一个口径；有冲突的行拒绝。改动后整份清单经 `CaliberCompiler#compile` 校验，失败返回中文错误且不落盘；成功后按 `CaliberSources#apply` 记来源为"手工编辑"（文档再起草不覆盖，记冲突），`CaliberCompiler#sync` 重新生成，记录草稿修改（`ModelingTurnPurpose#EDIT`）并标记知识库草稿有改动。内容改变后该行核对与验证结论按哈希自动失效。
- `CaliberService.Table` 增加 `columns`：清单用到的列（条件列、范围列、固定范围列）的显示名与已统计取值，供表单使用。
- 验收：(1) 点"编辑"改取值并保存，清单、生成视图更新，该行回到待核对，来源显示"手工编辑"；(2) 写不存在的列或空条件时提示错误且清单不变；(3) 有冲突的口径不能编辑；(4) 无 MANAGE 的用户调用接口被拒绝。
