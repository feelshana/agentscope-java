# spec110：问数教练——列出常用问题，助手分析缺口并提议，批准后起草和核对

> 状态：用户已确认（2026-11-03），一期实施中（主流程、验证只核对 SQL、语义上下文面板）；第 8 节"问数优化"交互调整已实施（2026-11-03，验收见 test-reports/20261103-spec110-section8-acceptance.md）；二期为基准问题批量重新生成对照。决策见 [ADR0127](../adr/0127-query-coach.md)。

## 背景与目标

数据开发希望在一个地方，用"业务常问的问题"来推动语义建设：说出用户可能会问什么，由助手判断要补规则、关系、计算字段还是查询模板，人批准后再建，最后用同一批问题核对 SQL。初次建模只做基础，其他环节不主动提议资产（ADR0127）。

受益人是有 MANAGE 权限的数据开发；问数用户在发布后得到更稳定的口径和问答示例。

## 用户流程

```text
基础模型首次发布后，"问数教练"页签可用
① 列出常用问题（一次最多 10 个，可从推荐问题、试问、问数点赞中挑选）
② 助手逐题分析 → 方案表
③ 逐项批准 / 不需要（可在对话里补充说明后重新分析）
④ 助手按批准项起草：规则、关系、计算字段、查询模板
⑤ 同一批问题自动生成 SQL → 页面并排展示逻辑 SQL 与展开后的 SQL → 逐题确认（存为问答）
⑥ 草稿栏统一发布；问题保留为基准问题集，口径变更后可一键重新生成对照
```

方案表示例：

| 常用问题 | 能否答对 | 缺什么 | 提议 |
|---|---|---|---|
| 各部门上周的报表访问次数 | 能 | — | 直接生成 SQL 供核对 |
| 最近 30 天的流失用户有哪些 | 不能 | "流失用户"无定义 | 规则（术语定义），先用确认卡问清范围和截止日 |
| 外协和正式员工的访问对比 | 能，但分类要现写 | 分类反复使用 | 计算字段"人员类型" |
| 每个用户第几次访问某张报表 | 能，SQL 里用窗口函数 | — | 直接生成 SQL（单题不建查询模板，见第 8 节） |
| 首次访问后 7 天内回访的用户；首次访问来自哪个部门 | 能，但两题都要先算"每人首次访问" | 同一中间结果反复使用 | 查询模板「用户首次访问」，关联两题 |
| 按公司统计访问 | 不能 | 缺关系 | 关系，确认关联键与多对一 |

## 方案概述

**1. 入口与页面**
- 语义建模页新增页签"问数教练"，位于"建模对话"之后；基础模型首次发布前显示"完成首次建模并发布后可用"。
- 页面三栏（已由第 8 节改为左右两栏单题工作台）：
  - 左：常用问题清单（基准问题集），带状态：待分析、有提议、待核对、已确认；
  - 中：方案表与提议卡（批准、不需要）；
  - 右：SQL 核对区（逻辑 SQL、展开后的 SQL、口径说明、确认 / 不正确）。
- 对话过程复用建模会话，在问数教练页内以折叠的"助手过程"展示，不跳转到建模对话页签。
- **语义上下文面板**：页面右上角"查看 MDL 与规则"打开侧栏，展示问数助手实际依据的内容，可切换草稿 / 线上：
  - **MDL**：编译后的 `target/mdl.json`，复用 `CompiledMdlPanel`（模型、字段与计算字段、关系、查询模板，可按对象筛选）；
  - **规则**：`knowledge/rules/` 下全部文件原文，按小节分组（`## Default filters`、`## Naming conventions`、`## Canonical tables` 等），非官方小节标出"自建小节"；
  - **问答示例**：已确认的问题与 SQL。
  - 批准一项提议并起草后，面板中对应的新增或修改内容高亮，便于对照方案表核对。线上版本的规则取已发布快照，草稿版本取工作区。

**2. 新轮次与工具**
- 新增 `ModelingTurnPurpose#COACH`。本轮规则：
  - 逐题判断能否用现有模型、关系、规则答对，只用 `dry-plan` 检查，不查询数据；
  - 对缺口调用提议工具，不直接写文件；
  - 按 ADR0127 的选型原则判断类型。
- 提议工具扩展：`propose_semantic_asset` 改为 `propose_modeling_change`，`kind` 为 `rule`、`relationship`、`calculated_field`、`view`，并带上关联的问题 ID。只在问数教练轮次可用，其他轮次返回"请在问数教练中提议"。
- 批准后，按类型发起对应轮次：
  - 规则、关系、计算字段：普通建模轮次，带"已批准的方案"；
  - 查询模板：资产轮次（ADR0123 写入边界不变）。
- 起草完成后，对关联问题发起试问轮次生成 SQL。

**3. 其他环节的调整**
- 自动建模、处理文档轮次：从提示词中去掉提议，结束说明里把复杂口径列为"可在问数教练中处理"。
- 建模对话：不主动提议；用户明确要求"建视图/查询模板"时直接起草；遇到复杂需求时提示"可加入问数教练讨论"。
- 对话底部和语义资产页的 spec109 提议卡移除，未处理的历史提议迁入问数教练的方案表。

**4. 验证只核对 SQL**
- 问数教练与语义资产页的问题验证统一为：助手生成 SQL，平台用 `dry-plan` 展开，页面展示逻辑 SQL 与展开后的 SQL，人工确认，不执行。
- `MdlPublishService#verifyAssets` 不再执行 SQL；资产判定改为"SQL 符合预期 / 有问题"。
- 时间门禁只对 SQL 文本做规则检查（与试问确认一致），不合规的 SQL 不能确认。
- 资产起草自检的 `dry-run` 改为 `dry-plan`。

**5. 视图的时间与性能约束**
- 视图 SQL 不写时间条件（现有规则）；问数最终 SQL 按视图登记的时间列经门禁检查（现有 `PublishedAssetWindows`）。
- 依赖受限事实表、含窗口函数或聚合的视图：外层时间条件推不进内部计算，会扫描整张表，结果语义也随之变化。用户确认：核查卡标红提示风险，并要求在描述中写明统计范围，允许发布。
- 发布前对视图的 `EXPLAIN` 检查：用户确认保留（不读数据行，能发现类型和函数错误）。

**6. 先定口径再写 SQL，业务文档优先（2026-11-03 流程调整）**

一期验收发现：问数教练遇到"高频用户"未定义时，按"前 20 名"的假设写了 SQL，同时在建模对话页签生成确认卡；用户在问数教练看不到卡，在题目上点"不正确"说明口径后，那张卡仍未关闭，若再回答会写入相反的规则。调整如下：
- **查口径的顺序**：问数教练分析时先读业务规则，再读 `raw/docs/` 下的业务文档。
  1. 规则已有定义 → 直接写 SQL；
  2. 规则没有、文档有 → 不弹确认卡，提议一条规则并在要点中注明出处（文档名与小节），批准后写入，再生成 SQL；
  3. 都没有或互相矛盾 → 只出确认卡，题目 SQL 留空，"假设"行写"待确认口径"，不按猜测写 SQL；同一口径不再在方案表重复提议规则。
- **确认卡关联题目**：`request_user_confirmation` 增加 `question_ids`，卡记录服务的题目。
- **卡在问数教练中显示**：右侧核对区对有待确认口径的题直接显示确认卡（与建模对话底部是同一张，任一处回答即同步）；左侧状态显示"待确认口径"；卡旁提供"上传业务文档"（跳到"资料"页签）和"重新分析"。
- **答完自动生成 SQL**：回答确认卡后，平台先发写入确认轮次，再自动为卡关联的题目发起试问轮次生成 SQL。
- **说明口径即回答**：在题目上点"不正确"并说明时，平台先关闭该题关联的待确认卡，再按说明写入规则并重写 SQL。
- **业务文档入口**：文档统一存于 `raw/docs/`，以首次建模时在"资料"页签上传为主；问数教练顶部显示已有文档数和"建议首次建模时上传口径文档"的提示，上传后点"重新分析"。

**7. 基准问题集**
- 问数教练中的问题存于 `knowledge/questions/`，标记来源 `coach`，作为基准问题。
- "重新生成对照"：对全部或选中的基准问题重新生成 SQL，与已确认的 SQL 并排对比，有差异的进入待确认；结合 spec108，口径变更后自动提示待复核数量。

**8. 问数优化：收紧视图提议，改为单题工作台（2026-11-03 交互调整）**

起因是对照外部方案评审（Codex 原型，见 SESSION_LOG），发现两个问题：
- 第 5 步"聚合、窗口函数、多步计算才用 view"措辞过宽，单题的 GROUP BY 或窗口函数也会被当成缺口去提议查询模板；
- 三栏布局在没选题时大多是空白，"已确认、可发布、问答"等状态说法混用。

调整如下。

1. **改名**：页签和页面标题改为"问数优化"，副标题"用业务问题检验并完善模型"。轮次标识 `coach`、接口路径、文件名和 ADR0127 中的名称不变。
2. **视图提议收紧**（`ModelingTurnRules#COACH` 第 5 步）：
   - 单题需要的聚合、窗口函数、多步计算，直接写进该题 SQL，不算缺口，不提议查询模板；
   - 本批有 2 道及以上的题反复用到同一段多步逻辑（同一个中间结果，例如"每人首次访问时间"）时，提议一个查询模板，`question_ids` 列出这些题；
   - 用户明确要求时照旧（建模对话 `explicit=true`）；
   - **已被 ADR0128 调整（2026-11-03）**：问数优化不再提议查询模板，上两条中"本批 2 题复用才提议"作废，工具在问数优化轮次拒绝 kind=view；
   - 计算字段同理：本批反复使用的单行分类才提议。
   跨大批问题的"公共资产提炼"不在本 spec。
3. **每题能力分析**：
   - 问数教练对每道题都写 `knowledge/questions/<ID>.yml`（SQL 为空的题也写），增加 `analysis` 列表，每项为 `{ok: true|false, text: 一句业务语言}`，最多 5 项。例如"可复用访问明细模型"为 ok，"高频用户口径未定义"为缺口。
   - 平台只读取和展示，不参与判定；缺少或格式不对时页面不显示该区块。
4. **三种结论**：由平台按题目的关联对象推出，不让模型另写。
   - 有关联的待确认卡 → "需要补充业务定义"；
   - 有关联且未处理或已批准未起草的提议 → "建议完善模型"；
   - 已有 SQL 且没有上述情况 → "现有模型可以回答"；
   - 还没分析 → "待分析"。
   - 实施补充：助手列了缺口却没有出卡或提议时（实测两次），页面把这些项标为"按假设处理"，结论注明假设数量，提示核对 SQL 时留意；问数优化轮次可只读 `views/` 判断能否复用已有查询模板。
   - 实施补充（用户实测）：问数优化轮次自称"已有确认结果"后写了规则并补回 SQL，改为代码约束：该轮次只能写 `knowledge/questions/`；题目有未答复的关联确认卡时，任何轮次写入非空 SQL 都被拒绝。
5. **统一状态**：待分析 → 待确认口径 / 待批准方案 → 待核对 SQL → 已确认（再标"待发布"或"已发布"）。依赖变化时转为待复核（spec108）。左侧清单、右侧工作台和问答示例都用这一套说法。
6. **布局改为左右两栏**，取代第 1 节的三栏：
   - **左栏问题清单**：每题下一行状态；支持添加问题、按状态筛选、勾选后"分析选中问题"，仍按批次分析。
   - **右栏单题工作台**：标题为题目原文，下面是步骤条"分析 → 口径/方案 → SQL → 保存问答"。步骤条只表示进度，已到达的步骤可以点开回看，未到达的不可点。各步内容：
     - 分析：能力分析清单（✓ / !）与结论；
     - 口径/方案：关联的确认卡，或关联的提议（批准、不需要）；提议服务多道题时注明"同时服务 N 道题"；
     - SQL：逻辑 SQL、展开后的 SQL、口径说明，以及确认、不正确；
     - 保存问答：确认状态、依赖和发布状态。
     每一步只突出一个主操作。
   - **未选题时**：右栏显示按状态的计数和"分析选中问题"。
   - **发布**：不放进单题步骤，仍在草稿栏统一发布。
   - "查看 MDL 与规则"侧栏、折叠的"助手过程"保留。

## 验收标准（Given-When-Then）

1. Given 新知识库首次自动建模，When 建模完成，Then 只写模型、描述、关系和文档规则，没有任何提议或资产文件；问数教练页签在首次发布前不可用。
2. Given 建模对话，When 用户说"以后要分析每个用户第几次访问某张报表"，Then 助手不提议，只提示可加入问数教练；When 用户明确说"建一个查询模板……"，Then 直接起草。
3. Given 问数教练，When 列出方案表示例中的问题，Then 方案表分别给出"直接生成 / 规则 / 计算字段 / 直接生成（单题窗口函数）/ 查询模板（两题共用）/ 关系"，规则类先用确认卡澄清歧义。
4. Given 方案表，When 批准其中 3 项、其余选"不需要"，Then 只起草批准项，未批准项不写任何文件。
5. Given 起草完成，When 关联问题生成 SQL，Then 页面展示逻辑 SQL 与展开后的 SQL，不执行查询；确认后存为问答，状态为已确认。
6. Given 语义资产页验证查询模板，When 生成并提交验证，Then 不执行 SQL，只核对 SQL 并判定；不合时间门禁的 SQL 不能判定为符合预期。
7. Given 资产轮次起草，When 自检，Then 只调用 `dry-plan`，不调用 `dry-run`。
8. Given 基准问题已确认，When 修改相关规则后点"重新生成对照"，Then 有差异的问题并排展示新旧 SQL，进入待确认。
9. Given 依赖受限事实表、含窗口函数的查询模板，When 核查，Then 按用户确认的约束处理（提示或禁止）。
10. Given 只有 QUERY 权限的用户，When 访问问数教练接口，Then 被拒绝，看不到问题和方案。
11. Given 问数教练页，When 打开"查看 MDL 与规则"，Then 能在草稿与线上之间切换，看到编译后的 MDL、全部规则原文（按小节分组）和已确认问答；起草后新增的规则条目和 MDL 对象被高亮。
12. Given 规则和文档都没有"高频用户"的定义，When 问数教练分析"高频用户爱看哪些报表"，Then 只出确认卡（关联该题），题目 SQL 为空、状态"待确认口径"，方案表不重复提议该规则。
13. Given 问数教练中有待确认口径的题，When 选中该题，Then 右侧直接显示确认卡；When 回答，Then 写入规则后自动为该题生成 SQL。
14. Given 题目有关联的待确认卡，When 用户改为在题目上说明口径，Then 该卡被关闭，规则按说明写入并重写 SQL，不留下待确认卡。
15. Given 业务文档中写明了"高频用户"的定义但规则中没有，When 问数教练分析，Then 不出确认卡，提议规则并注明文档出处。
16. Given 语义建模页，When 打开，Then 页签与标题为"问数优化"；首次发布前的不可用提示不变。
17. Given 本批只有一道题需要窗口函数，When 分析，Then 不提议查询模板，直接写 SQL；Given 本批两道题都要先算"每人首次访问"，When 分析，Then 只提议一个查询模板，并关联这两道题。
18. Given 分析完成，When 选中任一题（包括 SQL 为空的题），Then 右栏显示能力分析清单（✓ / !）和平台推出的结论，三种结论与题目关联的确认卡、提议、SQL 一致。
19. Given 有待确认卡的题，When 选中，Then 步骤条停在"口径/方案"，SQL 和保存问答两步不可点；回答后自动进入 SQL 步骤。
20. Given 未选中任何题，When 打开问数优化，Then 右栏显示各状态计数和"分析选中问题"，没有空白面板；单题步骤中没有发布操作。

## 测试要求

- 单元测试：
  - COACH 轮次的工具可用性（提议工具只在 COACH 轮次可用）；
  - 提议的类型、问题关联与批准流转；
  - `verifyAssets` 不再执行 SQL，只调用 `dry-plan`；
  - 资产自检不调用 `dry-run`；
  - 基准问题的重新生成与差异判定；
  - 提示词断言（AUTO、DOCUMENT、CHAT 不提议；COACH 单题不提议查询模板、本批复用才提议）；
  - 问题文件 `analysis` 字段的读取，以及缺失或格式错误时的容错。
- 多租户：QUERY 用户与其他用户看不到问数教练内容；批准排队期间被撤销 MANAGE 时拒绝起草。
- 真实验收：以报表访问知识库跑通验收 1–6，以重启后日志为准。
- 全量运行 AGENTS.md 第 8 节验证命令。
