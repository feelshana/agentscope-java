# spec098：推荐问题按日期规则生成，并在问数页首次回填

> 状态：已实施，待真实验收（2026-10-29）。措辞问“每天的指标”、发布后后台生成均经用户确认。

## 背景与目标

推荐问题用来引导用户先问数，再从结果进入归因、异常检测和预测（spec097）。现状有三个问题：

- 推荐问题只在建模页打开"试问"时由模型现场生成 3 个，不保存。
- 日期只把采样值当参考交给模型，没有固定规则，日期可能落在没有数据的时间段。
- 问数页选中知识库时没有任何引导。

目标：每个知识库有 1 个默认推荐问题，日期按固定规则确定、保证有数据；用户在问数页选中该知识库时自动填入输入框，可以直接发送。

## 方案概述

1. **日期规则由平台确定，模型只选指标和措辞。** 针对"带日期的事实表"：
   - **上传表，且有时间列**：平台对数据集 MySQL 中的 `ds_` 表执行一次 `MIN/MAX`。文本日期按登记的时间列格式先转换再取值，得到实际起止日期。问题写成"`起始日期` 至 `结束日期` 每天的`指标`"。
   - **外部表**：问题写成"最近一个月每天的`指标`"。表登记了查询时间窗口、且窗口小于 30 天时，改用窗口天数，例如"最近 7 天"，保证能通过时间门禁。
   - **没有带日期的事实表**：按原有方式生成，即一个汇总、排名或分组问题。
   - 有多张事实表时，由模型从中选一张最有业务意义的表和它的度量；日期范围只能使用平台给出的值，模型不能自己改。
2. **数量与保存**：默认生成 1 个，保存在 `dataagent_dataset_group.recommended_question`（`DatasetGroupRepository#updateRecommendedQuestion` 定向更新）。生成时机：
   - 发布成功后在后台生成（`RecommendedQuestionService#published` 监听 `PublishedQueryProjectChanged`，与问数准备同一事件），不影响发布结果；
   - 本功能上线前已发布、还没有推荐问题的知识库，在第一次读取时后台补生成；
   - 建模页"试问"面板顶部固定显示"推荐问题"卡片：可直接试问、修改、"换一个"；试问过的卡片带"推荐问题"标记。没有推荐问题时，按同样规则由草稿模型生成并保存（`GET /modeling/questions/recommended`，需 MANAGE），发布前也可用。"其他问题建议"另行生成，单独列出。
   - 推荐问题不属于语义模型，修改立即生效（`POST /modeling/questions/recommended`）；修改后标记为手动（`recommended_question_manual`），后续发布不再覆盖；清空保存或"换一个"恢复自动生成（`POST /recommended/regenerate`）。
   - 推荐问题只有日期一个维度：模型给出的指标名含"各/按/每个/分组/分布/占比/排名/排行/对比/Top/前 N/最多/最少/最高/最低"时丢弃（`RecommendedQuestionService#OTHER_DIMENSION`）。
   - 模型只返回所选表名和指标名，问题文本由平台用固定日期拼成"`日期` 每天的`指标`"；表名不在候选中、或指标名自带日期时丢弃，不回填。
3. **问数页首次回填**：同时满足以下条件时，把推荐问题填入输入框，并在输入框下方用小字说明"推荐问题，可直接发送或修改"：
   - 只选中一个知识库；
   - 输入框为空；
   - 当前会话还没有发过消息。

   用户输入或发送过之后不再覆盖。读取推荐问题需要该知识库的 QUERY 权限。
4. **措辞要能进入后续分析**：日期类推荐问题统一问"每天的指标"，结果是按日序列，回答下方会出现 spec097 的"为什么变化？/ 有没有异常？/ 未来走势？"按钮，起到引导作用。如果问成"`起止日期` 的指标是多少"，结果只有一个汇总数，就不会出现这些按钮。

## 影响面

- **后端：**
  - `QuestionSuggestionService`：新的日期规则和提示词，默认 1 个；
  - 新增"上传表日期范围"查询：在数据集 MySQL 上执行，用 `subscribeOn(boundedElastic)`；
  - 发布后后台生成：接入现有问数准备流程；
  - 推荐问题的存取接口：问数页读取需 QUERY；
  - 试问确认后的替换逻辑。
- **前端：** 问数页首次回填与说明文字；试问面板只显示 1 条推荐，加"更多推荐"。
- **数据：** 推荐问题字段，需迁移脚本 `docs/migrations/0097`。
- **文档：** ARCHITECTURE_zh.md。

## 验收标准

1. Given "测试"知识库（报表访问明细为上传表，数据覆盖 2026-09-20 至 2026-10-07），When 发布后，Then 推荐问题为"2026-09-20 至 2026-10-07 每天的报表访问次数"一类，日期与实际数据一致。
2. Given 只有外部事实表、且时间窗口为 7 天的知识库，Then 推荐问题写"最近 7 天每天的…"，发送后能通过时间门禁。
3. Given 没有带日期事实表的知识库，Then 推荐问题按原有方式生成（汇总、排名或分组）。
4. Given 用户在问数页只选中该知识库、输入框为空的新会话，Then 输入框自动填入推荐问题；切换到另一个知识库时换成那个知识库的推荐问题；用户输入过内容后不覆盖。
5. Given 发送推荐问题，Then 回答是按日结果，下方出现"继续分析"按钮。
6. Given 只有 QUERY 权限的用户，Then 能看到推荐问题；没有权限的用户读不到。
7. Given 模型不可用或生成失败，Then 不回填，问数正常可用。

## 不做的事

- 不做多个推荐问题轮播，也不按用户个性化推荐。
- 推荐问题不写入语义模型，不作为问答对，不进入召回。
- 不改时间门禁规则本身。

## 测试要求

- 日期规则的单元测试：上传表 MIN/MAX（含文本日期格式）、外部表窗口截断（<30 天与 ≥30 天）、无日期表回退。
- 推荐问题读取的权限测试：QUERY 可读、无权限 404。
- 发布后生成失败不影响发布结果。
- 前端：浏览器验收回填与"不覆盖用户输入"。
