# spec099：服务器拉取源码并构建应用镜像

状态：2026-10-29用户反馈66源码已拉取；源码更新、只构建与应用镜像入口已实施并通过本地空缓存构建/镜像预检及保护用例，随本次提交交付，用户自行push。66新builder及源码构建、业务启停与回退仍待完成。

## 目标和范围

用户选择GitHub源码交付：本地测试并提交源码，66按明确提交构建应用镜像，再启动容器。无需镜像托管服务和Jenkins。构建工具在容器中运行，宿主Java8、glibc与既有服务不变；应用仍同容器运行Java17/Python/Wren，分析沙箱为独立兄弟容器。

## 实施要求

- 使用完整仓库所需的core、harness、BOM和扩展模块，不能依赖开发机预装的SNAPSHOT或仅复制standalone模块。
- 只从明确提交构建；源码、镜像、日志记录提交标识。保留旧镜像，不自动覆盖正在运行的服务。
- 构建环境固定JDK/Maven/Node版本，使用项目专属依赖缓存和资源预算；源站访问和旧内核兼容需实测。
- 最终镜像包含应用、前端和已验收运行依赖；生产配置、密钥、模型缓存及业务数据外置，同路径共享沙箱文件。
- 构建完成与业务启动为不同步骤；先检查镜像，再在具备生产数据库/配置后明确启动。构建失败不停止旧服务。
- 源码拉取有限重试并有单次超时，兼容宿主Git1.8.3.1；普通账号执行，项目独立Compose配置/名称，无全局镜像清理，不按参考Dify脚本重写生产配置。
- 不自动提交/推送本地修改、不把私有配置和个人交接加入Git；不操作其他项目，不全局清理或重启Docker。

## 验收

1. 干净源码和空项目依赖缓存可构建，不借用本机Maven仓库掩盖缺失模块。
2. 缺依赖、网络失败、脏工作区和错误提交明确失败，旧服务继续运行。
3. 包内无私有配置，前端前缀正确，镜像记录完整提交和运行依赖信息。
4. 构建资源受限，旧服务保留；镜像启动、历史/附件/权限/沙箱及停启恢复通过。
5. 有明确回退步骤，不把数据库结构回退等同于镜像回退。

现有并发阻塞是独立业务缺陷，本spec不自动修改；旧运行环境验收不能替代新源码构建或正式上线验收。
