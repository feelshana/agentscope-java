# spec091：建模全流程交互重设计（推荐问题预填、问题直接确认、流程连贯）

> 状态：用户已确认（2026-10-21），已实施，待真实验收。调整 spec090 的第 2–4 节交互，不改变"基础建模不生成问答对、问答只来自用户确认"的边界。

## 背景与目标

2026-10-21 用户试用反馈：
1. 问题表单里只有灰色占位示例，不能直接使用。推荐问题应直接以可编辑的正文预填。
2. 问题确认太繁琐：必须先在页面上"Wren 验证当前草稿"跑出结果才能确认，并且确认区在"检查与发布"页最下方（发布面板之后）。
3. 填写问题后停在对话页，用户要自己找到"检查与发布"，操作不连贯。

目标：建模从上传到发布是一条线性流程，每一步都有唯一的下一步按钮，用户不需要在标签页之间自己寻找入口。

## 方案概述（目标交互）

```
① 数据与资料 ──上传/关联表──▶ 采样 ──▶ 表角色与事实表时间配置（已有弹窗）
② 对话建模（自动）：Auto-pilot 建模；确认卡逐张处理；全部确认且编译成功
③ 弹窗"基础建模已完成"：预填推荐问题（可编辑/删除/新增，≤5）
      ├─ 跳过 ──────────────────────────────▶ ④
      └─ 提交 ──立即跳转──▶ ④（问题显示"生成 SQL 中"，后台继续）
④ 检查与发布（一页从上到下）
      A. 状态条：模型校验结果 · 已确认 x/y 题 · 【发布】主按钮
      B. 问题确认（列表 + 右侧明细；确认按钮在明细里）
      C. 发布详情（变更 diff 等，默认折叠）
⑤ 发布成功 ──▶【去问数】
```

### 1. 推荐问题预填（反馈 1）
- 新增后端接口 `GET /api/modeling/{groupId}/question-suggestions`：平台基于当前编译后的模型目录（模型名、列描述、事实/维度角色）、业务文档摘要与逐表时间配置，用 LLM 生成最多 5 个业务问题。受限事实表的问题带上符合窗口的具体日期范围。这是确定的平台步骤，不依赖建模 Agent 自觉执行。
- 弹窗打开时请求该接口，把结果作为**输入框的正文**（不是 placeholder）填入，用户可直接提交、修改、删除或新增。接口失败或超时时退回空行，并保留现有占位提示。
- "数据与资料"页和"检查与发布"页的"＋添加问题"入口使用同一表单，同样预填。

### 2. 提交后自动跳到检查与发布（反馈 3）
- 弹窗提交后立即切到"检查与发布"，问题列表马上出现这些问题，状态为"生成 SQL 中"。对话面板保持挂载（现有 `display:none`），助手在后台继续生成 SQL。
- `ModelingChatPanel` 在 `knowledge/questions/` 的 `write_file` 成功（`tool_result`）时立即触发 `modeling:updated`，问题逐个刷新，不用等整轮结束。
- 某题生成失败时，在该题明细里显示原因，并提供"让助手重试"按钮。

### 3. 问题直接确认（反馈 2）
- **确认不再要求先执行**：明细中显示问题原文（只读）、口径说明、SQL，直接提供【确认】。确认时平台只做静态检查：只读、禁止笛卡尔积、时间门禁、引用的模型存在。通过后即写入 `knowledge/sql/<ID>.md`（`source:user-confirmed`）。
- 【试运行】是可选按钮，结果在明细内展示，不是确认的前提。截断结果不阻止确认。
- 明细内操作只保留：确认、试运行、修改 SQL（保存后回到待确认）、删除。"让助手修复"放进"更多"菜单。删除"视图定义 SQL"快照区（Cube/View 不读不写）。
- 列表顶部提供【全部确认】：对所有已生成 SQL、未确认的题依次执行确认，逐题显示结果。
- **确认失效规则改为与模型解耦**：确认只绑定问题与 SQL 的哈希。模型变化后不再整体置为"已过期需重验"。发布时平台对已确认 SQL 做官方 `dry-plan`（不执行）：通过的写入发布版本；不通过的不写入，在发布结果中列出并把该题退回"待确认"，**不阻止模型发布**。

### 4. 检查与发布页布局
- 顺序改为：状态条（含发布主按钮）→ 问题确认 → 折叠的发布详情。精简重复说明文字，只保留一句"问题可选，不影响发布"。
- 发布成功后，状态条的主按钮变为【去问数】。

### 5. 对话建模页
- 左栏只保留：业务文档、"下一步：检查与发布 →"、"查看语义模型"。去掉重复的"验证业务问题 →"和"请助手检查草稿"按钮（自动建模已包含校验与编译）。

## 影响面

- 后端：新增问题推荐服务与接口（`web/` 端点 + `dataset/` 服务，复用字段说明模型与 `FactQueryWindowPolicy`）。`MdlQuestionStore#decide` 支持不依赖验证回执的确认（静态检查 + 门禁），确认绑定问题/SQL 哈希。`MdlWorkspaceService#copyToStaging` 发布时对已确认 SQL 做 `dry-plan`，失败的题退回。`MdlQuestionService`/控制器调整。
- 前端：`QuestionIntakeForm`（预填）、`VerifyQuestionsPrompt`（提交后跳转）、`SemanticModelingPage`（发布页顺序、左栏精简）、`ModelingQuestionsPanel`（列表+明细、直接确认、全部确认、去掉视图快照）、`ModelingChatPanel`（问题文件写入即刷新）、`api/modelingQuestions.ts`。
- 数据：问题回执格式变更（确认不再需要 validationId）。按"不考虑历史数据"，旧回执视为待确认。
- 文档：ARCHITECTURE_zh.md 第 14 章问题流程、spec090 状态行注明"交互由 spec091 调整"、spec 索引。不需要 ADR（产品流程调整，不改变系统边界）。

## 验收标准

1. Given 自动建模完成且编译成功，When 弹窗打开，Then 输入框里已有 1–5 个推荐问题正文（非占位），受限事实表的问题含具体日期，可编辑、删除、新增。
2. Given 推荐接口失败，When 弹窗打开，Then 显示空行与占位提示，可手工填写。
3. Given 用户提交问题，When 点击提交，Then 页面立即切到"检查与发布"，问题列表显示这些问题为"生成 SQL 中"，每题写入后无需刷新即显示 SQL。
4. Given 一题已有 SQL 且未试运行，When 在明细中点【确认】，Then 静态检查与门禁通过即变为"已确认"，并生成 `knowledge/sql/<ID>.md`。
5. Given SQL 含 CROSS JOIN 或超出时间窗口，When 点【确认】，Then 拒绝并在明细显示原因，状态不变。
6. Given 3 题待确认，When 点【全部确认】，Then 逐题确认并显示每题结果，失败题不影响其他题。
7. Given 已确认问题引用的列在后续建模中被删除，When 发布，Then 模型照常发布，该题不进入发布版本，发布结果列出原因，该题回到"待确认"。
8. Given 检查与发布页，When 打开，Then 自上而下为状态条（含发布按钮）、问题确认、折叠的发布详情。
9. 问数 `recall_queries` 能召回发布版本中已确认的问答（沿用 spec090 验收）。

## 不做的事

- 不让建模 Agent 自动保存问答，不恢复 memory store。
- 不在确认时强制执行查询；不把试运行结果作为确认前提。
- 不改官方 Wren 技能文件，不改官方编译产物。
- 推荐问题只是问题文本，不预生成 SQL；不超过 5 题。
- 不处理历史问题回执的迁移。

## 测试要求

- `MdlQuestionStoreTest`：无回执直接确认；CROSS JOIN/门禁拒绝；问题或 SQL 修改后确认失效；模型变化不使确认失效。
- 发布测试：已确认 SQL `dry-plan` 失败的题不写入发布版本，并退回待确认，发布成功。
- 推荐服务测试：输出最多 5 题；受限事实表的问题带日期；LLM 失败返回空列表；只读取当前用户有 MANAGE 的库（看不到别人的库）。
- 前端：`npm run build`；真实验收按验收标准 1–9 走一遍并记录日志。

## 已确认决定（2026-10-21）

1. 推荐问题由平台接口生成（确定执行），不依赖建模 Agent 在对话末尾给出。
2. 确认与模型变化解耦；发布时 `dry-plan` 失败的题退回，不阻止发布。
3. 截断的试运行结果不阻止确认。
