# spec 044：问题验收依据与清晰操作闭环

## 背景与目标

视图查询只显示外层 SQL，用户无法审阅实际过滤与计算；业务确认后缺少持久反馈；多个问题入口藏在聊天输入区。让同一批分析问题贯穿对话、验证、确认与发布，始终显示已完成事项及下一步。

## 方案概述

复用 MdlWorkspaceReader，将验证时的视图目录（名称、定义 SQL、说明、路径）及问题 SQL 保存到平台验证凭据；验收页展示“本次验证快照”，明确目录包含当时全部视图，不冒充物理执行计划。旧凭据没有快照时提示重验；过期凭据保留旧依据并禁止确认。确认接口返回的 Review 立即更新卡片，确认人/时间持续可见，成功反馈与下一步按服务端工作流展示。问题清单在建模与验证阶段均提供显著“添加问题”弹窗，可一次填多个，每行一项，最多 50 个；仅带入对话，发送并经原生 HITL 后才标为已保存。复用同一个弹窗组件，模型修改仍遵守 YAML-first。

## 影响面

- 后端：MdlQuestionStore.Receipt、MdlPublishService#validateQuestion；无新端点/数据库迁移。
- 前端：ModelingQuestionsPanel、ModelingChatPanel、SemanticModelingPage、api/modelingQuestions.ts；统一问题输入组件。
- 文档：ARCHITECTURE_zh.md 第 11 章；ADR 0054。

## 验收标准

1. 视图问题执行后可在同一验收卡展开本次验证的视图定义与外层 SQL；修改视图后旧快照不变，状态过期且不可确认。
2. 旧凭据正常加载，显示没有定义快照及重新验证提示，不拼接当前定义伪装历史依据。
3. 确认成功即显示已确认、确认人/时间，撤下原确认按钮；失败显示错误，不误报成功。刷新后仍显示确认状态。
4. 下一步依工作流提示继续完善/验证/确认/发布/问数，只有服务端允许发布才提供发布行动。
5. 建模和验证问题清单均可显式添加一个或多个问题；未发送/未批准不写入，保存后由真实 YAML 清单展示。
6. 切换知识库时不泄漏上一组的状态、反馈、输入；保持现有 ownerId/DatasetScope 校验。

## 不做的事

- 不重写原生确认与 Agent 循环，不直查物理 SQL，不推断字段名为百分比，不自动发布或批准问题。

## 测试要求

新增凭据快照持久化、视图变化后失效、旧凭据兼容测试；保持多租户服务用例；前端构建及浏览器验证添加、确认/刷新、视图快照与下一步。
