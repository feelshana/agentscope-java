# spec149：多表口径资产——每表一份口径清单与使用场景，问数按场景选表、按口径取数

> 状态：已确认（2026-11-24，待确认项按建议）。P0、P1、P2、P4（时间维度门禁除外）本地完成（未提交）；P3 未开始；P5（多表选表、指标说法、范围维度、`run_sql` 原表门禁）2026-11-24 按建议确认并本地完成（未提交），多表真实验收待用户提供活跃用户等表和文档。P2 的验证问题由平台按口径确定性生成 Cube 查询（不调用模型），展开并 EXPLAIN 后由人判定。决策见 [ADR0155](../adr/0155-caliber-assets-view-plus-cube.md)。依据 [2026-11-24 对比验收](../test-reports/20261124-wren-dialog-vs-cube-view.md)。
>
> 变更记录：2026-11-24 初稿为单表"文档口径表生成 View + Cube"；同日按用户需求改为多表（一个知识库放很多表，每表有取数条件取值说明和使用场景），并补入规则/术语分工、口径清单作为唯一事实源、对话与编辑修改、取值存在性检查；再补入"清单的入口与确认"（行级来源与来源冲突）与业务文档多份增量上传（用户确认放开多份）。

## 背景与目标

对比验收中，只靠模型、术语、规则时 LLM 每题现场拼取数条件，多次自纠，两次建模写出的口径规则不一致；口径固化为 View + Cube 后一次取对。用户将把很多张预统计表放进同一个知识库，每张表都有"查数条件取值说明"（口径表）和"使用场景"，再让业务用户问数。

目标：每张表的口径一次定义、人核查一次；问数先按使用场景选对表，再按口径名取数，不再让 LLM 拼条件。受益人：问数用户（答案稳定、选表正确）、数据开发（批量上架、只核查变化）。

## 核心概念：每张表三件东西，各有唯一去处

| 内容 | 唯一事实源（工程内） | 发布后问数怎么用 |
|---|---|---|
| **表说明**：主题、粒度（日/月）、度量含义、固定汇总维、适用与不适用的问题、与相近表的区别 | `calibers/<模型>.yml` 的 `scenario` 段 | 平台生成模型描述、Cube 描述，以及 `## Canonical tables` 中一行选表规则 |
| **口径清单**：口径名、所属体系、取数条件、同义说法 | `calibers/<模型>.yml` 的 `calibers` 段 | 平台生成 `views/<模型>_caliber`（每口径一段）与 `cubes/<模型>_metrics` |
| **业务术语与一般原则**：跨表的说法、"不同口径不能相加"、默认汇总范围 | `knowledge/rules/`、官方 Naming conventions | `get_instructions` 照常读取 |

分工规则：具体口径的取数条件只存在于口径清单；规则只写原则和指引（"会员规模口径见 `<模型>_metrics`，按口径名取数，不要自拼条件"），术语只写说法到口径名的映射，不写取值条件。没有口径清单的表维持现有建模方式。

口径清单示意（格式以实现为准）：

```yaml
model: hhweb_video_vip_more_dimension_m
scenario:
  subject: 咪咕视频会员规模
  grain: month            # 时间列 period_id
  measures: {cnt_zd: 会员数, cnt_xz: 新增, cnt_jxz: 净新增, cnt_td: 退订}
  fixed_scope: {province_name: 全国, channel_type: 全部, pay_type1: 全部}
  use_for: [会员数, 会员新增与退订, 会员月趋势]
  not_for: [收入, 播放时长]
conventions: {all_value: 全部, unrestricted: 不限}
calibers:
  - {name: 足球通, group: 体育会员, synonyms: [足球通会员],
     where: {vip_type_1: 全部, vip_type_3: 体育赛事, vip_type_4: 足球, vip_type_5: 足球通, vip_type_6: 足球通会员}}
```

## 清单的入口与确认

改动有三个入口，都只写草稿清单；确认只有一处，由人完成：

| 入口 | 触发 | 产出 |
|---|---|---|
| 上传或重传业务文档 | 基础建模完成或文档更新后，卡片"可生成/可更新口径清单（涉及表 X、Y）"，用户点"起草" | 按文档逐行列出新增、修改、删除 |
| 建模对话 | 用户提出新增、修改、删除口径或调整使用场景 | 资产轮次改清单，变化行列入"AI 建模结果" |
| 表格编辑 | 数据开发在口径页直接编辑 | 直接改草稿行 |

- 问数优化发现缺口只提议"新增口径"，批准后经上述入口落地，不直接改清单。
- 确认唯一入口：口径页按表核查变化行（条件、取值检查、生成的 View/Cube 预览）→ 问题验证 → 草稿栏发布。助手不得声明口径已核查或已确认。
- 行级来源：每行记录来源（文档名、对话轮次或编辑人）与时间，核查页展示，便于追溯。
- 来源冲突：后到的改动与人已改过的行不一致时（如对话改过足球通条件，重传文档又是旧条件），该行标为冲突，由人选择保留哪一个，不静默覆盖；两份文档对同一表同一口径条件不同，同样按冲突处理。

## 方案概述

**P0 前置**
- Wren 升级到 ≥0.16（中文 Cube 元数据），处理 0.18 的 `run_sql` LIMIT 叠加与 Cube 维度自别名问题（构建检查报错提示改名）；回归清单沿用 spec118 第 1 部分。
- 问题验证补列存在性检查：引用不存在列的用例不能判"符合预期"、不存为已确认问答（0.18 dry-plan 未拦住 `stat_date/member_cnt`）。

**P1 建设：文档 → 口径清单草稿**
- 业务文档放开多份、增量上传：文档首部声明一个或多个"适用模型"（现有文档已有），平台据此关联文档与表；未声明的文档作为全库通用的规则与术语材料。上限由 20 份提高（数量以代码常量为准），保留单份大小上限；不鼓励一份总文档（易截断、无法定位变化）。提供文档模板（表说明、指标定义、固定汇总维、口径表、不适用场景）。
- 增量规则：新增文档只为其声明的表起草或更新清单；重传同名文档只对其声明的表与当前清单逐行比对，列出新增、修改、删除，确认后写入草稿，只有变化行待核查；删除文档不删除清单，仅去掉来源关联。
- 基础建模照常（新增表走增量建模）。建模结果中按表给出"可生成口径清单"卡片；用户点"起草"后，助手把文档口径表照抄为口径清单，文档缺的内容（如指标含义、合并方式）标"待业务确认"，不自行补全。
- 取值存在性检查：上传表由平台对清单引用的列做去重统计（实现为首次检查时统计并按数据集变化失效缓存，不改上传流程，已有表也可检查）；清单中引用了不存在的取值时，在核查页逐行标出（如"橄榄球会员"不存在）。外部表只按采样提示，不在建模阶段查询数据（ADR0135）。
- 起草同时在草稿中把规则、术语里与清单重复的具体条件改写为指引，用户在"AI 建模结果"中可见。

**P2 核查与发布：按表、按差异**
- 口径清单是可核查资产（`AssetReviewStore` 新增种类）：核查页按表展示表说明、口径表格（条件、取值检查结果）、生成的 View/Cube 预览；首次核查全表，之后只核查新增或修改的行。
- 问题验证：平台按口径名自动给出验证题（如"<口径> 最近一个月会员数"），助手只用该 Cube 生成 `query_cube` 参数，平台 `--sql-only` 展开，人判定；不执行。
- 发布门禁：未核查的清单、直接写入工作区的 View/Cube 不发布。重复定义检查：规则或术语中出现"名称 + 具体取值条件"且与清单重复或不在清单中，提示"疑似口径漏进规则"。
- 版本内各表独立：某张表的清单未核查时，是否允许其他表照常发布见"待确认"。

**P3 修改：对话为主，表格编辑为辅，改同一份清单**
- 对话：已有口径清单时，建模对话中的"新增/修改/删除口径""调整使用场景"转入资产轮次修改清单，不写规则；有歧义的说法先追问。
- 编辑：口径页表格增删行、改条件、改使用场景。
- 两者都只改草稿清单，平台重新生成 View/Cube，变化行回到待核查；依赖它的已确认问答按 ADR0130 待复核。

**P4 问数：按场景选表，按口径取数**
- 不做平台路由。问数助手经 `get_instructions` 读每表一行选表规则（由 `scenario` 生成，保持简短），需要细节时 `describe_cube`；口径内问题用 `query_cube`，清单覆盖不到的问题照常 `run_sql`。
- 多表冲突：同一口径名出现在多张表时，按度量区分（人数/收入），同度量时按粒度和规则中的优先说明；仍不唯一时先问用户。
- 跨表问题（如每个口径的人均收入）：分别 `query_cube`，再用 `run_python` 基于返回数据计算，不在 SQL 中跨 Cube 拼接。
- `query_cube` 参数门禁（拒绝不改写）：口径名维度必须筛选单值或分组（不可跨口径相加）；依赖受限事实表时必须带合规 `time_dimension`。
- 已确认问答按表召回；平台为每张表生成推荐问题时优先用其口径。

**P5 多表选表、指标说法与范围维度**（依据 2026-11-24 问数验收：“咪咕视频10月用户数”因指标和对象都未定义而反问；实际业务为多张表，按业务和统计对象分表）

- 背景：问“咪咕视频的会员”查会员规模表，问“咪咕视频的活跃用户”查视频活跃表，问“咪咕音乐的活跃用户”查音乐活跃表。现有选表只靠每表一行自由文字的适用/不适用说明，表多了以后，大模型靠语义猜，容易选错表；“用户数”这种说法在多张表都说得通。
- 表的选表键：`scenario` 新增 `business`（业务/产品，如咪咕视频、咪咕音乐，可多个及其说法）和 `audience`（统计对象，如会员、活跃用户、收入，及其说法，如“会员数、订购用户”“活跃用户、日活、月活”）。两项都由文档第 1 节照抄，人核查。
- 指标说法与默认指标：`measures` 每项新增 `synonyms` 与 `default`（每表至多一个）。用户只说对象不说指标时（“咪咕视频10月会员数”），用默认指标；没有默认指标时先问。
- 选表索引：平台把所有已发布清单的“业务 × 对象 → 指标 Cube、默认指标”生成为 `calibers.md` 的一张索引表，替代现在每表一行的长句；规则写明：先按业务和对象定表，再按口径名取数；业务或对象缺一项且对应多张表时先问（如“咪咕视频10月用户数”同时命中会员表和活跃表，问“会员还是活跃用户”）；问到索引里没有的业务或对象时，说明当前没有这类数据，不改用其他表凑数。
- 冲突检查：两张已核查清单的业务和对象相同（且时间粒度相同），发布时警告并要求在其中一张的 `scenario` 写明优先或区分说明；某张表的业务、对象说法与另一张的口径名或说法相同，同样警告。
- 范围维度：`fixed_scope` 扩展为 `scope`，每项为列、维度名、汇总值、未指定时的默认值，由文档第 4 节照抄并人核查。生成的视图把这些列作为列输出，不再写死在条件里；Cube 增加对应维度，并列入不可相加维度。`query_cube` 门禁扩展：每个范围维度都必须筛选到取值（in/eq）或分组，否则拒绝并提示默认值；筛选取值必须是表中存在的值，否则拒绝并给出相近取值（取值统计范围扩到范围维度列）。选表索引写明各表的默认范围，让第一次调用就带全条件。
- 有清单的表不再自由 `run_sql`：生成规则删掉“清单覆盖不到再用 run_sql”，改为“对不上口径或范围取值时告诉用户并给出最近的选项”；`run_sql` 门禁拒绝直接查询已发布清单的原表（查生成的视图不受限），提示改用对应 Cube。依赖范围维度：先有 `scope`，再加这条门禁，避免分省等问题无处可查。
- 文档模板：[docs/samples/caliber-document-template.md](../samples/caliber-document-template.md)，第 1 节写业务与统计对象，第 2 节写指标说法与默认指标，第 4 节写范围维度。

## 影响面

- 后端：口径清单解析与 View/Cube 生成（新）；`AssetReviewStore`、`SemanticAssetService`、`AssetSqlGenerator`；`MdlPublishService`/`MdlBuildChecks`（清单核查门禁、重复定义、维度自别名、列存在性）；`WrenProjectAccess`（资产轮次可写 `calibers/`，`views/`、`cubes/` 中生成文件只读）；`ModelingTurnRules`；`WrenScopedMcpClient`（`query_cube` 门禁）；`BusinessDocumentService`（文档与表绑定、数量上限）；上传取值统计（`DatasetImportService`）；`MdlQuestionStore`（问答依赖含清单行）。
- 前端：口径页（按表列出、表格编辑、差异核查、取值检查结果）；建模结果"可生成口径清单"卡片；问题验证支持 Cube。
- 数据：不新增数据库表；清单写工程 YAML，取值统计随上传元数据保存（同 ADR0135 日期范围）。
- 文档：ADR0155；ARCHITECTURE 第 14 章；AGENTS 第 5.4、第 6 节；README 文档模板说明；部署指南 Wren 版本。

## 验收标准

1. Given 升级后的 Wren，When 跑 spec118 回归，Then 建模、发布、问数与升级前一致，中文 Cube 可 validate/build/`--sql-only`。
2. Given 验证用例引用不存在的列，When 展开，Then 报错且不能判"符合预期"。
3. Given 会员规模表 + 第二张同主题不同度量的表（如会员收入，测试夹具）及各自文档，When 基础建模完成并点"起草"，Then 每表生成口径清单，条件与文档逐行一致，待确认项有标注，规则中重复的条件被改写为指引。
4. Given 清单中加一行引用库中不存在的取值，When 打开核查页，Then 该行标出取值不存在。
5. Given 两表清单已核查、验证、发布，When 问"10 月篮球通会员数""篮球通月趋势"，Then 选会员规模表、使用 `query_cube`、结果 3,283,751；同题 3 次参数一致。
6. Given 问"10 月篮球通会员收入"，Then 选收入表；问"10 月足球会员数"，Then 先问"足球通还是足球整体"。
7. Given 对话"增加橄榄球会员，条件是六级=橄榄球会员"，Then 修改进入口径清单而非规则，该行标取值不存在并待核查；其余口径无需重新核查。
8. Given `query_cube` 未按口径名筛选或分组，Then 被拒并提示不能跨口径相加。
9. Given 没有口径清单的知识库（演示订单库），When 跑既有问数回归，Then 行为不变。
10. Given 已发布的两表清单，When 重传只改了会员规模表一个口径的文档，Then 只有该行待核查，收入表不受影响；When 该行此前已在对话中被改过，Then 标为冲突由人选择，不被文档覆盖。
11. Given 一份文档声明两张表、另一份声明其中一张，When 两份对同一口径条件不同，Then 起草时列为冲突；When 删除其中一份文档，Then 清单保留，只去掉来源。
12. Given 任一入口产生的改动，When 未经口径页核查与问题验证，Then 不随版本发布；核查页可见每行来源。
13. 多租户：只有 MANAGE 能起草、编辑、核查清单；QUERY 只用已发布 Cube；排队撤权拒绝；看不到他人知识库的清单。
14. Given 会员规模表、视频活跃表、音乐活跃表三份已发布清单，When 问“咪咕视频10月会员数”“咪咕视频10月活跃用户”“咪咕音乐10月活跃用户”，Then 分别选中三张表、用各自默认指标、只调用一次 `query_cube`；When 问“咪咕视频10月用户数”，Then 先问会员还是活跃用户；When 问“咪咕阅读的活跃用户”，Then 说明当前没有该业务的数据。
15. Given 两张清单业务和对象相同，When 发布前校验，Then 给出冲突警告。
16. Given 会员规模表有分省、分渠道数据且 `scope` 已核查，When 问“10月浙江篮球通会员数”，Then `query_cube` 带口径、省份及其余范围维度默认值，结果为单行；When 漏写渠道或省份写成表中不存在的值，Then 被拒并给出默认值或相近取值。
17. Given 有已发布清单的表，When 问数对原表调用 `run_sql`，Then 被拒并提示对应 Cube；查生成的视图不受影响。

## 不做的事

- 不替换基础建模，不让口径清单成为必经路径；不做平台路由或 SQL 改写。
- 不从数据推断口径，只认文档口径表或用户明确要求；不在建模阶段查询表数据。
- 不在 Cube 间做 SQL 拼接；不做预聚合、物化；取值同义词入 MDL 与基准评测仍属 spec118。

## 待确认

- Wren 目标版本：0.18.x（建议，本机已实测）或 0.17.1。
- 某表清单未核查时，其他表能否先发布（建议可以：未核查清单不随版本发布，该表退回基础建模问数）。
- "可生成口径清单"卡片在初次建模结束即出现（建议，仅提议不自动生成；会轻微改变 ADR0131 "初次建模只做基础"的体验）。
- 不可相加校验硬拒绝（建议）或仅提示。
- P5 选表键的取值是否在知识库内统一（如“咪咕视频”在各表写法一致，建议由核查页提示不一致，不另建业务字典）。
- P5 范围维度门禁对“未指定”硬拒绝并提示默认值（建议），或由选表索引写明默认值、仅提示。
- P5 内部顺序：建议 选表键与指标说法 → 选表索引与冲突检查 → 范围维度 → `run_sql` 原表门禁；多表验收需要用户提供活跃用户等第二、三张表和文档。
- 实施顺序：建议 P0 → P1 → P2 → P4 → P3；真实多表验收需要用户提供第二张及以上表和文档。

## 测试要求

- 单元：清单解析与 View/Cube 生成（含"全部/不限"约定、多值候选）、资产轮次写入边界、清单核查与差异核查、重复定义检查、取值存在性、列存在性、文档与表关联及增量比对、行级来源与来源冲突、`query_cube` 两项门禁、维度自别名构建检查；P5 的选表键与索引生成、业务对象冲突、指标默认值、范围维度生成与门禁、取值相近提示、`run_sql` 原表门禁。
- 多租户：看不到他人清单；QUERY 不能编辑或核查；排队撤权拒绝。
- 真实验收：会员规模表加至少一张同主题表按验收 3–8 实测，以重启后日志为准；演示库跑验收 9。合并前按 AGENTS.md 第 8 节完整验证。
