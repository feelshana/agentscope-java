# ADR 0008: 禁「摸底查询」硬门上移 + 回答计数一致性自检

- 状态：已采纳（2026-09-22 实施，见 [spec 002](../specs/002-anti-probe-and-count-consistency.md)）
- 日期：2026-09-22
- 证据：`logs/LLM.log`（会话 `main-cd465cf5`，17:01:27→17:02:08，4 轮 LLM / 7 次工具调用，
  问题「有哪些领导访问了，分别访问了哪些模块，哪些报表？」）；
  `DataAgentToolkit#buildTableSection`（javadoc 明确 no bulky sample values）；
  `shared/agents/data-agent/skills/sql-analysis/SKILL.md` 第 2、3、4 步
- 关系：补充 ADR 0007 的分层准绳（明确「门 vs 手册」的切分方式），不改变其三层分工

## 背景

ADR 0007 落地后重跑同一道题，跨表硬门全部生效：两条 SQL 都是
`WITH leads AS (SELECT DISTINCT account, ... FROM 用户表 WHERE position_name='领导')
SELECT ... JOIN leads l ON c.user_account = l.account GROUP BY ...`，无 `IN (...)`
字面量搬运，`prepare_data_context` 一次批量取回 3 张表，4 轮 7 次调用完成。
但同一份日志暴露三类新错误：

1. **三条纯摸底查询。** 第 2 轮并行发出：
   `SELECT position_name, COUNT(DISTINCT account), COUNT(*) FROM 用户表 GROUP BY position_name`、
   `SELECT MIN(click_time), MAX(click_time), COUNT(*) FROM 点击详情表`、
   `SELECT MIN(visit_time), MAX(visit_time), COUNT(*) FROM 报表访问表`。
   其中职位分布那条完全多余——第 1 轮 prepare 的返回里已经有
   `| position_name | 职位 | VARCHAR(1024) | 用户职位名称，包含领导等值 |`；
   两条 MIN/MAX 的结果只被用来在回答里写「数据范围」说明，最终 SQL 并未据此加时间过滤，
   即三次查询对答案没有任何贡献。
2. **结论计数与自列明细自相矛盾。** 回答写「共 8 位领导」，紧接着的表格列出 9 个账号
   （按明细求并集确为 9 位）；另一处写「MG视频量质构效日报（4 位）」，该段明细只有 3 位。
3. **技能没有被加载。** 全程 0 次 `load_skill_through_path`，所以 `sql-analysis`
   第 3 步「不要发纯『摸底』查询……不要发 `SELECT COUNT(*)` / `SELECT MIN(date)`
   等仅为了了解数据规模、日期范围的探查查询」与第 4 步「先执行校验，再汇报」
   都没有进入上下文。第 1 类错误正是该反模式的原文复现。

顺带查出一处**文档与实现不符**：技能第 2 步说 prepare 返回「列名、类型、描述和维度值样例」，
而 `buildTableSection` 只输出 `| 英文名 | 原始名 | 类型 | 描述 |` 四列，javadoc 亦写明
不含样例值（受 toolResultEviction 4000 字符预算约束；实施 spec 001 时已删掉工具描述里
与实际输出不符的「维度值示例」字样，技能侧漏改）。模型若相信「本该有样例值却没看到」，
反而更有理由去探查取值。

## 决策

1. **明确 ADR 0007 准绳的切分方式：门常驻，手册下沉。**
   同一条规则可以出现在两层，但两层写的不是同一种东西——常驻层写**一句话禁令/义务**
   （模型在做动作的当下必须读到），按需层写**完整手册**（例子、替代做法、校验清单）。
   跨表 JOIN/CTE 硬门已是这个形态（`@Tool` 描述一句门 + 技能第 3 步带 `WITH u AS (...)`
   示例）。漂移源是「同一层级的同一句话抄两遍」，不是「门与手册分工」。
2. **「禁摸底查询」作为硬门写进常驻层 A。**
   - `query_structured_data` 的 `@Tool` 描述追加一句：不要发仅用于了解数据规模、
     日期范围或取值分布的探查查询（`COUNT(*)` / `MIN` / `MAX` / 全表 `GROUP BY` 分布统计）；
     结论本身需要的聚合不在此列。
   - `prepare_data_context` 的 `@Tool` 描述补一句能力陈述：输出的字段描述通常已含枚举与
     取值提示（如「包含领导等值」），据此直接写 `WHERE`，无需再探查取值。
     两处分工是「门」与「门的替代方案」，不重复表述同一条禁令。
3. **「回答计数一致性」作为义务写进常驻层 B。**
   `DEFAULT_AGENT_SYS_PROMPT` 的「# 回答规则」追加一行：结论中的每一个计数都必须与
   自己列出的明细行数一致，不一致时以明细为准重算后再回答。
   放常驻层 B 而非技能，因为它跨所有工具（SQL、Python、检索都可能产出计数），
   且与「不编造数据」同级；按 ADR 0007 准绳，它必须在模型还没选定技能时就成立。
4. **修正技能侧的不实描述并保留完整手册。**
   `sql-analysis` 第 2 步的「维度值样例」改为「字段描述中的取值提示」，与
   `buildTableSection` 的实际输出一致；第 3 步的禁摸底条目保留为完整版（含具体 SQL 例子），
   第 4 步的校验清单不新增计数一致性条目（该义务已由常驻层 B 承载，避免同层重复）。
5. **双向守卫测试。**
   `DataAgentConfigTest` 断言常驻层 A 含禁摸底门、常驻层 B 含计数一致性义务；
   `SharedSkillContentTest` 断言技能不再声称返回样例值、且仍承载禁摸底完整版。

## 理由与权衡

- **为什么不能只靠技能**：本次日志是实测反证——模型没有加载技能，技能里的反模式原文
  一字未进上下文，错误照犯。ADR 0007 已注明这是分层的代价，本 ADR 是该代价的第一次兑现：
  把「违反即错」的门搬到每轮必然下发的 `@Tool` 描述里。
- **为什么不把技能全文常驻**：常驻提示词会从当前约 900 字符（占 system message 6.6%）
  涨到数万字符，且与按需层彻底重复。门的成本低（两句），手册的成本高。
- **为什么计数一致性不用代码校验**：结论是模型自行组织的自然语言，服务端无法从中可靠抽取
  「声称的计数」与「对应明细」的配对关系；`query_structured_data` 已在返回里带上 SQL 与
  结果表，能做的只有要求模型自检。这是提示词门而非代码门的典型场景。
- **为什么服务端不拦截摸底 SQL**：无法与合法聚合区分——「有多少位领导」本身就是一条
  `COUNT(DISTINCT ...)`；用「有没有 `WHERE`」判据会误杀全表统计类正当需求。
- **代价**：`@Tool` 描述再长两句，每轮多占少量 token；门写成「仅为了解…的探查查询」
  这类意图判据，依赖模型自评动机，仍可能被绕过（故保留技能侧的完整手册作为第二道）。

## 被否决的替代方案

- **让 `prepare_data_context` 直接回每列的 DISTINCT top-N 样例值**：输出体积成倍增长，
  批量 3 张表极易撞 4000 字符驱逐阈值（本次 prepare 返回 2043 字符已过半），
  且多数列的取值对当前问题无关。
- **服务端正则拦截 `COUNT(*)` / `MIN` / `MAX` 且无 `WHERE` 的查询**：误杀合法聚合，
  且模型可以加一个恒真 `WHERE` 绕过，属于用代码打补丁掩盖提示词问题。
- **强制加载技能（把 `sql-analysis` 全文注入 system prompt）**：常驻 token 暴涨，
  与 ADR 0007 的按需层设计冲突；等价于取消分层。
- **把计数一致性也写进 `sql-analysis` 第 4 步校验清单**：该清单是 SQL 专用手册，
  而计数一致性对 Python 分析、检索汇总同样适用；写进技能会把跨工具义务窄化，
  且与常驻层 B 形成同层重复。
- **只修技能的「维度值样例」表述、不上移硬门**：技能没被加载，修了也不生效。

## 适用与失效条件

依赖两个当前事实：`@Tool` 描述随每轮请求原样下发；`prepare_data_context` 的字段描述由
AI 生成且通常含取值提示。若某数据源的列描述为空或不含取值信息，禁摸底门会让模型缺少
必要信息，此时应由数据集侧补描述（而不是放宽门）。若 harness 改为裁剪或摘要工具描述，
常驻层 A 失效，需重新评估把门放回何处。计数一致性是自检门，无代码兜底，
其有效性只能通过日志抽查验证。
