# ADR0103：按表来源分层探查、门禁以逐表明细为准与 CLI 契约对齐

## 状态

已接受，2026-10-20。关联 spec089；补充 ADR0098/0099/0102，替代 ADR0102 中“检查模型判定与明细矛盾本次不处理”的部分。

## 背景

2026-10-20 rrr 库日志显示：

- 上传表（`origin=upload`）不在事实表时间配置范围内，建模 SQL 全部 `SKIPPED_NO_LIMIT`。Agent 违反统一的“禁止探查”提示，执行了全表 MIN/MAX 和 COUNT。
- `memory store --source/--tag` 被适配器拒绝。官方 CLI 只有 `--tags`，Agent 随后手改了 frontmatter。
- 技能经原生挂载加载后，又通过 `wren_cli skills get` 重复加载，并多次执行 `--help`，触发上下文压缩。
- `cube list` 在工程锁内才被拒绝。
- `memory index` 默认带种子示例，确认卡把它当成保存问答展示。
- 关系声明为 MANY_TO_ONE，而描述说明对端一键多行。
- 另一个库中，90 天等于上限，检查模型却输出 `allowed=false`，而它的 reason 写明应放行。

## 决策

- **上传表不加时间门禁。** 上传数据量有限，上传表继续不进入事实表时间配置。
- **建模运行上下文按当前库逐表列出来源。**
  - 上传表允许官方技能内的采样或探查，结果只作参考。
  - 外部数据源、手工及未知来源表禁止探查，样例 SQL 继续受逐表门禁约束。
  - 未列出的表按外部表处理。
  - 采用运行时变量而非两套静态提示词；同一知识库可以混合两类表。
- **建模上下文与问数一样，注入服务当前时间、日期和时区。**
- **门禁的 `allowed` 由逐表明细重算。**
  - 明细非空时，全部行有条件、窗口有限且不超过上限，才放行。
  - 模型结论与明细矛盾时，以明细为准并在 reason 中标注。
  - 明细为空时无法核验，维持模型结论。
  - 检查提示词改为先输出明细、最后输出结论。
  - 门禁仍不改写 SQL，也不补条件。
- **CLI 契约对齐。**
  - 示例写回使用 `--tags "source:enrich"`，禁止手改 `knowledge/sql` 的 frontmatter。
  - `memory store` 已自动索引；需要重建时使用 `memory index --no-seed`。
  - 拒绝未知选项时，错误中列出该子命令的可用选项。
  - 技能已挂载时关闭 CLI 的 skills 通道。
  - 基础建模的工具描述不再列出 cube 命令。
- **检查前移。** 参数解析、Cube 拒绝和时间门禁在获取工程锁之前完成。`memory store` 在确认卡之前先过门禁。
- **确认卡按真实子命令展示。** 关系基数必须与两侧粒度一致。同一文件多次 `edit_file` 允许，但 old_string 不得重叠。问数中已写月日、未写年份时，按当年理解，不向用户提问。

## 后果

- 门禁结论更稳定，可审计；但明细本身的计算仍依赖模型，不等于确定性 SQL 解析。
- 上传表探查是有意放开的，不能描述为门禁漏检。
- 技能挂载判断基于定位到的技能目录；运行时挂载异常的罕见情况下，需修复环境后重启。
- 提示词约束仍是软约束；真实 Agent 行为必须通过加载后的日志验收。
