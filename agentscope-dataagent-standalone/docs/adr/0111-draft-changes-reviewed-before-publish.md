# ADR0111：建模修改直接进入草稿，发布前统一审阅，取消逐项确认卡

## 状态

已接受，2026-10-21。

取代：ADR-0031（建模写入的逐项原生 HITL 确认）

同时修改：ADR0069 中"未授权写入保留原生 HITL"、ADR0094 中"业务口径冲突等高影响变更遵循确认流程"两处条款，改为本 ADR 的发布前审阅；两者其余内容不变。

## 背景

2026-10-21 多轮真实验收暴露出逐项确认卡的结构性问题：

- 助手每写一个文件就暂停等待确认。后续请求（文档更新、问题生成 SQL）排在确认卡之后，而确认卡只在对话页可见，用户在"检查与发布"页看到"生成 SQL 中"一直不动。
- 同一次修改被拆成多张卡，用户需要在对话中逐张处理；业务文档、确认卡、问题确认分散在三个地方。
- 对照 Palantir 本体（分支 → 提案 → 审批 → 合并）、Power BI（编辑 → 发布）、Wren（建模 → 部署），主流做法都是修改先进入隔离区，发布或合并前统一审阅差异。

## 决策

1. 建模助手、用户上传的业务文档、用户在对话里补充的口径，所有修改都直接写入当前知识库的草稿工程，中途不再弹出确认卡。线上已发布版本不受影响，问数始终使用已发布版本。
2. 发布前统一审阅：列出草稿与已发布版本的全部差异，按文件撤销单项或放弃全部草稿。发布仍然只能由用户显式触发。
3. 写入安全边界不变：仍由 `WrenProjectAccess` 和写入层校验 MANAGE 权限、单库工程、路径、禁写平台文件、YAML 语法、models 目录文件布局、Cube/View 不读不写、问答对不由建模写入。
4. 推断与确定口径分离，由平台约束而不是提示词约束：没有业务文档、也不是用户直接要求的建模轮次，不得写入业务规则（`knowledge/rules/`），推断只能写入待确认事项（`knowledge/caveats/`）。
5. 平台记录每个文件修改的来源（自动建模、文档更新、用户对话、问题处理）、触发用户和时间，审阅时展示；助手修改了用户在对话中写入的内容时单独提示。
6. 助手运行期间不允许发布；发布期间不接受新的写入（沿用发布锁）。
7. 多人共同管理同一知识库时共用一份草稿，不做分支；审阅时显示每项修改的作者。

## 备选方案

- 保留逐项确认卡，再加全局"待处理"列表：改动小，但仍然会阻塞后续请求，交互也与主流不一致，未采纳。
- 每个用户或每次会话一个草稿分支，合并时解决冲突：最接近 Palantir，但对当前规模过重，未采纳，留待多人协作成为常态时再评估。
- 让助手判断哪些修改需要确认：判断本身不可靠，且仍保留暂停与排队问题，未采纳。

## 后果

- 助手不再因确认而停下，文档更新、问题生成 SQL 不会被确认卡阻塞；用户只需理解"草稿"和"审阅并发布"两个概念。
- 改错的内容要到审阅时才发现。草稿不影响线上，风险可控；但审阅变成唯一把关点，审阅页必须把来源、推断项和对用户内容的改动标清楚。
- 撤销以文件为单位，一个文件内多处不相关修改只能整体撤销；撤销后需要重新编译检查。
- `ModelingHitlMiddleware` 的逐项确认路径、确认卡前端、确认恢复接口退出建模主流程；问数和其它 Agent 的 HITL 不受影响。
