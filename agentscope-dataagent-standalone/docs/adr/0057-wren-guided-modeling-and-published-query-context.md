# ADR 0057：基于 Wren 的业务方案审阅与已发布问数上下文

- 日期：2026-10-08
- 状态：Accepted（用户于 2026-10-08 确认；实现以 specs 047–050 为准）
- 关联：ADR 0029、0040、0048–0056。
- 通过后替代：ADR 0050 的默认对话入口、0055 的聊天登记问题方式、0056 的逐文件审批粒度和 EXAMPLE 仅限一次性查询限制；保留 YAML-first、原生 Harness/ReAct、真实 Wren 验证、人工结果确认和租户隔离。

## 背景与目标

用户目标是由 agent 借助 Wren 建立可复用语义模型，让后续问数尽量准确；用户负责提供业务背景和判断业务结果，不承担 YAML 编辑、函数兼容和技术重试工作。

最新 logs/LLM-modeling.log 中，三个问题产生六次问题文件写入提案、八次 create_view 调用（四次失败后重试）。问题先以空 SQL 登记，后再补全；文档已有口径被重新询问。ModelingHitlMiddleware#onActing 通过 limit(1) 将相关写操作逐个审批。工具调用数不等于日志能证明的点击次数，但这种审批粒度会放大负担。

日志也暴露业务准确性缺口：承诺统一排除人员但 TOP10 视图遗漏过滤；定义固定前十却用 DENSE_RANK 可能返回超过十行；用两个独立 MIN 选择公司与部门可能组合出不存在的归属。资产存在、SQL 引用和执行成功均不能单独证明业务正确。

本 ADR 确定完整交互、审阅边界、资产路由与问数一致性；具体 API、持久化字段和组件拆分在确认后的 specs 定义。

## Wren 最新实践及适配边界

于 2026-10-08 核对官方仓库 main，作为本次设计依据；实施时必须核对本机安装版本及其 CLI 输出，固定兼容版本，不假设 main 的能力均已安装。

- [enrich-context](https://github.com/Canner/WrenAI/blob/main/core/wren/src/wren/skills_content/enrich-context/SKILL.md)：自动补充与访谈两种方式，普通补充可自动处理，冲突及新增公共语义资产需要审阅。
- [Cube 选择与校验](https://github.com/Canner/WrenAI/blob/main/core/wren/src/wren/skills_content/enrich-context/references/cube_proposals.md)：先检查已有资产，聚合考虑 Cube，复杂数据准备考虑 View，并验证表达式可编译。
- [usage](https://github.com/Canner/WrenAI/blob/main/core/wren/src/wren/skills_content/usage/SKILL.md)：读取上下文与规则、召回历史 SQL、选用 Cube 或逻辑 SQL、执行并积累示例。

这是参考官方 CLI agent 工作流后的平台适配，不声称官方网页产品提供本 ADR 的整套向导。平台选择更严格的示例治理：执行成功不自动升级为人工确认示例。官方 enrich-context 的只增不改原则也不扩展成平台禁止用户修正旧模型；修正既有资产必须明确审阅并重验。

## 决策一：一条主流程与五个用户阶段

上传数据/关联数据 → 基础语义模型就绪 → 业务背景 → agent 建模 → 验收与发布 → 问数。

| 阶段 | 用户操作 | 系统/agent 行为 | 完成反馈与主要入口 |
|---|---|---|---|
| 1 数据与基础模型 | 上传文件或关联已有数据表 | 自动建立逻辑模型、字段映射、已有元数据；校验、编译、初次发布 | 显示表/字段数量、成功与失败原因；“继续完善业务语义”及“开始基础问数” |
| 2 业务背景 | 上传业务文档；在表格批量填写常用问题 | 保存原始需求、读取文档、检查重复及已有资产 | 文档上传/解析状态与问题保存状态；“开始建模” |
| 3 agent 建模 | 回答关键歧义，审阅业务方案 | 综合文档和问题、设计共享资产、完成草稿与技术修复 | 当前处理事项、受影响问题、变更摘要；“查看待验收结果” |
| 4 验收与发布 | 审阅口径、SQL 依据、真实结果；确认或退回；发布 | 自动执行 Wren 校验和问题验证，生成发布预检查 | 已确认/待处理数量、阻塞原因；就绪时“发布并开始问数” |
| 5 问数 | 自然语言提问、查看依据、反馈错误 | 使用同一已发布版本的语义资产与知识，经 Wren 查询后分析 | SQL、口径、版本与必要的数据限制；可提交建模改进建议 |

“关联数据”指将数据资产关联到知识库，不自动表示建立表间 JOIN 关系。PK、关联基数不能凭字段名猜测；数据库约束作为证据，无约束的关系作为候选，在业务建模阶段审阅。

基础模型就绪表示在已发布逻辑对象上可以查询，不表示完整业务口径已经验收。已有知识库新增数据不得自动覆盖当前业务版本；新增数据先进入草稿并经兼容性检查、审阅与发布。失败时保留上一份可用版本。

文档可选且入口显著。上传、解析、已用于方案、待修复必须分别展示；上传成功不等于业务规则生效。允许没有问题时按文档建模、没有文档时按问题建模；两者均为空时继续基础问数，不强行生成业务资产。

所有阶段常驻“查看语义模型”入口，在一个面板展示模型、关系、Cube、视图、MDL，区分草稿和已发布版本。

## 决策二：可增加行数的问题表格直接保存需求

默认不展示聊天输入框。业务背景页将文档区和问题表格放在主要区域。

表格列为序号、分析问题（必填）、口径/备注（选填）、参考答案或预期结果（选填）、删除操作；支持增加行、批量粘贴形成多行、修改、删除和一次提交。用户无需填写 SQL、选择 Cube/View 或选择必验级别。忽略纯空白行，逐行显示错误，提交幂等；相同问题提示复用，语义近似问题不能擅自合并。

表单提交属于用户明确保存原始需求，服务端鉴权后直接保存，不经 LLM 再逐项登记和 HITL。原始需求与 agent 生成的口径/SQL/资产声明区分，空 SQL 是待处理需求，不伪装成已完成模型。用户参考答案属于测试预期，不得冒充 Wren 执行结果。

点击“开始建模”后展示对话与进度。以后新增问题仍使用同一表格；对话用于澄清和结果反馈，若对话出现新分析需求，提供“加入问题表格”的明确操作，不建立另一个隐形登记入口。已发布问题始终以编号列表展示。

## 决策三：按业务方案审阅，技术执行在隔离候选工程完成

默认采用自动辅助方式，另保留逐项审阅作为高级选项。按共享口径组织问题，文档明确且无冲突的事实直接引用，不逐条追问；只询问会改变结果的缺失定义、规则适用范围及冲突，每次提供推荐答案与依据。

一次业务方案包含：采用的定义、文档来源与不确定项、规则适用的问题、新增/修改/复用资产、影响范围及已生成的技术变更。用户可接受方案、修改口径或跳过某项；不同问题可共享一个方案。新 Cube、View、关系、指标/计算列及修改既有口径必须审阅。

agent 经 write_file/patch_file/create_view 在租户隔离的候选工程生成具体内容；候选工程不影响当前工作区和 published。平台自动校验候选改动并提供聚合差异。用户通过一次原生 HITL 业务方案审批，将绑定具体文件哈希和工作区基准版本的候选变更原子应用到草稿，不逐个审批底层文件。若原生框架不能直接承载聚合审批，specs 先定义复用框架的适配方式，不另写 ReAct 或绕过权限。

这明确替代当前“每次 agent 写文件都要单独确认”的项目规则；通过 ADR 后在实现阶段同步 AGENTS/架构约束，保留白名单、保护路径和实际写入前校验。无方案授权不得写入正式草稿；模型不能自行给提案标记 ALLOWED，也不能通过自动点击确认获取授权。

低影响的新描述与文档明确规则可在候选工程自动补全，并集中展示审计。不能把业务范围扩大当作描述补全。审批后修复仅允许在已审阅业务定义不变的范围内进行；改变过滤、粒度、公式、关系、资产集合须重新审批。基准工程发生并发变化时旧审批失效。失败不半写入；重试必须有界且展示状态、支持取消和恢复。

## 决策四：问题用于发现语义缺口，资产按复用价值建设

先盘点已有模型、关系、规则、Cube、View 和有效示例，再规划新增资产，不按问题数量创建资产。

- 行级语义和字段表达式：模型描述或计算列。
- 稳定度量、分组、时间维度：在 Wren 版本支持且表达式可用时采用 Cube。
- 多步识别、复杂 JOIN、窗口或 CTE：按能力验证采用 View，必要时在其上建 Cube。
- 已有资产可完整回答、或仅是查询变体：复用资产并形成 SQL 示例，EXAMPLE 不再仅限一次性查询。
- 规则和术语：进入 Wren 工程知识上下文，明确适用对象和来源。

每个问题关联资产与业务依据；“引用了 Cube 的 base_object”不足以证明实际使用 Cube，需保存可重放的 Cube 查询规格及其生成 SQL。结果验收执行实际所选路径。平台知识为 Wren 上下文的补充，不能创建第二套独立语义真相。

避免同一指标多份不一致 SQL。禁止用任意 MIN/MAX 静默解决归属冲突；遇到跨公司/部门账号时必须定义归属规则或提示数据质量问题。视图依赖及 SQL 方言能力以本机 dry-plan 证明，不把一次 table not found 泛化成 Wren 永远不支持视图引用。

## 决策五：验收关注业务结果，发布保留明确门槛

三个层次分别呈现：结构校验、Wren 计划/执行校验、业务口径与结果确认。agent 自动完成前两项；用户审阅第三项，SQL 与视图/Cube 的展开依据可阅读、可放大。

每个已提交且未移除的问题必须生成可执行查询并提供真实结果；支持逐题确认和勾选已审阅问题批量确认，不默认全选、不自动确认。失败、截断、过期凭据不可确认。空结果允许确认，但必须显著展示并说明适用时间范围。

全部当前问题有效确认、方案已应用、工程及资产检查通过、无阻塞冲突才允许发布；不重新引入“必验”分类。用户明确移除的问题不再阻塞。发布一次覆盖 MDL、规则、有效示例与检索索引，失败保留旧版本，成功显示版本及问数入口。零问题允许发布经审阅且工程校验通过的文档建模成果。

增加业务一致性检查与边界用例，重点覆盖过滤传播、日期边界、固定 N 与并列排名、去重粒度、关联放大及 NULL。确定性检查负责可证明的条件，LLM 审查辅助提出风险，不承诺自动证明任意自然语言口径等价。数据可变时比较结果特征与测试预期，不将过去数值作为永久答案。

历史确认问题作为回归样例重新执行。先保守延续全工程变更使确认过期的机制；仅在依赖图可证明完整后优化为影响范围内重验，避免漏掉规则变化。

## 决策六：问数同步改造

WrenToolkit#wrenRecallExamples 当前是按空白/标点切分问题、对示例全文做 contains 匹配、排序取前三；未设相关度门槛，零匹配也可能返回示例。DatasetService#semanticBusinessRulesText 经工作区读取规则，需消除“已发布 MDL + 未发布规则”的版本混用。

新问数流程：固定知识库已发布版本 → 获取同版本规则与相关模型 → 召回确认示例 → 判断资产覆盖 → 优先匹配 Cube，其次 View/模型逻辑 SQL → Wren 编译执行 → 展示结果与依据 → 必要时 Python 分析。

- 模型、规则、示例、索引均绑定同一 ownerId/groupId/publishedVersion；多知识库上下文分别标注，禁止混用同名资产。单次回答内版本不漂移。
- 示例召回优先复用可用的官方 memory recall；若未安装语义后端，采用明确的中文词法召回，提供阈值和无命中行为。两种模式均过滤未确认/未发布示例，展示真实后端类型，不将关键词匹配称为向量召回。
- Cube 覆盖需包括度量、维度、时间粒度和过滤；覆盖不足允许在已发布对象上生成逻辑 SQL，经 Wren 查询，保持 Wren-only。
- 规则适用范围随查询路径落实；相似示例只能提供结构参考，不覆盖业务规则、不复用旧结果。
- 本次不擅自替换 LLM 提供商，也不假设调用 Wren 引擎就等于使用官方 AI 服务的 Text2SQL。平台 agent 负责组织推理，Wren 提供语义、Cube、计划/执行及可用的 memory 能力；如安装版含可用 Text2SQL API，specs 核实后再决定接口适配。
- Python 只分析 Wren 实际返回的数据，明确截断与样本范围；不能借 Python 新建物理直查回退。
- 问数错误反馈可生成关联原问题、SQL、版本和证据的建模改进需求，经用户明确加入后进入下一轮；问数 agent 不直接改已发布模型。
- 查询成功可记录执行历史，但只有人工确认可进入受信示例集合；示例变更通过正常发布，避免学习污染。

## 影响面与实施顺序（确认后细化为 specs）

1. SemanticModelingPage、ModelingQuestionsPanel、ModelingChatPanel：五阶段向导、文档状态、增行表格、单一问题入口、方案审阅及验收列表。
2. 问题需求保存接口、MdlQuestionStore、ModelingWorkflowService：原始需求直接保存、处理状态与生成结果分离、幂等和凭据兼容。
3. ModelingToolkit、ModelingHitlMiddleware、候选工程应用服务：聚合方案、原生 HITL、版本/哈希绑定、原子应用和校验恢复。
4. DocEnhanceService 与建模提示词：文档和问题共用方案，逐条文档采纳入口收敛到同一审阅流程；删除重复口径询问及逐项空 SQL 写入要求。
5. MdlPublishService、MdlWorkspaceReader、DataDynamicContextMiddleware、WrenToolkit：统一 published 上下文、版本索引、召回和 Cube 路由。
6. ARCHITECTURE_zh.md、AGENTS 相关规则及迁移说明：实施时同步，不在 Proposed 阶段把计划描述为已经实现。

新增表格保存 API 仍需 AgentAccessGuard、ownerId/DatasetScope 双层鉴权；阻塞调用走 boundedElastic。不得增加 KG、复活物理 SQL 回退、恢复退役结构化 agent 写工具或重写 Harness 内核。

## 兼容、取舍与验收方向

旧 YAML 和已发布版本保留；不自动批量改写历史资产，不将旧确认标记伪装成新业务方案批准。旧会话待审批工具先按原协议处理或由用户明确取消，再进入新流程，不在迁移时自动批准。新需求未就绪不成为受信示例；恢复页面必须显示真实保存、应用、验证和发布状态。

代价是增加候选工程、方案审阅和版本索引治理；收益是减少用户技术审批，并避免草稿规则泄漏到生产问数。拒绝保留逐文件审批作为默认流程、无审阅自动发布、每题强制建 View/Cube 和仅靠提示词保证业务一致性。

后续 specs 应覆盖：表格直接保存无 HITL；共享方案一次审批与过期拒绝；技术修复不重复询问但业务变更重新审阅；创建失败无半写入；发布版本一致；无关示例不召回；Cube 实际路径验收；多租户不可读写他人数据；对日志中的遗漏过滤/TOP10/归属问题建立回归用例；端到端走完数据接入、背景提交、建模、验收、发布与问数。

本 ADR 已经用户确认。实施分为 specs 047–050：业务背景与问题表格、业务方案审批、验收发布、已发布问数上下文；本次确认不表示这些能力已经实现。
