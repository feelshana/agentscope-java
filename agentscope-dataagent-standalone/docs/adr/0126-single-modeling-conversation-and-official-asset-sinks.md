# ADR0126：建模对话作为唯一说需求的入口，资产按官方去处选型

## 状态

已接受，2026-11-03。实施 [spec109](../specs/109-single-entry-asset-proposals.md)。第 2 条已被 ADR-0127 取代（2026-11-03）：提议只在问数教练中产生，用户明确要求时直接起草。

取代：ADR-0124（第 1 条加工表与查询模板的选型；第 2、3 条不变）。ADR0123 第 1 条（只有页面声明的资产轮次能写 `views/`、`cubes/`）保持不变。

## 背景

- 用户反复问"这个需求在建模对话说，还是在语义资产说"。两个说需求的入口要用户先给需求分类，分错了还会被转走。语义资产页的"交给助手起草"本来就发到同一个建模会话，只是附带了资产轮次标记。
- 对照官方技能原文（Wren 0.15.0 `skills_content`）：
  - 默认过滤写入 `knowledge/rules/` 的 `## Default filters`，不建资产；
  - `cube_proposals.md` 的去处判断为：有名字的指标或聚合 → Cube（首选），单行表达式 → 计算字段，跨模型 JOIN、窗口函数或 CTE → View；
  - 官方技能里没有用 `ref_sql` 补充业务口径的做法；
  - 新建 View、Cube、关系和指标属于影响面大的改动，即使在 Auto-pilot 下也要先起草好内容、再问用户。
- ADR0124 把"按固定规则筛选一张表"做成加工表（`ref_sql`）。2026-11-03 发布的 MDL 暴露了它的限制：
  - 只能写物理表名，不能引用其他模型。"报表类有效访问明细"因此复制了"有效报表访问明细"的整段过滤逻辑，描述里写的依赖与实际读取的表不一致；
  - 多出一列恒为 1 的 `account_matched`；
  - 加工表与"用户列表"之间没有关系。

## 决策

1. **只有一个说需求的入口：建模对话。** 用户用业务语言说需求，由助手判断去处。语义资产页负责资产清单、核查、验证；页面上的输入框只是把需求发到同一个对话的快捷方式。
2. **资产先提议，用户点了才起草。** 助手在普通轮次识别出查询模板或指标需求时，不直接写文件，而是给出一张提议卡：类型、建议名称、要解决的问题、起草要点。用户点"起草"后，页面发起资产轮次，起草时沿用 ADR0123 的写入边界、核查与验证流程。自动建模轮只提议，不起草。
3. **资产按官方去处选型。**
   - 默认过滤（排除、只保留、软删除）只写 `## Default filters` 规则，不建资产；
   - 单行表达式 → 计算字段，仍需确认卡；
   - 跨模型 JOIN、窗口函数、CTE → 查询模板（View），用逻辑模型名；
   - 有名字的指标 → 指标（Cube），在升级 Wren 后开放（spec107 P4）。
4. **加工表（ref_sql）不再作为默认选项。** 已建的继续有效；只有用户明确要求、且 View 无法表达时才起草，并在核查卡写明原因。
5. **资产仍配默认使用规则**（ADR0124 第 2、3 条不变）：查询模板、指标建好后写 `## Canonical tables`，问数不做平台路由。

## 备选方案

- **维持两个入口：** 分类负担仍在用户身上。今天的反复询问说明这一点行不通。
- **一个入口，并允许助手在任意轮次直接写资产：** 违背官方"影响面大的改动先问用户"，也会削弱 ADR0123 的写入边界。
- **保留加工表作为默认过滤的落点：** 与官方不一致，且受 ref_sql 只能写物理名的限制，会重复逻辑、口径漂移。
- **默认过滤一律建 View：** 需要关联其他表才能判断的过滤（如"用户列表里找不到的账号"）在规则里同样写得清楚。是否建 View 取决于用户是否要一张可直接查询的结果，不由过滤本身决定。

## 后果

- 用户不再需要先分类。提议卡多一次点击，但这次点击就是官方要求的人工确认。
- 默认过滤由问数助手每次按规则补条件，正确性取决于规则写得是否清楚。上线前需实测"只写规则"时问数是否稳定地加上过滤。
- View 是否走 DuckDB 函数绑定、MySQL 专有函数能否使用（ADR0042 的旧结论），需要在 Wren 0.15 上复测。
- 已有加工表保留。与新规则重复的，由用户在语义资产页决定是否删除，删除能力在 spec109 中补齐。
