# ADR0123：数据开发通过对话建设语义资产，核查和问题验证后才能发布

## 状态

已接受，2026-11-01。第 5 条中执行验证 SQL 的做法已被 ADR-0127 取代（2026-11-03），改为只核对 SQL。第 2 条已被 ADR-0124 取代（2026-11-02）：按用途选加工表或查询模板，并配官方默认使用规则。第 5 条的验证方式已按 spec107 调整（2026-11-02）：问题由用户输入，助手基于资产生成 SQL，未引用资产的 SQL 不算验证。为 ADR0111 增加高级资产逐项把关的例外，并修正其第 1 条未落地的代码行为。

取代：ADR-0107（Cube/View 不读不写仅限基础建模，资产轮次除外）
取代：ADR-0106（Cube 命令和 Cube 参考的拒绝仅限资产轮次之外）

## 背景

问数上线后，真实问题常需要多表 JOIN、窗口函数和 CASE WHEN 口径。基础建模（ADR0107）不读写 Cube/View，发现的需求只留在建模结束时的说明里；旧结构化 Cube 接口已退役（返回 410）；页面没有维护 View、`ref_sql`、Cube 的入口。用户的路线是先基础上线、后渐进深化，第二阶段目前没有落点。

调研（`reports/Wren 语义层渐进建模路线.md`）得出的约束：

- 业界主流是 Agent 起草、人工确认、用问题和 SQL 验证后发布。开源 Wren 有文件、校验和技能，但没有这条闭环。
- 官方决策树：同模型聚合走 Cube，行级表达式走计算字段，跨模型 JOIN、窗口、CTE 走 View。官方技能不覆盖 `ref_sql`，也反对为口径未定的指标建 Cube。
- 0.15.0 本地实测：View 不能引用 View；`ref_sql` 逻辑名和裸物理名都是 `dry_plan` 通过、执行失败，全限定名才成功。ADR0069 禁止重写官方产物，平台不再物化 `ref_sql`。

现有实现还有两处直接阻碍：

- ADR0111 写明问数始终使用已发布版本，但 `DatasetService#markMdlDirty` 同时处理数据变更和草稿修改，`WrenQueryAccess#resolve` 会因 `isModelingPending` 拒绝问数。线上知识库一改草稿，问数就停。
- 时间门禁按已登记事实表名匹配 SQL，未登记名称与 `query_cube` 不覆盖（ADR0112）。查询 View、`ref_sql` 模型或 Cube 时，事实表名不出现在 SQL 里，等于绕过门禁。

## 决策

1. **新增由页面显式声明的资产建模轮次。** 只有 `ModelingTurnPurpose` 为资产建模时才开放 `views/`、`cubes/` 的读写和 Cube 参考文档，并要求 MANAGE。自动建模、文档更新、普通对话和试问的边界不变，基础建模仍不读写 Cube/View。
2. **资产类型按最低可行层选择。** 行级口径和一对多聚合用计算字段；跨模型 JOIN、窗口和 CTE 用 View；口径已确认的高频指标用 Cube；只有 View 表达不了或用户明确要求时才用 `ref_sql`，且必须写物理全限定名并说明原因。Agent 不从单道问题直接建 Cube。
3. **Agent 起草，人负责把关。** Agent 不查询外部表数据，口径没有依据时只能提问。核查和验证结论只能由用户通过接口写入，Agent 不能改写，也看不到存放这些记录的 `.platform/`。
4. **高级资产是 ADR0111 的例外。** 新增或修改的 View、Cube、`ref_sql` 模型必须逐项核查和验证才能发布；其他草稿仍发布前统一审阅。结论绑定资产内容哈希，内容一变就失效。删除资产不需要验证，但要受影响问题的提示。
5. **用问题验证，分两层。** 验证资产：直接执行问题 SQL，比较线上版与草稿，由用户判定，不用 LLM。验证问答：让助手基于草稿重新生成 SQL 后执行，用于确认 LLM 能用上新资产。发布门槛只要求第一层。
6. **草稿修改不再拦截问数。** 拆分标记：数据集或表结构变化继续要求重新发布；只改语义草稿时问数继续使用已发布快照，发布后才切换。这是把代码拉回 ADR0111 的决策，不是新规则。
7. **时间门禁覆盖资产。** 发布时计算资产依赖的受限事实表，并记录用户在核查时确认的时间列；门禁把资产名视为派生规则，窗口取依赖表中最小值，实时读取平台配置。依赖受限事实表却没有时间列的资产不能发布。这些记录是平台数据，不写入 MDL。`query_cube` 按 `time_dimension` 校验。
8. **分期开放。** 顺序为前置修复、View、`ref_sql`、Cube。Cube 需要先把 Wren 升到 0.16 以上，它修复了 Cube 元数据的 UTF-8 读取。

## 备选方案

- **只提供手工编辑器，不用对话：** 改动最小，但无法帮助数据开发把业务需求和已有 SQL 转成资产，手工编辑保留为同一流程的一个入口。
- **基础建模直接放开 Cube/View：** 会回到 ADR0085/0107 要避免的流程变长、上下文膨胀和未确认资产的问题。
- **让 Agent 按用户问题自动建资产并上线：** 业界没有默认这样做的产品，历史 SQL 算错时还会把错误口径固化，因此只做“系统提议、人工批准”。
- **模仿 yolo-data 自建查询构建器：** 放弃 Wren 的语义能力，且不支持多表，不符合 Wren-only 路线。
- **每个用户一个草稿分支：** ADR0111 已判定当前规模过重，继续共用一份草稿。
- **门禁改查 `dry_plan` 展开后的 SQL：** 能看到物理表，但 CTE 会大量落到 LLM 判断，成本高且不稳定，因此用发布期的确定性依赖。

## 后果

- 基础建模保持简单，第二阶段有了明确入口；代价是多一个轮次、一组资产状态和验证界面。
- 高级资产发布变慢，这是有意为之。逐项把关只用于能静默算错的资产，不扩大到描述和规则。
- 官方技能的 Auto-pilot 在此轮不适用：新 View、Cube 属于官方定义的高影响提案，统一走平台核查。
- `ref_sql` 指引由平台提示词承担，官方升级时要复核；Wren 版本行为变化可能使本 ADR 的实测结论失效。
- 门禁只保证查询带时间条件，不保证条件能下推到 View 内部。内层先聚合的资产仍可能全表扫描，要靠数据库物化和核查控制。
- 基础模型仍对 LLM 可见，模型可能绕过资产自己 JOIN，目前只能靠描述、规则和问答对引导。
- 基准集、线上问题回流、自动提炼资产不在本 ADR 内，留待后续 spec。
