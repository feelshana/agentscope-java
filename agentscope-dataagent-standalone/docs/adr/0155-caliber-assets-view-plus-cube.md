# ADR0155：文档口径以 View + Cube 作为可核查口径资产，问数优先 query_cube

## 状态

已接受，2026-11-24（用户按建议确认待确认项）。实施 [spec149](../specs/149-caliber-views-and-cubes.md)，P0 实施中。

取代（随 P1 实施生效）：ADR-0107 中资产轮次 `cubes/` 不读不写的部分（基础建模轮次不变）；ADR-0138 第 2 条（指标 Cube）由本 ADR 收窄实施，ADR-0138 其余各条仍为提议。

## 背景

- 2026-11-24 会员规模宽表对比验收（[报告](../test-reports/20261124-wren-dialog-vs-cube-view.md)）：只靠模型、术语、规则时，LLM 每题现场拼六级取数条件，多次自纠；同输入两次建模写出不同口径规则，其中一次匹配不到行。View 固化文档口径、Cube 提供度量后，LLM 只选参数，结果一次正确。
- 现状缺口：问数已开放 `query_cube`，但 Cube 发布只做 `--sql-only` 试跑、不经人工核查；`query_cube` 无时间门禁，也不防止有包含关系的口径被相加；问题验证会放过引用不存在列的 SQL。
- 平台固定的 Wren 0.15 读取中文 Cube 元数据有问题，需升级。

## 决策

1. 口径资产是可选层：文档中已列明的口径（名称 + 固定条件 + 度量）以 View 固化条件、以 Cube 暴露度量和维度；基础建模不变，未建口径资产的知识库行为不变。
2. Cube 纳入 ADR0128 的人工核查与问题验证；Cube 与其 base View 同组核查，未核查的 Cube 不发布；验证只展开不执行，展开失败的用例不可判为符合预期。
3. 只在资产轮次读写 `cubes/`；起草来源仅限业务文档口径表或用户明确要求，条件照抄文档，文档未说明处标"待业务确认"，不由模型补全。
4. 问数不做平台路由：通过官方默认使用规则提示口径内问题优先 `query_cube`；平台只对 `query_cube` 参数做拒绝式校验（不可相加维度须筛选或分组、受限事实表须带合规时间维度），不改写查询。
5. 先升级 Wren 并完成回归，再开放上述能力。

## 备选方案

- **维持现状（只用规则文字）**：零改动，但口径由 LLM 每次推导，验收中不稳定。
- **引入独立本体/语义引擎（自建或 Cube.dev 等）**：确定性最强，但推翻 Wren-only 主线、双份元数据，成本过高；Wren Cube 已提供同类能力。
- **平台按关键词把问题路由到 Cube**：更确定，但违背"问数不做平台路由"（ADR0129/0131），且歧义问题会被静默选错口径。
- **自动从数据推断口径**：省人工，但口径定义来自业务，不应由模型从数据猜。

## 后果

- 口径稳定、调用次数少；代价是数据开发多一类资产要核查维护，口径变更须同步 View。
- Cube 的聚合对有包含关系的口径无意义，依赖"不可相加维度"门禁；未声明时仍有误加风险。
- 升级 Wren 涉及本地与 66 环境回归；0.18 已知 LIMIT 叠加与维度自别名问题需在升级中处理。
- 歧义说法（如"足球会员"）靠规则提示先问，模型仍可能不问，需真实验收确认。

## 补充（2026-11-24，同日按多表需求调整，仍为提议）

用户将把很多张预统计表放入同一知识库，每表有口径表与使用场景。在上述决策基础上：

6. 每张表的口径表与使用场景以平台约定的口径清单（`calibers/<模型>.yml`）为唯一事实源，View、Cube、选表规则行和模型描述由平台从清单生成，生成文件不手工编辑；具体口径条件不得同时写在规则或术语中，规则只写原则与指引，术语只写说法到口径名的映射。
7. 修改以对话为主、表格编辑为辅，两者只改同一份草稿清单；核查按表、按变化行进行。
8. 问数按使用场景选表仍由问数助手根据规则自行完成，平台不路由；同名口径跨表时按度量、粒度区分，仍不唯一则先问；跨表计算基于各 `query_cube` 返回数据完成，不跨 Cube 拼接 SQL。

补充备选：直接手写每口径一段的 View（初稿做法）——多表时维护量大、易漏改，且无法按行核查，不再采用；Wren 无原生命名过滤（segments），因此以清单生成 View 模拟，代价是平台多一层生成逻辑。

## 补充（2026-11-24，P0 实施）

9. Wren 固定版本升到 0.18.0（wren-core-py 0.8.2）；ADR0072 的 LIMIT 兼容补丁适用版本扩展到 0.18.0，升级到上游修复版本后再移除。
10. 0.18 的 dry-plan 不解析列名，资产与问答的验证在展开后追加官方 dry-run（EXPLAIN），由数据库解析列名、不读取数据；这补充 ADR0132"只展开不执行"的边界。发布时已确认问答同样追加 EXPLAIN，连接不可用只告警，不撤销确认。
11. 构建检查拒绝成员名与其表达式引用列同名的 Cube 成员（0.18 下度量报循环依赖、维度筛选时规划失败）。

## 补充（2026-11-24，P5 多表选表与范围维度）

12. 每张表在清单中声明选表键：业务（产品）与统计对象，各带常见说法；平台把所有已发布清单汇总为 `calibers.md` 中的选表索引（业务 × 统计对象 → 指标、默认指标、默认范围、口径），问数先按业务和统计对象选表、再按口径名取数，仍由问数助手完成，平台不路由。两张清单业务、对象和粒度都相同，或选表说法与其他表的口径名相同时，发布前警告。
13. 度量可写常见说法和一个默认指标；用户只说统计对象时用默认指标，没有默认指标时先问。
14. 汇总值与明细值并存的列（省份、渠道、支付）作为范围维度保留在生成的视图和 Cube 中，不再写死为固定范围；`query_cube` 必须对每个范围维度指定取值或分组，清单列出取值时只允许这些取值，否则拒绝并给出默认值或相近取值，不改写参数。
15. 有已发布清单的表只经其 Cube 取数：`run_sql` 直接引用该表时拒绝并提示对应指标；查询生成的视图和其他表不受影响。这收窄了"清单覆盖不到再用 run_sql"的做法，前提是范围维度已能覆盖分省、分渠道等问题。
16. 表说明的核查哈希对未使用 P5 字段的清单保持不变，已核查的清单无需重新核查。
