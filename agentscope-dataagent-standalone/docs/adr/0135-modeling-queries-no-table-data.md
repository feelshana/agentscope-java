# ADR0135：建模不查询任何表的数据，上传表的日期范围在上传时统计

## 状态

已接受，2026-11-04。

取代：ADR-0103（"上传表允许官方技能内的采样或探查"）；ADR-0104（第 1 条上传表两类探查、第 2 条上传表全表验证唯一后可声明 MANY_TO_ONE）

## 背景

2026-11-04 新手任务实测（上传的演示订单 48000 行、客户 2000 行），自动建模共 75 秒，其中查询 32 秒：
- 一条关系核对查询用 `NOT IN (SELECT …)` 计算匹配率，经 Wren 展开后 MySQL 无法用索引，单条 27.4 秒；同样的核对改用 `LEFT JOIN` 只要 1.4 秒。
- 另外两条超出 ADR0104 允许的范围：维度表的时间极值、订单表的去重数与空值统计。提示词只限定用途，工具层只限条数，助手仍会"随意发挥"。
- 所需事实大多平台已有或能直接得到：总行数上传时已记录；时间列起止日期平台本来就能直连数据集库查询（推荐问题已在使用）。
- 用户决定：客户编号全表是否唯一、订单能否都匹配客户，不需要探测。

## 决策

1. 建模助手在任何轮次都不执行 `query`，上传表与外部数据源表相同，由 `OfficialWrenToolkit` 直接拒绝；试问、资产轮次照旧只用 `dry-plan`。
2. 上传表的时间列（DATE、DATETIME、TIMESTAMP）在上传时由平台直连数据集库统计一次起止日期，写入该列的字段描述，不经过 Wren。
3. 上传表的总行数（上传时已记录）列在建模运行上下文的表来源中。
4. 候选关系不再核对全表唯一性和匹配率：上传表与外部数据源表一样，按字段命名得出候选，用确认卡请用户确定；采样不能证明唯一性的约定不变。

## 备选方案

- **只拦截 `NOT IN` 写法：** 能省 27 秒，但其余越界探查仍会发生，规则继续靠提示词约束。
- **平台代算唯一性和匹配率写入上下文：** 用户确认不需要这项信息，关系由用户确认即可。

## 后果

- 自动建模省去全部查询及围绕查询的模型调用，新手任务的建模时间预计明显缩短，以重启后的日志验收为准。
- 上传表的关系不再能凭"全表核对"直接写成多对一，需要用户确认；关系确认卡的数量可能略有增加。
- 字段描述中的起止日期是上传时的快照，重新上传会重新统计；采样刷新不更新该值。
