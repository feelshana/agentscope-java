# ADR0127：问数教练——用常用问题驱动语义建设，提议只在这里产生

## 状态

已接受，2026-11-03。实施 [spec110](../specs/110-query-coach.md)（一期）。第 1、4 条中"问数教练可提议查询模板"已被 ADR-0128 取代（2026-11-03）：问数优化不提议查询模板，公共视图改从全部已确认问答中提炼。用户确认：发布前保留对查询模板的 `EXPLAIN` 检查；依赖受限事实表、含窗口函数或聚合的查询模板，核查时提示风险后允许发布。

取代：ADR-0126（第 2 条普通建模轮次识别出需求就提议资产）
取代：ADR-0123（第 5 条中"验证资产时直接执行问题 SQL、比较线上与草稿"）

## 背景

- spec109 让助手在普通建模轮次识别出复杂需求时主动提议查询模板。讨论中用户提出：提议应当来自数据开发明确列出的常用问题，其他环节不应主动提议；初次建模必须只做基础。
- 2026-11-03 的讨论与实测结论：
  - 日常语义建设的主体是规则（口径、默认过滤、术语定义）。关联靠关系，大模型能写出正确的 JOIN（实测"各公司访问次数"未声明关系也写对了）；
  - 计算字段只用于反复使用的单行业务分类；
  - 查询模板只用于聚合、窗口函数、多步计算，或用户明确要求的固定数据集；
  - "留存/流失"这类依赖统计日期的分类应写成术语规则加问答示例，不建视图。
- 业界主流产品都把这一环节定位为"数据团队用常用问题教 AI、检验 AI"：ThoughtSpot Coach Spotter（业务术语、参考问题，人批准对话中提出的映射）、Power BI Prep data for AI（AI 说明、已验证答案）、Databricks Genie（Instructions、SQL 示例、Benchmarks）、Snowflake Verified Query Repository。
- 用户要求验证只确认 SQL，不执行；视图自身的 SQL 不执行，时间条件由问数最终 SQL 决定并经时间门禁检查。资产验证当前会在草稿副本上执行 SQL，与此不符。

## 决策

1. **新增独立入口"问数教练"。** 数据开发列出业务常问的问题；助手逐题分析现有模型、关系、规则能否答对，给出一张方案表（每题：能否答对、缺什么、提议什么），提议类型为规则、关系、计算字段、查询模板；数据开发逐项批准后，助手起草；随后用这些问题生成 SQL，由数据开发核对确认，存为问答。
2. **提议只在问数教练中产生。**
   - 初次建模（自动建模、处理文档）只做基础：模型、字段描述、关系、文档写明的规则，不提议资产；
   - 建模对话不主动提议；用户明确要求"建视图/查询模板"时直接起草（资产轮次，ADR0123 第 1 条边界不变）。
3. **验证只核对 SQL，不执行。** 问数教练与语义资产页的问题验证，都由助手生成 SQL、平台用官方 `dry-plan` 展开，页面并排展示逻辑 SQL 和展开后的 SQL，由人确认；时间门禁只检查 SQL 文本。资产起草时的自检也只用 `dry-plan`。
4. **选型原则。** 关联靠关系，口径靠规则，计算字段只用于反复使用的单行分类，查询模板只用于聚合、窗口、多步计算或用户明确要求的数据集；依赖统计日期的分类写成术语规则加问答示例。
5. **常用问题成为基准问题集。** 问数教练中的问题保留为知识库的基准问题；口径变更后可一键重新生成 SQL 对照（与 ADR0125 待复核配合）。

## 备选方案

- **维持 spec109（普通轮次主动提议）：** 提议时机不可预期，用户不清楚需求从哪来。
- **把讨论并入试问面板：** 试问面向单题核对，问数教练面向成批问题的缺口分析和方案批准，职责不同，且用户要求单独入口。
- **验证继续执行 SQL：** 能发现"SQL 对、数据错"，但违背用户要求；视图无时间条件时还可能扫描大表。改为展示展开后 SQL、在核查卡写明 JOIN 基数与未匹配处理来弥补。
- **为带出关联属性优先建衍生字段：** 与官方"用关系写 JOIN"重复，风险并未减少。

## 后果

- 初次建模更快、更稳定，资产全部来自数据开发列出的问题。
- 看不到执行结果，"SQL 看着对、数据不对"的问题需要靠展开后的 SQL、关系基数与规则来防范。
- 现有的 spec109 提议卡、`propose_semantic_asset` 改为只在问数教练轮次可用；建模对话中的提议卡退出。
- 发布前对查询模板的 `EXPLAIN`、依赖受限事实表的窗口/聚合视图如何约束，按 spec110 中用户的确认执行。
