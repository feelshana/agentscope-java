# ADR0124：语义资产按用途选型，并配官方默认使用规则

## 状态

已接受，2026-11-02。实施 spec107（P1 调整）。第 1 条已被 ADR-0126 取代（2026-11-03）：默认过滤只写规则，加工表不再作为默认选项，资产先提议后起草。

取代：ADR-0123（第 2 条资产选型；其余决策不变）

## 背景

ADR0123 第 2 条规定跨模型 JOIN 优先用 View，只有 View 表达不了时才用 ref_sql。真实问数验收发现：
- 问数助手按名称和规则选择模型。View 即使连同完整说明放进上下文（`wren://mdl`），助手仍然自己写 JOIN，多轮测试从未使用 View。
- ref_sql 模型在助手看来是一张普通表，问题里说出"排除测试账号"时会用上；但问题不提时，助手仍查原表，得到"SQL 正确、数据错误"的结果。
- 官方 enrich-context 对这类问题的写回路由是 `knowledge/rules/`：默认过滤写在 `## Default filters`，存在相似表时用 `## Canonical tables` 写明该用哪张；原文指出缺少这条规则时，助手会按名称相近随意选表。
- 补上这两类规则后，同一套问题在资产对话中全部生效：不提过滤时默认用资产，明确要求包含被排除数据时改用原模型，View 也被问数助手直接查询。

## 决策

1. **按用途选型，由助手判断，用户不说技术名词。**
   - 把一张表按固定规则筛选、排除或去重后长期代替原表统计，用 ref_sql 模型，页面和回复称为"加工表"。
   - 把多个模型固定拼接，或用窗口函数、CTE 算出可以直接查询的结果，用 View，称为"查询模板"。
   - 单行计算仍用计算字段，不建资产。
2. **每个资产配一条官方默认使用规则。** 资产轮次建好加工表或查询模板后，按 enrich-context 的写回路由，在 `knowledge/rules/` 的 `## Default filters` 或 `## Canonical tables` 下追加规则，写明哪些统计默认使用该资产、什么情况改用原模型。是否默认使用不明确时向用户提问；不修改已有规则。规则和资产在同一份草稿里，随资产一起发布。
3. **问数侧不加平台路由。** 问数助手通过官方 `get_instructions` 读取规则后自行选表；平台不改写 SQL，也不强制替换模型，与 Wren-only 路线一致。

## 备选方案

- **维持"优先 View"：** 实测问数助手不用 View，资产建了也是白建。
- **平台在问数时把原模型替换为资产：** 等于自建路由，违反 Wren-only，也无法处理"包含测试账号"这类例外。
- **只写规则、不建资产：** 官方对简单默认过滤就是这样做的，仍然可行；但过滤逻辑复杂时，每次查询都要助手重写，口径无法由人一次核查固定。
- **把资产说明写得更详细，期望助手自己发现：** 已在 View 上验证无效。

## 后果

- 用户用业务语言提需求即可，页面给出示例；资产页只显示"加工表 / 查询模板"。
- 资产的使用取决于规则。规则与资产必须一起维护：删除或改名资产后，要同步修改对应规则，否则问数会查不存在的模型。平台目前不能从页面删除加工表，这一缺口单独处理。
- 加工表仍须使用物理全限定名，不能引用其他模型的计算字段（需在 SQL 里重写表达式）；查询模板可以建在加工表上，沿用其默认过滤。
- 助手在正文里自行加总 SQL 结果的问题与本决策无关，仍需另行处理。
