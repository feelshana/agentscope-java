# ADR0144：渐进约束包依赖，按职责消减历史耦合

## 状态

已接受，2026-11-12。

取代：无。

## 背景

当前四根包均有双向引用，web还承载JPA、身份、会话、沙箱等共享能力。直接声称业务层不得依赖整个web包会与实际装配冲突；全面迁包又会扩大权限、事务及文件回归面。测试基础治理完成后，先约束依赖增长，再逐次抽取职责。

## 决策

- 保留四根包和单应用部署，不为本轮增加微服务、Maven子模块或通用空接口。
- 使用生产字节码依赖门禁：业务/运行/工具层不依赖HTTP控制器或web装配；JPA实体与仓库保持为被使用的持久化叶节点。
- web.persistence.jpa暂按现有持久化适配归属使用；其他下层→web耦合以精确外层类对和原因记录技术债，不将包整体设为豁免。新增依赖需消除或明确评审，消除后的例外同步删除，测试不自动放宽基线。
- 通用Agent计时归runtime.observability，上下文关联键归runtime.context；web可使用这些能力，runtime计时不反向依赖事件总线。日志与协议键值保持兼容。
- 每次职责抽取先列实际入口、授权、事务、文件与恢复边界，保留行为回归；静态门禁和单次绿灯不替代实际故障恢复与服务验收。

## 备选方案

- 立即按教科书分层批量迁包：当前共享类型与Spring装配交织，变更风险和审查成本过高。
- 只补文档：无法在后续开发中自动阻止边界退化。
- 依赖全量冻结或数量阈值：容易限制合法调用，数量抵消也会掩盖新增违规；选择局部硬约束与可审查类对债务。

## 后果

ArchUnit仅进入测试依赖，生产无新库。现有双向依赖仍存在；类对基线不限制同一既有类对内的方法调用数量，不覆盖反射字符串、Spring运行装配、资源锁/事务或跨进程一致性。下一轮依据调用清单选择单个职责抽取，不把当前包名视作永久理想结构。
