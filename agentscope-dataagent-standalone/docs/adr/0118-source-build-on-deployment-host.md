# ADR0118：GitHub源码交付与服务器容器化构建

## 状态

已接受（选型），2026-10-29；实现及66验收待完成。

取代：无。补充ADR0117的源码构建交付选项，保留既有tar挂载方式作为备选，不改变Java/Wren同容器与兄弟分析沙箱边界。

## 背景

用户不接受额外持续镜像托管费用，文件上传渠道也不稳定。用户和同事选择将源码推送GitHub，由66拉取并构建应用镜像。现有runtime.Dockerfile只生成运行环境，不能直接当完整源码构建入口。

## 决策

构建工具在容器内运行，基于完整依赖模块和明确提交生成应用镜像；66宿主不安装或升级全局Java/Maven/Node。保留已验收运行环境、分析镜像和离线模型缓存。生产配置、状态和用户数据独立持久化；构建与运行分离，失败不更换旧服务。

先验证GitHub读取及依赖源访问，再实现和验证构建、镜像入口及启停方式。远程不可达或缺数据库时不猜测配置、不自动启动业务。提交/推送需要明确执行授权，选择该流程不等于已把工作区上传。

## 备选方案

- 本地镜像推送私有镜像仓库：成品交付方便，但当前没有合适的长期仓库资源。
- 本地导出镜像文件上传：可行备选，但用户最新选择源码交付。
- 66宿主原生编译：构建依赖与旧系统兼容维护成本较高，采用容器隔离构建工具。

## 后果

66承担构建资源和依赖下载；需要资源限制、项目缓存、明确版本和保留旧镜像。GitHub访问、空缓存构建与旧内核仍待现场验证。镜像交付改变不会解决已发现的问数并发阻塞。
