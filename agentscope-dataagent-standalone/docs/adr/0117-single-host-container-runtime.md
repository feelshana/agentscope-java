# ADR0117：旧系统主机使用独立应用运行容器

## 状态

已接受，2026-10-28。用户明确授权按建议完成环境部署。

取代：无；补充单机部署选项，原生bin启动仍保留。

## 背景

生产66为Anolis7.9、glibc2.17、内核3.10，现有多套业务运行；不能升级宿主库或重启Docker。当前Wren依赖组合含较新glibc预编译包。用户已实测bookworm容器内Python、Wren原生依赖和默认模型断网向量计算成功。

## 决策

Java17、Python与Wren在一个应用容器内；Java继续直接调用官方CLI/MCP，兼容文件和环境传递保持当前实现。分析沙箱是同一宿主Docker daemon下的独立兄弟容器，复用框架管理；应用镜像仅带客户端，不运行嵌套Docker。

用户本人构建上传业务tar。JAR、私有配置、日志、状态、工作区、MDL和附件保留在宿主专属目录，容器挂载使用；模型缓存单独持久挂载。宿主与应用保持项目绝对路径相同，避免宿主daemon无法解析应用容器内部路径。运行环境镜像不包含私有配置、生产账号、业务数据或业务JAR。

容器使用操作者UID/GID和socket所属附加组，启动前台Java以接收停止信号。挂载Docker socket意味着应用可管理宿主Docker，属于现有沙箱管理能力的部署延伸，并不把容器描述为宿主权限隔离边界。只对带本项目及路径标签的应用容器执行停止/替换；不清理业务目录或其他容器。生产入口端口、环境变量和配额在部署时明确并验收。

## 备选方案

- 全部宿主原生安装：当前预编译依赖不适配，源码构建/隔离库维护成本高。
- Java宿主、Wren容器：需额外适配stdio、临时文件、环境、取消和进程生命周期。
- 新系统VM/主机：可行，但不属于当前已提供66环境的直接实施路径。

## 后果

保留原业务流程和用户tar交付方式，增加运行镜像及容器维护；Docker socket授权、绝对路径挂载、磁盘备份、重启恢复和旧内核兼容必须实际验证。Python或向量检查成功不等于完整应用/BI/数据库/并发上线验收通过。
