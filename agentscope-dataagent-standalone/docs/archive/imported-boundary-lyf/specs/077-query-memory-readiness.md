日期：2026-10-19；状态：根因分析与真实链路复现完成，以下修复方案尚未实施或部署。

2026-10-20安排：用户明确由同事处理本项，我方停止实施；保留本页供交接及后续验收参考，不将其列为已接受ADR或当前分支已有性能修复。spec076的既有计时实现单独保留。

## 目标

验收对象为用户从发问、看到“召回示例”运行，到获得完整业务答案的真实时间；以真实SSE/浏览器与服务端阶段记录核对。单个向量读写微基准不代表用户体验达标。

## 本轮复现

专用普通账号、同一六表知识库，将一个已有建模示例问题加上诊断标记，SQL不变；经真实SQL示例编辑API与显式发布，测试库v8→v9。原用户知识库、角色和数据源不动。未替换云JAR或重启应用。

| 同一问题，不同新会话 | 召回工具从tool_call到tool_result | 实际COUNT工具 | 整轮到done |
|---|---:|---:|---:|
| 发布后第一问 | 20.557秒 | 0.112秒 | 25.522秒 |
| 紧接着再问 | 0.046秒 | 0.059秒 | 5.498秒 |

两轮均实际查询得162862。第一轮仅一个召回调用便占20秒，说明真实后台工作已足以造成问题，不依赖多工具显示效应。发布API仅1.380秒，它的“已发布”尚不包含检索就绪。

## 当前完整链路与主因

1. `ChatController#stream`进行问答容量准入、会话恢复与授权，LLM产生工具调用；`ToolNotificationMiddleware#onActing`在工具执行批次开始发布tool_call，前端显示运行。
2. `WrenMcpToolkit#callTool`先做每库工具发现/许可校验；`WrenInstanceRegistry#acquire`必要时启动当前库的常驻只读MCP。发现工具并不会加载其向量模型。
3. 对recall_queries和get_context，平台都同步执行`WrenPublishedProject#indexed`：同库锁→准备工程/合并点赞示例→MDL及全部knowledge指纹→如变化，启动CLI运行官方memory index→再启动一个CLI运行memory status。
4. 官方memory index重新向量化整个schema，再同步示例；`--no-seed`只禁生成种子问题，不等于跳过schema。recall_queries本身只查query_history，本不需要在每次示例变化时重算全部schema。
5. index的Python进程加载过向量模型后结束。真正的官方MCP recall_queries再新建MemoryStore，通过get_index→LanceDBIndex→MemoryStore#recall_queries执行搜索；该MCP进程第一次搜索仍需导入LanceDB并加载自己的ONNX模型。磁盘模型文件共享不等于进程内模型对象共享。
6. 同一MCP后续调用可复用官方embeddings模块的进程内ONNX缓存，因此本轮第二次仅0.046秒。问答已使用常驻MCP，不能把CLI每次冷启动的成本笼统归到“每次问答召回新启动进程”。
7. 真实结果返回Agent后，还需LLM继续选择SQL工具、实际查询、组织最终答案。初始模型等待与这些后续轮次也计入用户整轮时间，不应混入纯召回CPU时间。

### 发布和更新生命周期的缺口

`MdlPublishService#doPublishLocked`检查/编译/替换快照并标PUBLISHED，控制器随即invalidate旧MCP，未准备向量索引及新实例的首次检索。第一位问数用户因此承担检索准备成本。

`AnswerQueryMemory#feedback`在同库锁内保存示例并调用indexed。单条示例变化也会触发整个schema重算；其他请求的indexed会等待同一把锁。因此问题不仅存在于第一次访问，同库其他人点赞/保存也可能影响问答。此排队风险由源码确认，本轮未将它冒充已完成10人实测。

### 另一个显示放大因素

`ToolExecutor#executeAll`返回collectList；`ReActAgent`在整批结果返回后依次发ToolResultEndEvent；业务通知层收到end才给页面tool_result。所以同批快工具也可能显示一直运行。它扩大了显示时长，但无法解释单独召回20.557秒的全部真实耗时；应与后台性能一起修，不以提前显示完成掩盖真实等待。

## 交叉证据

- 同一真实请求进程观察（约150毫秒采样）：独立index进程约10.136秒，status约2.190秒，同时存在一个MCP进程；不是纯向量检索用了20秒。
- 使用真实官方stdio MCP、同一已发布工程的隔离副本，按平台顺序实际调用：MCP启动初始化0.874秒、工具发现0.007秒、index7.306秒、status2.300秒、MCP首次召回3.741秒、第二次0.022秒，总14.252秒。官方安装不变，结束关闭临时MCP并清理副本，发布源哈希一致。
- 以上是另一条受控链路，不把14.252秒硬拼成前一条20.557秒的精确分解；主请求进程观察已证明index/status占大头，受控MCP证明跨进程重复加载及后续复用机制。
- 此前独立API无全局跟踪：模型就绪后保存/召回约16–19毫秒。它证明可复用的计算路径很快，不能直接作为页面SLO。

## 修复方案

### P0：让“召回示例”只承担读取检索结果

1. **发布准备检索资料。** 在候选版本阶段完成官方schema及示例索引，验证对应版本/后端；完成后再切换可用发布版本。失败保留原可用版本，不能在“发布成功”后让第一位问数用户建索引。检查/编译成功与检索就绪分开记录，升级时对已有活跃库做一次准备，不要求重新建业务模型。
2. **分离schema与示例更新。** 分别追踪发布模型版本及示例版本；schema未变时不执行全schema index。通过固定版本官方示例接口增量同步新增/更新/删除，保留Markdown事实源、来源冲突处理及失败恢复；已有超时落盘的样例直接同步，不重复创建新文件。不能只删掉indexed检查而留下旧索引。
3. **复用与预热实际查询实例。** 索引完成后，对即将接收查询的同一个只读MCP实例做受控首次检索；新库选择/实例重建时可触发有限预热。只预热有预算的活跃库，绑定groupId/发布版本，保持实例池上限、活动租约、取消和空闲回收。磁盘缓存存在、CLI预检通过都不等于该MCP已预热。
4. **精简重复状态进程。** 后端/维度检查在准备阶段和实例重建时完成并与就绪版本绑定，正常召回只检查轻量就绪标记；示例更新不反复开一个status进程。依赖或索引失败需使对应就绪状态失效，不能沿用错误成功标记。
5. **有界等待与并发准备。** 同库同版本只允许一个准备任务；查询使用已就绪版本。后台准备不持有阻挡所有已就绪读取的大锁，遵循原有授权与写入串行边界；确实没有可用索引时，在短预算内给出真实“准备中/失败”，避免180秒重试。不能把不可用伪装成没有示例。

保存/点赞仍要明确区分源已持久化和向量可检索；只有实际同步并验证成功才能报告SAVED。若选择异步更新，须显式增加待索引/失败状态，不能只提前返回成功。这是可选交互方案，尚未决定采用。

固定版官方MCP的store_query对索引错误采用非致命处理，返回path并不保证索引成功；实现增量更新必须加可验证的完成条件。问数MCP继续只读，若采用常驻写入执行器，应是受预算的内部通道，复用最终答案反馈授权/建模确认，不能把写工具直接开放给问数Agent。

### P1：让页面准确展示工具实际完成

通过框架工具执行能力，逐工具发出实际开始/结束事件；维护结果顺序、工具ID、request/run隔离、取消和HITL，LLM仍等待本轮所需结果。业务通知层消费真实单工具完成，前端区分计划/排队/执行/完成；不在业务层重写ReAct循环。另修建模页非零CLI退出码仍绿色完成的问题。

### P2：基于整轮链路控制附加耗时

按请求关联容量排队、会话恢复、每轮LLM等待、工具准备/排队/实际执行、结果发送和答案结束；同库并发及发布/点赞同时发生都纳入。按发布版本复用既有工具schema/模型说明，先证实重复读取或大文本的实际占比，再优化；保留必要业务规则与查询证据，不以少查必要步骤换速度。

## 拟定验收门槛（目标，尚未达到）

- 已就绪库：真实tool_call到tool_result召回p95≤1秒；新会话不能重新全量建索引。
- 发布完成后的第一问也满足已就绪目标；空闲回收/服务重启后的冷实例单列，目标≤5秒完成检索准备或给出明确状态，不再几十秒静默等待。
- 当前固定简单COUNT题整轮p95目标≤10秒；复杂业务题按自身SQL/分析成本单列。记录首个业务答案时间，不用“正在查询”文字代替答案时延。
- 10人同库、10人多库以及问答期间点赞/示例编辑/发布：统计p50/p95/最大值、错误率、排队时间、MCP/CLI数量、CPU和PSS/内存峰值；满足目标才宣称达到该容量。当前云机与65分别记录，不互相外推。
- 覆盖无示例/有示例、首问/后续问/新会话、重启/空闲回收/实例驱逐、发布变更/仅示例变更/删除/失败回滚、缺模型/坏索引/取消、库切换/撤权/共享查询隔离。原结果正确性、SQL只读和官方Wren路径保持。
