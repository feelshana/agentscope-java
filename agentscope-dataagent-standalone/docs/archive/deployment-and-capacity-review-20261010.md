### 代码原因与待处理边界

- `LocalSessionTurnGate.acquire()` 使用无期限的 Semaphore.acquire；`HarnessGateway.withGatedStream()` 在 doFinally 释放会话门。当前能串行，但没有有限等待/队列大小和普通问答全局准入。
- `WrenInstanceRegistry.call/callAuthorized()` 用每库 synchronized，等待监视器本身没有期限且不响应线程中断。既有 MCP 请求超时、初始化超时和 30 分钟空闲回收存在，不能说 Wren 完全没有超时；这些超时未覆盖获取每库锁之前的等待。实例集合没有总上限，本轮实际增长至 5 个。
- `ChatController` 的 10 分钟 timeout 在工具事件订阅的 takeUntilOther 上，异常后会结束这条旁路；它不是整个 Agent 执行的统一截止时间。
- `AuthController.login/me()` 内 JPA/密码检查没有主动切换调度器；聊天入口的前置 guard/会话登记也有同步路径。本轮小负载未表现为页面明显变慢，结构问题仍应收口。
- `SharedSandboxFilesystem.execute()` 将 InterruptedException 转为取消；`LazySandbox.exec()` 随返回释放本地操作租约；底层 `DockerSandbox.doExec()` 通过宿主 docker exec 的 Process.waitFor 等待，没有在中断路径上完整清理宿主客户端与 drainer，更没有按本次 runId 停止容器内作业。只杀宿主 docker 客户端也不能保证远端 Python 结束。
- RunPythonTool 已有容器内 `timeout --kill-after=5s 120s`，这是现存保护；不能据此宣称用户停止后立即释放 CPU/内存。预算必须跟随真实作业生命周期，避免请求门提前释放后反复启动遗留计算。

#### 原因定位与修复方向

1. **8 个沙箱上限**：实际观察到 8 个本项目管理的容器，后续用户获得“沙箱容量已满”。这是容器数量预算，不是已经证明磁盘满；模型有回答将其误述为存储空间不足。需调整容量、闲置回收及明确繁忙错误，不能让模型自行猜测原因。
2. **内部消息检查遗漏本轮上下文**：短时 JFR 捕获的异常栈显示，`InboxMiddleware` 每轮推理调用 `WorkspaceMessageBus.queueDrain/listSorted` 和 `WorkspaceAsyncToolRegistry.findStale`；这两个 workspace 实现使用固定空 `RuntimeContext`，访问 `SandboxBackedFilesystem` 时无法使用本轮的 `SandboxAcquireResult`，转而依赖代理共享 fallback。其他请求完成后，生命周期中间件会清除此共享引用，尚未完成的请求就可能在下一次推理前失败。单人成功、十人混合两轮均有失败；部分 Python 工具已返回 exit_code 0 / 正确求和结果，随后消息检查失败，最终没有成功 done。需让内部消息与异步状态操作携带本轮绑定，保留原用户/会话隔离；不能仅吞异常或让共享引用永久指向某用户。
3. JFR 同时捕获技能预加载 callback、后台 memory flush 和 session mirror 的同名异常；前者/后台任务有各自容错，**不能把所有同名异常都算作本次问答终止原因**。上述 inbox/异步检查位于推理主路径，需要作为优先阻断处理。修复后还需覆盖后台回调与会话结束的生命周期。
4. 上一轮已证实的取消后 Python 继续执行仍未修复。应与容量提升一起处理，避免反复停止/重发绕过真实计算预算。

### 具体实现

1. **每轮上下文**：消息总线、异步工具登记、inbox 检查捕获本轮上下文；后台 memory flush/maintenance 和 session mirror 保留沙箱绑定与文件路由。非沙箱场景沿用原上下文身份，避免改变本地建模/既有扩展的契约。技能预加载前先绑定本轮沙箱，再执行原回调与启动。
2. **准入和等待**：新增 `ChatCapacity`，普通问答每进程执行 16、每用户 2，等待 16、每用户等待 1，最多等 30 秒，执行最多 600 秒。等待不占工作线程或沙箱，开始执行前重新检查授权和选库。同一会话重复发送明确拒绝；前端有排队状态和停止操作。建模对话不套这组普通问答预算。
3. **真实作业取消**：Docker exec 为本次命令建立进程组，唯一 PID 标记和取消标记处理启动竞态；取消或超时先 TERM，再清理仍存活进程。Python 的 `timeout` 加 `--foreground`，使它及 Python 留在该组；否则 GNU timeout 会另建进程组，底层普通 shell 测试通过也不能证明 Python 已停止。文件系统中断抛取消异常，不继续收集产物。请求结束后，真实 Python 尚在退出时仍保留执行预算；不杀整个容器，不干扰同用户另一会话。
4. **实例总量**：默认 16 个用户容器、16 个普通问答长期 Wren 实例。预算满时只回收闲置实例，保护活动租约和正在调用的 Wren；关闭失败保留预算并重试，不假定已经释放资源。Wren 同库改用可中断、限时的锁，保留 stdio 客户端必要的串行调用；不同库可并行。建模临时校验进程未纳入该池，不能写成全项目所有 Wren 已统一限流。
5. **减少平台 IO**：会话索引写锁按实际用户数据路径区分，避免不同用户写各自 sessions.json 却串行等待。内置 data-agent 的会话索引和内部队列放到固定工作区 `.runtime/data-agent/`，会话文件按用户隔离，保留路由和身份检查；Python 输入/执行仍在各用户沙箱中。避免每次 inbox/索引操作都启动一次 docker exec。正式历史和附件沿用原持久化。
6. **页面线程和发布**：登录/me 的 JPA、密码操作和聊天前置阻塞检查切到工作调度器。前端构建产物已同步，旧哈希 JS 清理；分析镜像加入 util-linux/setsid。发布仍是现有 Maven conf/bin/lib 和 start/stop，参数、备份位置见简单发布指南。
7. **首事件前连接恢复**：持续负载两轮分别出现 2 次、1 次模型 HTTP/2 GOAWAY；原异常包装不能触发既有重试。只处理 GOAWAY 的中间版本又观察到同一连接上的 3 次 closed，因此补齐断连类型。OpenAI 协议客户端现在只对尚未收到任何原始事件的 GOAWAY/closed/connection reset/EOF 等待 250ms 后重建本次模型 HTTP 请求一次，收到文字或工具事件后不重试，显式 maxAttempts=1 时不启用。它不重新执行 Agent 或工具，也不解决任意中途截断；取消退避不会再发请求。另有 6 项确定性测试覆盖成功、耗尽、部分文字/工具、显式禁用/其他异常、HTTP 错误与取消，以及该模块全量回归。
8. **模型连接协议**：补齐首事件前恢复的 HTTP/2 版本持续负载仍有 327 次中 2 次 closed，其中一个已输出最终文本但没有成功结束，另一个可能已收到无可见文字的原始事件；按规则不能重放。错误同刻出现，保留于 `http2-recovery-pass/`。为避免共享 HTTP/2 连接被关闭时影响多路请求，应用层模型客户端改用独立配置的 JDK HTTP/1.1 连接池（`dataagent.openai.http-version: HTTP_1_1`）；可显式改回 HTTP_2，但应先在目标模型网关回归。没有修改 SDK 全局默认协议，也不把半截内容冒充成功。此为基于实测的兼容措施，尚不能断言关闭连接的根因一定在供应商或 JDK 的哪一侧。
