## 三、数据源能力边界必须先处理

`MdlPublishService.selectWrenSource()` 当前明确接受/拒绝：

| 一个知识库内的数据组合 | 当前发布支持 |
| --- | --- |
| 全部为上传文件生成的表 | 支持，使用项目数据集库连接 |
| 全部来自同一个 MySQL 外部数据源 | 支持，使用该源的 Wren profile；具体查询仍需实际验证 |
| 上传表与外部表混合 | 拒绝 |
| 多个外部数据源 | 拒绝，即使都是 MySQL |
| PostgreSQL 外部源 | 连接/探查界面支持，但 Wren 发布拒绝 |

`DatasetService` 当前已在上传/关联前校验来源组合，拒绝上传与外部表混合、不同外部源及非 MySQL 关联，并有对应测试。这个后端限制已经实施；数据源配置页面仍支持保存/探查 PostgreSQL，前端应清楚区分可配置和可用于 Wren 知识库的范围。

### 3.2 新增/移除数据后的实际行为（代码核对，新增风险未运行复现）

`DatasetController.upload/delete`、批量上传及 `DatasetGroupController.associate` 会在数据变更之后调用 `BaselineMdlService.publishAfterDatasetChange()`，不是只标记 DIRTY。随后 `MdlPublishService.publishBaseline()` 使用与显式发布相同的 `doPublish` 链路，读取整个当前 workspace。

1. 新表由 `MdlSeeder.reconcile()` 补基础模型，已有人工业务模型尽量保留；不会自动正确推导所有新增表的业务关系、指标和口径，相关部分需要增量建模与核对。
2. 自动发布读取整个工作区：此前已写入工作区但尚未显式发布的业务修改，工程检查通过后可能随本次数据变更发布。这不是仅发布新增表，需确认是否符合产品预期，原建模代码暂不改。
3. 移除数据集会移除其基础模型；依赖它的关系、视图或派生模型可能阻断发布，需要修复引用。上传表在发布之前就会尝试 DROP；保留旧 MDL 快照无法恢复已删除物理表，旧问答可能报错。外部取消关联不 DROP 业务表；发布失败保留旧模型时，旧模型仍引用已移除关联表的风险需验证。
4. 发布成功替换当前快照并递增模型版本；失败保留旧快照并记录错误，已有版本时状态会回到 PUBLISHED。前端应清楚展示失败及当前有效版本，不能只看状态标签。
5. 删除最后一个数据集会清理该库 Wren 工作目录/发布产物、状态重置 NONE、版本归零；重新加表不能假定旧业务模型仍在。
6. 当前发布替换仅使用临时 previous 目录回滚，成功后删除 previous；模型版本数字不代表所有历史版本都可一键恢复。
7. 外部业务表只增删记录、字段不变时，正式查询读取源表当前数据，无需为每批新行重新建模；新增/改名/删字段需要元数据刷新、模型校验与发布。当前发布播种主要读已保存的字段元数据，未见完整的外部结构自动刷新闭环，不能假定重新点发布会发现所有源库 DDL。

建议产品规则（待确认）：首次导入允许自动基础发布；已有业务模型的数据变更进入待发布状态，新增表保留旧有效模型、依赖删除先检查影响、业务口径审阅后显式发布。这个调整涉及建模发布流程，按用户安排先讨论，不自动实施。

## 四、权限与身份差距

### 4.1 已确认的首期规则

以 ADR 0050/spec 041 为准：

- 不分组织；全局管理员查看、管理所有知识库。
- 创建者自动有 MANAGE；普通用户按成员授权获得 QUERY 或 MANAGE。
- QUERY：看授权卡片、选库问答、下载本人生成 CSV/图表/报告；不能进入详情、预览原始数据或维护库。
- MANAGE：包含 QUERY，并可维护数据、描述、字段说明、术语、建模、发布、授权和删除。
- 撤权后阻止新的数据读取及续问；本人已生成历史与附件继续可读。
- 库管理员不因管理库就自动获得他人私有会话及附件。
- 首期不做行列级权限。QUERY 可以通过问答和明细 CSV 读取库内数据。

### 4.2 已实施并完成本地验收，待线上专项验证

当前已经加入成员授权表和统一 ACL，知识库卡片、数据集、建模、发布与工具按 QUERY/MANAGE 检查。共享库数据归属与提问用户身份分开，历史和附件继续私有；列表和选库框服务端分页，最近选择及提问范围快照持久化，Wren 排队结束后复核权限。入口、数据库表及验收场景统一见 [权限 spec 041](specs/041-knowledge-base-sharing-and-bi-identity.md)。

普通问答每轮可不选、单选、多选或全选；建模保持单库。九个新建测试库及跨创建者问答、建模发布、权限撤销与附件隔离的实际结果，见 [2026-10-13 全流程体验](experience-results-20261013.md)。BI 用户同步/停用尚未实现；例行任务的实际调度和执行授权仍需后续收口。

### 4.3 BI 免登录与同步

当前 `AuthController` 是用户名/密码登录与 JWT，未见 BI 用户同步或票据交换入口。

用户表同步解决“本地有哪些用户”，可信身份交换解决“这次访问是谁”。需要 BI 同事提供稳定用户 ID、显示名、管理员映射、同步/停用规则，以及可信入口或短期票据协议。保留用户无需再次输入密码的体验，但服务端仍验证可信身份；浏览器直接传用户名不可作为已验证身份。

iframe 还需明确 BI Origin、入口路径、同源代理或跨域、会话过期/登出和尺寸。当前前端资源和路由未专门适配任意子路径，首次优先独立域名根路径或一致的代理路径；子路径接入须同时改资源、路由与 API。

2026-10-13 最终确认普通问答每轮可不选/单选/多选/全选，保留上下文；全选每次发送展开最新授权。建模保持单库，具体规则见权限 spec 041。

### R06 本地实施结果（2026-10-14）

- 默认单文件 50MB，一次选择最多 10 文件/100MB；每文件最多 100,000 数据行、100 列、2,000,000 单元格，同时生效。单元格按数据行数×表头列数计算，不含表头；超限拒绝，不截取前半份作为成功数据。
- 前端保留多文件并行，按服务器策略分批启动；进程内全局最多 8 个上传处理名额，满额返回 429，不堆积无限后台等待。同库不同名称可并行，同库同名在处理中返回 409。Excel 工作表探查、服务端批量接收和批量发布也占用处理名额。此名额不是 R08 的全站问答准入。
- multipart 大块内容临时落盘，应用另按实际字节限制；每次前端选择校验总量，服务端 `/batch` 在全部暂存并确认累计字节后才开始导入。单文件 API 的多次独立请求不被当成一个跨请求“选择批次”。框架仍会先解析 FilePart，再进入导入准入；不能把它当作 HTTP 连接数或临时磁盘总配额。
- 保留每文件 4 个写入工作线程、每批最多 5,000 行；最多 4 个未完成批次，解析过快时等待写入。另以批次字符数控制宽表缓冲。失败停止继续入队，等实际写入收敛后只删本次新表；清理失败保留既有资源记录和明确日志。JDBC 增加连接/读写/语句等待上限，URL 显式选项优先。
- 单文件发布失败返回 `IMPORTED_MODEL_PENDING` 和已保存 datasetId；批量接口逐文件返回成功/失败/模型待发布，成功项不会被失败项隐藏。页面提供现有“检查与发布”入口；网络、超时和无法确认的服务端异常提示先刷新确认，避免盲目重传。
- 状态仅供实际上传者在仍具管理权限时读取；前端缓存按登录身份及知识库隔离。服务端最近状态在内存保留约 30 分钟/最多 2,000 条，重启不保留，数据集元数据和表继续持久化。没有增加任务中心、后台续传或自动恢复服务。
- 全量 561 项测试（0 失败/0 错误/12 跳过）、前端构建、36 项真实接口检查和 15 项前端逻辑检查通过；39 张隔离测试表逐表 COUNT 与元数据相等，未发现孤立导入表或临时上传文件。具体资产、测速和保留问题见体验记录的“上传稳定性最小方案验收”。用户当前 8080 后端未由助手重启。
- **新增观察项，未改建模代码**：新版两轮 8 并发测速中，3 次自动发布在 Windows 报 `published.next -> published` 替换失败；30 个文件数据均保存，后续发布覆盖全部，最终三库均可查询且无未发布变更。4 并发那轮 10/10 请求成功。需要后续单独复现和定位发布目录替换错误，不能宣称 8 并发发布已稳定验收。

### R07/R08 改造前基线（2026-10-14，历史记录）

五个新普通账号在本地已有上传库进行 2/5 人聊天、同库/不同库 SQL、Python：39 次常规问答完成，数值与独立核对一致，SSE/历史也一致；159 次页面 API 探针成功。另完成同会话串行及排队/执行取消测试，确认已启动 Python 在断连后仍可能继续执行并写文件。当前仍无普通问答全局/每用户准入、有限等待及 Wren 实例总预算。

下一步先讨论取消真实计算的回收和问答/实例有界方案，再实施；测试与具体建议统一见 [容量评估](deployment-and-capacity-review-20261010.md#2026-10-14-问答稳定性基线与最小方案)。当前只测小型查询和合成计算，本机 32 逻辑核/31.7 GiB，不能直接判定公司环境容量。没有改建模代码，也没有顺带修复偶发回答结束判断。

**最新补测优先于上述初始基线**：用户要求至少 10 个不同用户同时执行并争取更高并发，原 5 执行 + 5 等待方案作废。补测的 35 个 10/15 人小型 COUNT 正确，但聊天、Python 和两轮十人混合未通过；JFR 定位到内部消息/异步检查遗漏本轮上下文、依赖共享 fallback 沙箱的问题，Python 还触及默认 8 个容器上限。先修上下文和真实计算取消，再调整容量及准入，重新验收；不能宣称现在已稳定支持十人。详细指标集中维护于容量评估。

## 七、建议执行顺序

1. **首发范围与版本基线**：确认 MySQL/Doris、例行任务、BI 身份设计及建模暂缓风险；整理当前未提交的已验收改动形成中文提交。
2. **稳定性（R07/R08，R06 线上回归）**：上传和普通问答最小方案均已实施，本地结果见容量评估；下一步按典型规模在部署环境回归，不再重复启动同一套改造。
3. **真实数据源（R04）**：云 MySQL/Doris 所测小数据路径已通过，继续匹配公司版本、表模型、网络和典型规模回归；失败先记录原因和影响，建模原有实现修改仍先讨论。
4. **BI 和正式环境（R03/R05/R09/R10）**：功能设计确认后推进，完成身份/停用、iframe、Linux 启停、数据持续保存、删除异常、升级回退和备份恢复。
5. **容量与业务验收（R08）**：本地已修复已复现阻断并验证 10/15 人梯度、连续混合、取消和隔离；在 65 重跑并与模型及数据库预算一起确定实际容量。当前基准仍是小型 COUNT/合成 pandas，复杂业务分析需另测。

后续已按用户确认实施 R06 上传最小方案，其余建模问题、云部署/并发演练、BI 接入及全站界面改造继续遵循用户最新安排，确认方案后再推进；正式上线前仍需完成首发承诺范围的验收。
