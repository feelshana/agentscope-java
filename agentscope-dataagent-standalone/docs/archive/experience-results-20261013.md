## 初次发现的问题与后续状态

优先级是本次建议，不代表已经获准实施。

### P1：文档提案详情的 JSON 结构异常（后续已修复）

九库 `/modeling/enhance` 提案的 `payload` 返回 `array:false`、`containerNode:true`、`nodeType:OBJECT` 等节点属性，未返回应审阅的关系/术语/规则实际字段。浏览器“查看落库草案”同样显示这些属性。标题、摘要、来源引文仍正常。

影响：用户不能完整核对即将落库的参数。本轮因此没有盲目采纳这 104 项文档提案，改用完整对话提案审阅完成建模。不能宣称文档提案逐项采纳流程全部通过。

源码线索：`SemanticModelingController` 使用 Jackson 2 `JsonNode`；项目 Spring Boot 4 HTTP 序列化链路可能按节点对象的属性处理。异常响应已确认；具体修复还需确认统一 Jackson 类型/转换方式，不能仅凭推测修改全局序列化。

证据：[页面截图](../../output/playwright/e2e-1013/document-proposal-payload.png)、`document-final-status.json`。上述问题来自 HEAD 的原有实现；初次验收只记录，后续获用户确认后的修复见文末。

### P1：问答语义说明和发布快照未完全一致

电商发布前：模型上下文中已出现草稿「销售明细」「订单销售额」的说明和 SQL，但 `wren_describe_model` 仍正确拒绝这两个尚未发布的视图。助手因此说明“文档里有口径，并不等于已经发布”。查询引擎没有执行未发布视图；发现的是语义说明提前可见。

源码确认：`DatasetService.semanticViewsText()` 读取 `workspaceReader.read(gid)`；`semanticBusinessRulesText()` 读取工作目录 `knowledge/rules/*.md`。`MdlWorkspaceReader` 直接读取 workspace；正式 Wren 查询使用已发布 manifest。对应实现来自 HEAD，不属于本次新增授权判断。

影响：草稿口径可能提前影响模型生成 SQL，甚至用旧模型字段自行拼算新口径。建议后续让普通问答中的视图、关系、规则统一读取发布快照，建模工具继续读取草稿。

证据：`draft-isolation.json`、`ecommerce-corrected-proposal.json`、发布前截图。

### P2：单文件“覆盖上传”参数与后端契约不一致

向新建电商库重传同名商品文件，传 `overwrite=true`，后端仍返回 409，原四张表保持不变。前端有覆盖参数，但单文件 `DatasetController.upload()` 没有接收/执行该参数。

同一入口的 `selectedSheet` 也未在该控制器声明；本轮源 Excel 均为单工作表，**未运行验证多工作表问题**。后续需要先明确重名更新、模型变更、历史版本及失败补偿的语义。

证据：`extra-answers.json` 的 `duplicateUpload`。该上传实现是原有代码，未修改。

### P2：建模页面恢复与文案体验不一致

- 重新进入建模页面只恢复待确认提案，已结束的建模对话不在页面恢复；源码 `ModelingChatPanel` 清空消息且没有 pending 时直接返回。普通问答历史不受此限制。
- 页面仍写“使用右侧问题清单”“每个问题由你确认后再发布”，实际无预设问题可以完成发布。
- 发布时间直接显示 UTC 字符串，本地北京时间差 8 小时。
- 发布变更中同一视图按 metadata.yml / sql.yml 显示两次；实际只创建一份视图。此前 10 月 10 日已记录，此次再次复现。

## 后续：文档提案 JSON 响应修复

2026-10-13，用户确认采用接口返回普通 Map/List 的方案后实施。

- 原因确认：项目内部使用 Jackson 2 的 `JsonNode`，Spring Boot 4 WebFlux 使用 Jackson 3 序列化，导致节点被当作普通 Java 对象输出内部属性。用项目实际依赖独立复现；只读检查数据库，存储的业务 JSON 结构正常。
- 代码：`SemanticModelingController.EnhanceProposalVO.payload` 改为 `Map<String, Object>`；`CubeVO` 的 measures/dimensions/timeDimensions 改为 `List<Object>`。读取存储 JSON 时转换普通容器，嵌套对象、数组、数字、布尔值和 null 成员保留。空内容、JSON null 或解析失败返回空对象/数组。
- 范围：仅响应 DTO 与映射方法。内部提案生成、数据库结构、采纳业务逻辑和全局 Jackson 配置没有修改；前端契约保持 JSON 对象/数组，无需修改页面。

原异常 API 历史与本地原始 JSONL 都保存了 `afcbe0f3-e658-47df-8f74-6aed1af873e7` / “两个库已分”，前面的两次工具结果各为 100。说明异常内容已在服务端形成，不能归因于前端独自截断或只在历史 DTO 转换时丢失。人工可读 LLM 日志不包含上游 finish_reason/结束标记，原请求原始模型 SSE 未保存，无法判定当时是资源中断、提前 EOF、长度上限，还是正常 stop 但只回答半句。

### 已确认的程序缺陷

1. 默认 JdkHttpTransport.readSseLines() 遇 EOF 即完成流，用 takeWhile 消费 [DONE]，没有要求有效模型结束状态；OkHttpTransport 读循环也在 EOF 后 sink.complete()。
2. OpenAIResponseParser 已解析 ChatResponse.finishReason，但 ReasoningContext.processChunk() 没有保留或校验这个独立字段；ReActAgent.isFinished() 在没有工具调用且存在非空文字时判定完成。
3. ChatController.stream() 对正常完成的 Agent Flux 追加 done；ChatPanel 收到 done 后标记完成。前端已有“没有 done/error 就断流”的检查，但服务端已经发 done 时无法知道模型实际是否完整结束。

使用真实项目依赖、独立本机 HTTP SSE 服务，在 JDK/OkHttp 两条传输路径运行 **28 组隔离测试**：原行为 14 组 + 拟议结束检查原型 14 组。每条路径的 EOF 无结束信息、[DONE] 无结束原因、insufficient_system_resource、length、aborted 五种异常，都在原行为下生成成功 AgentResult，把“两个库已分”保存为 ASSISTANT。忽略目录内加入模型结束检查原型后，这十个异常全部报错，半句不进入成功历史；正常 stop 完整回答和正常 stop 短答“好的”两类控制保持成功。

这是**异常生成被误判成功**的明确缺陷复现；响应由隔离服务主动构造，不是原请求的上游原文。该缺陷足以导致同类现象，但不能据此断言原请求的具体结束原因。DeepSeek 官方区分 stop/tool_calls 与 length/content_filter/insufficient_system_resource/aborted，见 [API 说明](https://api-docs.deepseek.com/api/create-chat-completion/)。

### 修复建议（待用户确认）

- 异常走现有 error 路径，提示“回答生成未完成，请重试”，不发成功 done、不保存半句为成功回答/样例。复用现有页面失败展示，验收错误后的历史与刷新行为，避免误导为完整答案。原五字历史保留，不追写伪造完整回答。
