# 回答依据与可复核链路：可行性讨论稿

日期：2026-11-05 Asia/Shanghai。状态：分析建议，尚未确认本轮实施范围；不是已交付功能或新的正式架构决定。

## 目标与判断

用户提出：回答给出了数据或结论，如何让使用者知道数据从哪里来、怎么算、能否信任。建议将产品能力命名为“查看依据”，正文关键数字附近提供引用，展开后分层展示口径、结果、计算与技术详情。目标是让用户能够判断并复核答案，提高与实际可靠程度相符的信任。

必须分别回答四个问题：来源是否可靠、查询是否符合业务口径、回答是否忠实于结果、推断是否超出数据支持范围。有来源不等于结论正确，执行成功也不等于业务正确。

展示真实执行事实、明确公式与公开的分析方法；模型对过程的自然语言描述不能充当实际执行证据。业务用户无需阅读全部工具日志。

## 建议的用户体验

第一层：回答正文保持简洁，在适合定位的关键数字、图表或结论后提供“依据1”等引用。回答底部有“查看依据”；没有逐项绑定时文案只能是“本轮查询记录”，不可让用户误以为每个结论已经得到证明。

第二层：复用现有详情侧栏的交互模式，展示选中结论的业务解释。若与附件预览共用侧栏，保留返回位置和选中依据，窄屏用整页或抽屉，避免多个面板叠加。

虚构示例：

```text
本周活跃用户 823 人 [依据1]，较上周增长 12.1% [依据2]。

查看依据 → 活跃用户 823 人
数据来源：BI平台使用分析 / 操作日志、人员信息
统计时间：2026-10-26 至 2026-11-01（北京时间）
计算口径：有操作记录的账号去重计数
筛选条件：排除测试账号（仅在实际条件已确认时显示）
结果依据：查询1，active_users = 823
数据状态：同步完整截止日期来自同步任务记录；无记录则显示未知
操作：查看结果表格 / 下载本次结果 / 展开技术详情 / 反馈口径问题
```

823、734、12.1%均为交互示例，不是本项目实测业务数。增长率依据应明确显示 (823-734)/734，原始两期查询均可定位；舍入由程序统一处理。

第三层：技术详情提供完整语义 SQL、参数、执行时间、发布版本与查询 ID。实际执行 SQL 只在执行层确实留存时显示；事后 dry-plan 应标为重新解释的计划，不冒充当时实际执行 SQL。

业务链路按结果依赖组织，而非简单按调用时间排列：

```text
已发布口径 ─→ 本期查询结果 ─┐
                          ├─→ 增长率计算 ─→ 增长结论 / 图表
已发布口径 ─→ 上期查询结果 ─┘
```

运行日志另设折叠入口，失败、诊断、未采用查询不会默认混入最终结论依据。也不展示未经记录的“思考步骤”。

## 可信状态的表达

不做统一可信度分数，也不把全部状态压成一个绿色认证徽章。

| 状态事实 | 可用文案 | 不能据此声称 |
| --- | --- | --- |
| 查到了真实结果 | 已取得查询结果 | 业务口径正确 |
| 引用存在且数值/单位/舍入一致 | 数值与结果一致 | 过滤和分母符合业务要求 |
| 参考了确认样例 | 参考已确认问答 | 本轮严格使用了同一逻辑 |
| 对有严格身份/修订匹配的逻辑确认 | 采用已确认口径，显示版本及确认来源 | 当前原始数据无错误 |
| 人工审核了本轮具体答案 | 本回答已由某角色确认，显示时间 | 将来重跑的结果也自动有效 |
| 解释/预测/业务假设 | 统计解释、预测或待验证推断 | 已证明原因或未来事实 |

应分别显示：查询返回是否截断、正文是否仅展示前N条、数据同步覆盖是否已知。未截断只说明这条查询的结果没有被工具裁剪，不能证明源数据完整或 SQL 没有主动 LIMIT。SUM/去重人数/均值不能一律相加校验。

## 可行的技术契约

沿用官方 Wren、当前权限与 AgentScope 运行循环，不新增物理 SQL 通道、不改官方工具参数来塞入证据字段。

建议先明确以下四类对象，具体存储方案在正式 spec/ADR 中决定：

1. QueryEvidence：服务端生成 evidenceId，绑定用户/会话/轮次/调用、实际发布修订、工具与参数、时间、结构化结果/受限预览、类型信息、截断与错误、结果文件引用。
2. ComputationEvidence：输入 evidenceId 列表、代码/公式与版本、参数、运行状态、输出指标/产物；与既有 Python runId/附件关联。
3. ClaimReference：正文稳定的片段/事实 ID，对应查询的具体单元格或计算输出、单位与展示精度，以及核对状态。优先绑定结构化事实或 Markdown 节点，不使用流式文本易漂移的字符偏移。
4. RuleReference：规则/确认样例的稳定 ID、当时版本与确认状态。区分“本轮读取”“被引用解释”和“有可验证条件证明逻辑采用”，不能把读取文件等同于执行遵循。

服务端记录执行事实；模型只能从本轮允许的 ID 中选择引用，并补充受约束的说明。引用 ID 真实有效，不等于引用内容足以支撑整句自然语言。

对可结构化的数值，让模型选择事实 ID，由程序渲染数字/单位/舍入，可显著减少复制错误。自由文本仍保留解释边界，不声称自动证明所有结论。错误或缺失引用不展示为有效引用；有数值矛盾时让受影响事实进入待核对状态，避免阻塞整个回答或通过猜测修正。

业务化 SQL 解释采用受支持语法的确定性解析：聚合、分组、过滤、日期、去重字段。遇到复杂 CTE、窗口函数、UDF 或无法解析的表达式，展示原 SQL 与“未自动解析”；如额外使用模型解释，应标为解释文本并可对照原始条件，不能作为已验证执行事实。

图表应按结果引用取数，执行可记录的选择、排序、TopN、单位换算，保留和文本的同源关联。自由 Python 的输入依赖不能靠搜索 read_csv 字符串可靠证明；固定分析脚本先记录真实输入清单/运行清单，任意 Python 代码的精确列级追踪单独评估。

历史重开优先读取当时的证据记录，避免每次从整段会话猜测；复用会话持久基础不等于每次重新扫全部工具历史。已发布语义版本和数据快照是不同对象。查询保存结果支持“查看当时结果”，重新运行只能承诺按原条件重算，动态源不能承诺得到相同数值。

结构化结果须保留 NULL、空字符串、decimal、时区和单位；现有 CSV 的 NULL→空单元格不适合作为唯一精确事实存储。结果内容哈希可用于去重/完整性检查，但不能证明源数据真实。

权限必须核对会话/证据归属，按项目已有策略决定撤权后的历史结果可见性。ArtifactStore 当前侧重 owner/session，若新增按知识库撤权控制，属于需要明确的策略调整；不能宣称现有附件已经具有该行为。证据随会话删除与配额治理，存储失败显示可追溯能力降级，不伪造完整记录。

## 分期建议

### 第一步：修复来源可见性，建立结果身份

统一官方回执解析、补齐真实结果元数据、持久化 evidenceId 与调用/附件关联、显示查询记录和技术详情。只使用现有结果，不点击即重查，不增加每轮模型审查。历史缺字段展示未知，不回填猜测。

这一步工程风险相对低，但只能解决“本轮查过什么”，不能独立兑现“每个结论从哪来”。源码中的CSV、回执、会话恢复是基础；结果身份、存储和协议闭环需要后端参与，不能仍按旧稿2–4小时前端修补估整个功能。

### 第二步：关键事实与结果绑定，作为业务首版目标

覆盖单库 SQL 聚合、TopN、同比/环比等常见场景，建立关键数值引用、结果定位、确定性计算与业务条件摘要。正文、图表和下载共用结果身份。先支持有限、可验收的事实类型，再扩展任意自然语言。

建议第一步和第二步组成对用户正式发布的最小闭环。明确引用不足/缺失，不静默退化成看似完整的证据。

### 第三步：分析链与维护闭环

固定归因/异常/预测脚本记录参数、输入、方法及输出；区分观察、统计贡献、预测与因果假设。反馈定位到具体结论/口径，经既有建模确认与发布路径修复。人工确认按修订失效，不把点赞自动等同于全库认证。

性能原则：先记录现有事实，证据按需加载；不默认额外跑SQL、全表扫描或第二个LLM审查。为证据保存、引用校验和首次打开设置明确预算，并实测首token、最后token到done、存储成本；任何具体延迟和工期待样本验证后给出。

## 验收建议

独立标准答案与执行证据分别验收。用冻结虚构数据覆盖：

- 单值、TopN、同比/环比和多查询修正，最终引用不会落到未采用查询。
- 相同数值出现在不同表/行/列，不按数字文本搜索猜出处。
- SQL空结果、聚合0、NULL、除零、舍入、单位换算、重叠去重人数。
- 工具截断、SQL主动LIMIT、界面截取、CSV失败/超额、数据截止未知。
- 同轮去重、重试、取消、失败后继续、流式显示、历史重开与跨轮引用。
- 发布过程中切换版本、动态数据变化、确认问答待复核。
- 跨用户/会话拒绝、共享库撤权策略、附件删除、会话删除。
- 正文/图表/文件同源；Python 运行失败不标成功。

正式实施前形成新 spec；如确定新增持久模型、撤权策略或替代旧引用契约，再用 ADR 记录取舍。与 ADR0081/spec069 既有方向衔接，旧文档的待实施/完成标记不能代替逐项源码和行为验收。

本轮没有实施业务代码，没有运行真实问答或竞品对照测试。建议优先评审：业务首版是否聚焦单库 SQL 结果和关键数值绑定、首个试点场景、撤权后的历史证据策略。其余实现细节可按项目边界继续收敛。
