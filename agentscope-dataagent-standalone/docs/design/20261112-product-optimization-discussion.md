## 2. 为什么继续优化、往哪里优化

用户希望产品真正好用、爱用、愿意长期使用，能够对标优秀企业级 Agent 产品，而不只是界面美观或能完成一次查询。

前一轮建议关注五种体验：知道怎么问、相信回答、方便追问、成果能用、下次还想来。对应七个方向：回答依据、上下文追问、统一结果操作、保存分析、汇报分享、例行任务、反馈与失败恢复。

另一份报告补充了跨会话积累和运营：用户能看到系统学到了什么、纠错有回执、质量变化可发现、任务主动交付。综合建议是：

> 问得可靠 → 分析能复用 → 纠正有结果 → 重要工作按约定持续完成。

这个顺序不是要求严格串行开发全部功能。应先确定证据、分析定义和权限等共同基础，再按小范围业务场景逐步交付，避免收藏、报告、分享、任务分别建设一套互不相通的对象。

“有没有自动推送”“是否暴露多 Agent 编排”不能作为产品是否有价值的唯一标准；用户独立完成真实工作、减少重复劳动才是主要判断依据。

## 4. 候选方案清单：保留稳定编号，后续按编号选范围

以下均为**待选择**。MVP 是建议的最小用户闭环，不是已确认需求；复杂度是相对判断，不是工期承诺。

### F01 回答依据与数据状态

- 用户目标：回答“这数怎么来的，能不能拿去用”。
- 建议首版：覆盖单库聚合、TopN、同比/环比；业务摘要呈现知识库、时间、筛选、口径、查询结果入口；关键数字逐步绑定真实结果，技术详情按需展开。
- 必须区分：查询时间/源数据更新时间、模型发布版本/数据快照、结果未截断/源数据完整、参考问答/本次人工确认、统计贡献/因果解释。
- 基础：服务端记录实际执行事实和结果身份，绑定当时使用的修订，保留 NULL/精度/单位；模型只能引用允许的真实记录。无法取得的信息标未知。
- 首版不承诺：任意 Python 的精确列级血缘、全部自然语言结论自动证明、统一可信度分数。详细边界见 20261105 提案。
- 复杂度：跨前后端，中等至较高；优先考虑。

### F02 上下文追问与条件核对

- 用户目标：继续问时不用反复解释，能看清本轮条件怎么变了。
- 建议首版：复用现有结果适用性判定，给出有数据支持的“按渠道拆开”“与上一周期比较”等具体动作；展示本轮有效时间与筛选及变化。
- 日期、分母、单位或业务词真正有歧义时再澄清；已发布规则足够明确时不反复打断。示例“流水”可以澄清实付或净销售，不把毛利当作收入的同义选择。
- 不通过推荐按钮绕过现有查询、权限和时间门禁。具体建议是否需要额外模型调用待评估。

### F03 统一结果交付与失败恢复

- 用户目标：快速看重点，结果可下载，局部失败不用整轮重来。
- 建议：复用现有结果组件，按内容组织“结论、必要图表、数据、口径、操作”，无需每次强行出图；聊天、保存结果、分享与任务结果保持一致。
- 查询成功但作图失败，应保留数据并提供适当恢复；不能为了重画图默认再查一次 SQL。重试可能产生新结果时应明确告知。
- 执行中展示真实阶段和已耗时，不编百分比。“离开页面仍能运行、完成后通知”依赖可靠任务生命周期，单独估算。

### F04 我的分析与个人历史复用

- 用户目标：第二次处理同类工作明显更省事。
- 分开三类对象：收藏会话用于找回讨论；保存结果保留当时数字/图表/依据；保存分析方法用于按新日期重跑。
- 建议首版：回答入口“保存分析”，明确知识库、指标、维度、日期规则、筛选、展示方式；首页提供轻量最近分析入口，结合个人历史搜索与整理。
- 动态源重跑不保证相同数值；“查看原结果”和“刷新数据”必须明确区分。
- 不急于决定“我的 Agent/我的工作台”一级导航；也不要求将所有遗留页集中暴露。实际入口先以常见任务为依据。

### F05 反馈处理与可控学习

- 用户目标：指出问题有回应，纠正后能知道影响范围。
- 建议首版：点踩可选原因并补充预期，关联本次问题、结果及版本；分流时间/筛选、数据异常、查询、口径、分析解释、展示问题，给处理状态和结果。
- 共享口径问题进入管理者复核与既有草稿发布流程；普通用户不能用反馈直接改全库规则。修复后回到原会话提供重新提问入口，按当前权限运行。
- 个人偏好、已确认查询经验、共享业务口径、可执行技能分别治理。先做明确保存、持久、可关闭和删除的偏好；不得让个人偏好覆盖业务事实。
- 分析类反馈可以沉淀问题与方法，但统计结论不能直接当成普遍适用 SQL 样例；技能沉淀需要独立审核。

### F06 汇报整理与受控分享

- 用户目标：将一次分析方便地用于汇报和团队讨论。
- 建议首版：选取结论、图表、表格和依据，形成简洁结果快照；组织已有复制/CSV/产物下载入口。完整简报编辑器、Office 格式生成应单独评估，不描述成已有能力。
- 分享范围、接收人、附件、有效期、撤销以及知识库撤权后历史快照能否查看，必须先明确。
- 接收人继续分析时，以自己的身份与当前 QUERY 权限开新会话，只带入允许分享的内容和条件；不继承发送人的私人完整上下文。

### F07 例行任务：先可靠订阅，再条件预警

- 用户目标：约定好的业务分析不用记着每次手动问。
- 建议保留“例行任务”名称，区分“定期分析”和“条件提醒”；定期周报无异常也可以正常交付，提醒才按条件抑制重复通知。
- 首版建议：从成功分析创建每日/每周任务，明确知识库、相对日期和时区；先站内结果、暂停、手动运行、历史与失败原因。
- 工程前提：创建人真实身份、运行时授权、所用发布修订、执行记录、防重复、有限重试、资源预算与重启恢复；数据未就绪不发送误导结论。
- 后续：阈值、数据未更新、异常检测、受控归因与真实 IM 投递。推送明确统计依据及继续分析入口，不宣称已经证明业务原因。
- 两组 BI 入库同步与用户分析订阅分开；已有同步状态可以成为判断数据就绪的依据之一，不等于已经有用户任务执行器。
- 复杂度：较高，独立跨模块功能；不开放旧 CRUD 充当首版。

### F08 质量评测、版本恢复与运营

- 用户目标：常见问题持续稳定，维护者能发现并处理退化。
- 先选 30–50 个真实高频问题作为候选样本，覆盖不同问法、澄清、空结果、缺数据和失败；样本数是讨论建议，不是本次已建立的测试集。
- 分开固定测试数据的正确性回归、线上变化数据的业务核对、编译/计划与依赖检查。已确认问题并不自动拥有独立标准答案。
- 当前建模只做 dry-plan、不查询业务表。自动执行型评测需独立定义权限、环境、预算和预期，不把线上结果改变一律判错，不将所有问题失败一律阻断发布。
- 历史恢复先补不可变快照与依赖检查，建议“恢复成新草稿/新版本”，不是直接把版本号减一。
- 日常指标：任务完成、结果复用、反馈处理、延迟、查询与模型资源成本；首问成功不只看 HTTP/工具成功，准确率须有独立评价。追问多可能代表探索或误解，不能单独判断好坏。
- “委派深度下降预示流失”仅作观察假设；用户用简单问题高效完成工作也可能是成功。

### F09 速度、数据准备与入口衔接

- 延续此前用户要求：列表和工作台展示清晰且快速；沿用聚合摘要、分页、有界加载与详情按需读取，避免列表按条触发多组请求。
- 新增依据、反馈或记忆时优先记录已有事实，证据按需加载，不默认增加业务查询或第二个模型审查。
- 分开首屏、首 token、查询、作图、最终完成耗时；没有生产数据量实测，不承诺固定秒数或任意规模秒开。
- 优先利用分析云内嵌入口，后续可从现有报表携带知识库和筛选进入分析。跨库联合查询、全渠道聊天属独立架构议题。

## 5. 综合优先级建议与尚未决定的取舍

| 建议阶段 | 主要方向 | 原因与依赖 |
| --- | --- | --- |
| 第一阶段：可靠完成一次工作 | F01、F02、F03，穿插 F09 | 回答可复核、条件明确、局部失败可恢复；同时定义可复用的结果身份 |
| 第二阶段：第二次更省事 | F04、F05 | 保存分析与反馈有落点，支撑后续分享和订阅；偏好不混入共享口径 |
| 第三阶段：进入团队日常工作 | F06、F07 的定期分析 | 分析成果可交付、可按约定持续生成；分享与执行身份要完整 |
| 第四阶段：扩展主动服务 | F07 条件预警、受控能力共享等 | 建立在可靠数据、任务与反馈基础上，再决定多渠道与技能市场 |
| 并行铺底 | F08 的真实采集、样本与基础校验 | 不等最后才发现无法度量，也不先造大而空的运营看板 |

最推荐先讨论的组合：**可信回答 + 保存分析 + 反馈处理**。也可以先从其中一个高频场景切入，用户尚未选定。

暂不建议为视觉差异继续大量制作重复原型、为展示能力开放全部遗留路由、复活知识图谱、堆叠多 Agent 编排，或把跨库/本体等架构级功能混进小改动。README 中关于用户 fork Agent、市场等历史描述，与当前主流程和权限边界需分开阅读。

## 7. 后续深入讨论时逐项确定什么

用户选定 F 编号后，再形成对应实施方案：

1. 服务谁、哪个真实场景、当前具体困难和完成标准。
2. 最小范围、明确暂不包含什么、入口与完整交互状态。
3. 已有组件/接口、必须补的持久对象与事实来源。
4. QUERY/MANAGE、私有与共享、撤权及历史结果可见策略。
5. 空结果、缺数据、失败、取消、重试、过期和版本变化行为。
6. 实测性能预算、容量与成本、验收样本及上线/回退方式。
7. 是否需要新 spec/ADR；确认之后才实施，不把本讨论稿当开发授权。

建议先用两三个真实高频场景验收：能否独立问清、快速核对口径、复用同类分析、收到反馈处理、交付可理解成果。真实用户是否愿意把下一次工作交给它，比功能数量更重要。
