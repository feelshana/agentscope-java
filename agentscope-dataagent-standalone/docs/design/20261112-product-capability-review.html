产品功能设计评审 · 2026-11-12

从「能问数」到「离不开」

我们不缺能力，缺的是把能力交到用户手里、并让它在用户手里长大的那一层产品。今天的产品是一条线性流水线：上传 → 建模 → 发布 → 问数。而 2026 年顶级 agent 产品是一个复利飞轮：问 → 教 → 沉淀 → 复用 → 主动找人。建模工作台已经把「造」这一段打磨得相当扎实；真正决定用户是否爱用的，是流水线之后剩下的部分。

范围：agentscope-dataagent-standalone 全产品（不含建模工作台内部交互） 依据：本地源码盘点 + 2026 年公开产品资料 状态：讨论稿，未实施
最尖锐的一条事实。 README 写着「让公司里每位数据分析师都有一个属于自己的数据 agent……越用越顺手」，并把「多人并行进化」「能力市场」「三通道」列为三大设计支点。但主导航只有 5 个入口（新建对话 / 知识库 / 语义建模 / 例行任务 / 更多），另有 25 条以上已注册路由没有任何可点入口：技能、子代理、工作区、能力市场提交与审批、通道、用量、用户资料，全都是「有代码、有 API、用户摸不到」。也就是说，我们最独特、最像顶级 agent 产品的差异化能力，恰恰是用户完全触碰不到的。用户看到的是一个 ChatBI，不是会长大的 agent。

01先把参照系校准

2026 年这个赛道的共识变了：模型能力不再是瓶颈，也不是差异化来源。差距在模型周围。

把 Databricks Genie One、Snowflake Cortex Agents / CoWork、Microsoft Fabric Data Agent、Google Looker Conversational Analytics、ThoughtSpot Spotter、以及国内快手 / FineBI Next / 阿里云 DataWorks 的公开能力与落地数据放在一起，能抽出五条几乎无争议的基线。它们决定了用户「敢不敢用」和「会不会用第二次」。

基线 1
信任是被设计出来的功能
可验证、可挑战、可撤销、可追溯。用户不要求完美，要求看得懂；一个偶尔出错但能解释怎么算的 agent，比黑盒的正确更让人放心。
基线 2
复用是核心策略
快手沉淀上百业务 Skill、Skill 市场 2000+，周人均对话 55 次、分析师渗透率超 80%、NPS 73.5。高频不是功能多，是「同类问题第二次不用从头开始」。
基线 3
主动性是留存锚点
不问也给：自动发现 KPI 异常 → 下钻归因 → 条件触发推送到 IM。停止使用后价值会消失的产品，才不会被弃用。Tableau Pulse 只盯预设指标、阈值告警，被普遍评为「被动」。
基线 4
入口在用户已经在的地方
看板旁的「点我问更细」、Slack / Teams / 钉钉 / 飞书里的卡片与追问、从已验证答案直接起一段对话。不是新建一个网站让用户记住。
基线 5
评测是发布门禁，不是仪表盘
固定问题集 + gold SQL，模型 / schema / 语义层一变就重跑。有自动化评测的 agent 12 个月回滚率 9%，没有的 47%。生产 trace 反过来变成新的回归用例。
一条可直接拿来验收的判据。 行业里把「把 NL2SQL / 出图 / 跑代码重新包装成 agent」叫 agent washing。真正的测试是：当某个 KPI 异常波动，平台能否不待用户提问就检测到、分解归因、量化各因素贡献，并把解释送到人面前。按这个标准，我们今天还是「问了才答」。

02六个让用户「用着用着就不想用」的断点

每一条都写成真实用户场景；每条都标明「我们其实已经有什么」——多数改进不需要造新后端。

断点 1 · 最高优先级

说好的「越用越顺手」，我既看不见，也教不了

小李用了三周，纠正过五次「GMV 要剔除测试订单」。第四周问同类问题，agent 又答错了。他不知道自己有没有教过它、教了什么、能不能撤回，也不知道同事那份好用的技能去哪领——最后他回去写 SQL 了。
现状
私有 workspace / MEMORY.md / skills / subagents 后端齐备；/workspace 是只读文件树且为孤儿页；能力市场提交端 ContributionsPage 与审批端 ApprovalsPage 均为孤儿路由；subagents-enabled=false 默认关闭。用户没有任何一个界面能回答「我的 agent 现在会什么」。
对标
OpenAI 内部数据 agent 的 continuously learning memory（用户纠正会进入后续上下文）；快手三层 Skill 体系与 Skill 市场；FineBI Next 的「记忆 + Skill，越用越懂企业」；ThoughtSpot Memory 保证业务定义在每次追问中一致。
已有基础
OverlayFilesystem、MarketContributionController / ContributionApprovalController 全流程、SkillsWorkspacePanel / SkillsMarketplacesPanel、SubagentPanel、AgentWorkspaceController。几乎是纯前端接线工作。
建议
新增「我的 Agent」作为一级入口，只做三件事：
① 它学会了什么——列出记忆 / 技能 / 子进程，每条标明「哪次对话、谁教的」，可停用、可编辑、可删除；
② 教它一句——用自然语言直接写规则，落成一条可撤销的记忆或技能，下次问同类问题时显示「已按你的口径修正」；
③ 能力市场——浏览共享能力、安装、提名自己的贡献、查看审批状态。
关键是可见 + 可撤销：可逆性是信任设计里杠杆最高的一个动作，也把 README 的三大支点真正变成产品。
断点 2

答错了只能重开，既纠正不了，也回不来

「这数不对。」——用户点了踩，什么也没发生。想改问法只能手动复制原问题重发；想说清楚哪里不对，没有地方可说。
现状
AnswerFeedback 点赞会把问答存成 SQL 问答对（藏在建模 coach tab 的 <details>「全部已确认问答」里），点踩仅记录；无分支、无撤销、无「从这一步重来」；会话标题是首问截断 40 字。20261101-prelaunch-polish-candidates.md 已提出「失败后修改问题再问」，但只到输入框回填。
对标
允许挑战假设而非单向接受；反馈带原因分类（口径错 / 数字错 / 没答全 / 结论越界）；错误按五类归因（语义缺失、数据异常、查询错误、权限错误、分析错误）分别路由去修，而不是笼统记「agent 答错了」；每周复盘 bad case，把生产失败变成回归用例。
建议
把点踩做成有落点的动作：选「哪里不对」→ 自动生成一条待复核的口径修订 → 走已有的建模确认与发布路径 → 发布后回到原会话提示「已修好，要不要重问一次」。这样现有的「问答对 + 确认流 + 发布」三件孤立能力被串成一个闭环，也顺带兑现了 20261105-answer-evidence-proposal.md 第三步「反馈定位到具体结论 / 口径」的设想。
断点 3

发布之后，没人知道它有没有悄悄变差

业务方最怕的不是「答不出来」，是「自信地答错」。改了一次口径，上周还对的一批问题这周全偏了，直到有人拿去开会才发现。
现状
产品内无评测 / 回归 / 准确率看板（前端源码无相关文案）；离线评测素材散在 docs/fixtures/answer-quality/、docs/fixtures/wren-native/，验收靠 70+ 份人工报告。语义模型有 draft / published / compare 与 draft/revert、draft/discard，但没有「回滚到历史已发布版本」的用户入口，published 只能只读查看。
对标
Databricks Genie Benchmarks 用固定测试问题集测准确率（含 Agent mode）、Trusted assets / verified queries；Snowflake 返回 verified_query_used 含确认人与时间；回归是发布门禁。运营指标看的是有效回答率、歧义主动拦截率、用户继续追问率、高频失败问题，不是 DAU 和提问数。
建议
「发布前体检」：发布 MDL 前自动跑一遍已确认问答（现成的 golden set），明确显示「本次改动影响 12 个已确认问题，2 个结果发生变化，是否预期」，未通过则阻断发布；再补一个一键回滚到 vN-1。中期加轻量质量看板，并把「委派深度」纳入监测——用户开始只问「这表有几行」这类查表问题，说明 agent 已退化成搜索框，这是比使用量下降更早的流失信号。
断点 4 · 性价比最高

它只在我想起来打开它的时候才有用

周一早上老板问「上周华东怎么掉了」，用户才知道要来问一次。产品从没主动找过他。
现状
主导航「例行任务」整页占位，明写「当前版本暂不支持创建和执行例行任务」（ScheduledTasksPage.tsx:8,16）。但 ScheduledTaskController 是完整 CRUD，VO 已含 email / 频率 / 生效日 / runCount；OutboundController、WebhookCallbackController、通道 API 都在，只缺执行器与前端。无订阅、无预警、无推送。
对标
ThoughtSpot 的 KPI 监控 + 异常检测 + 条件触发（「only sends when the data warrants it」，避免变成骚扰）；FineBI Next 日报周报定时推钉钉 / 企微 / 飞书、按角色分发；Tableau Pulse 摘要 digest；场景 Agent 按周主动做经营体检并下钻归因。
建议
把「例行任务」从占位改成「指标守望」，定位别做成「定时重跑一句话」：选指标 → 设关注条件（异常波动 / 超阈值 / 数据未更新）→ 结果送钉钉 / 企微 / Webhook → 只有条件成立才推送，且推送里带一句归因与「点进去继续问」的深链。这一条几乎把现有后端件全部用上，却直接命中「agent washing 检验标准」，是让产品从「工具」变成「同事」的分水岭。
断点 5

我拿到了一个数，但没法拿去开会

答案很好，想发给同事看，只能截图。同事想追问一句，得自己重新建库、重新问。
现状
可下载 CSV、复制答案、看图、预览 Python 产物；但无会话 / 回答分享链接、无评论讨论、无导出成汇报材料。后端反而已有 AgentAclService / AgentShareGrant / AgentShareEntity 与 GRANT_SHARE 审计事件，前端只用到「知识库成员与权限」；精确搜索「分享 / 协作 / 共享链接」无功能命中。
对标
ThoughtSpot Connected Slides 把 Liveboard 推进汇报材料、从已验证答案直接开一段 Spotter 对话；Slack / Teams 里渲染可交互卡片；一句被反复引用的产品判断是「让数据在协同流程里找人」，而不是「人在系统里找数据」。
建议
答案级「分享」：生成带权限约束的只读链接（复用现有 ACL 与撤权策略，需明确撤权后历史证据可见性——回答依据提案已把这条列为待决策），接收方可在同一上下文继续追问；再加「推送到群」复用 OutboundController。这是最便宜的自然获客与日活杠杆，也让一次分析变成可复用团队资产。
断点 6 · B 端一票否决项

管理员看不清，也管不住

采购方问「这个月花了多少、谁在用、答得准不准」，现场打不开一个可信的页面。
现状
UsagePage / admin/UsagePage 调用 /api/admin/usage/*，后端无对应 Controller 映射，页面本身也是孤儿路由；无 token / 成本 / 配额 / 预算告警。两套 Admin 导航并存（AdminAppShell 只被 ApprovalsPage 引用），中英混排，侧栏高亮指向未注册路径 /admin/global-administrators；ScheduledTaskController:90 有硬编码 createdBy = "当前用户"。
对标
2026 年 agent 观测的标配是 OpenTelemetry GenAI span + 成本可见性（按 agent / 按任务，不只是按 token）+ 在线评测与告警；审计要能证明「这个动作被允许、谁批准的」。评测 / 治理 / 集成三堵墙，是 92% 失败部署的真正死因。
建议
先止血：修死链与假数据（这是信任底线，比任何新功能都急）、统一 Admin 导航与语言、清掉或显式标注 25 条孤儿路由。再做成本与额度：按用户 / 知识库统计 token、耗时与查询量，超预算告警。中长期把跨会话 trace 做成可查的用户界面——现在只有单次工具检查器与单轮执行摘要。

03小，但决定手感

这些不改变能力版图，却决定用户第一周会不会回来。多数在已有提案里出现过，值得从「候选」升为「必做」。

会话标题自动命名

现在标题 = 首问截断 40 字，侧栏一串日期前缀且互相重复。顶级产品用模型生成短标题。历史会话是复用的入口，标题不可用等于历史不可用。

澄清优先于猜测

「看下收入」应当反问「毛利还是净额？」，而不是编一个看起来对的数。Snowflake 把意图分类放在生成链最前面；歧义主动拦截率是核心运营指标。

失败要有路由出口

不是「重试」，而是给具体下一步：改问题再问 / 换知识库 / 交给人工，并保留已完成的部分状态。检测停滞、说出原因、给出出口，是 agent UX 的基本功。

数据新鲜度与版本

每个答案标「数据截至 X · 已发布 vN」。20261105 提案已如实记录：当前查询时的发布版本与源数据更新时间并未随回执记录，原型只能显示「未知」。这是信任的最小必补项。

速度感

显示真实阶段与已耗时、支持「后台跑完通知我」。Microsoft 2026 年把 Data Agent 端到端响应压了 50% 才让对话「感觉快」。排队提示有了，但用户没有预期，也没有离开的余地。

零 / 单库约束

每轮只能选一个知识库，跨库问题直接不可答；对标 Genie One 已可跨 space 并结合 SharePoint / Drive。属架构级，列中长期，但要在产品里诚实说明边界，别让用户以为是 agent 不够聪明。

04优先级：先接回来，再补信任，最后拉开差距

按「用户价值 × 现有基础」排，而不是按功能大小排。刻意把「复用已有后端」放在最前，因为它性价比最高。

优先级动作为什么现在做现有基础
P0 接线「我的 Agent」：学到的 / 教一句 / 能力市场把 README 的核心承诺变成可触摸的产品；不写新后端，直接决定用户是否觉得这是「agent 产品」而非 ChatBI。OverlayFS、贡献审批、技能面板全部就绪
P0 接线「例行任务」→「指标守望」唯一能让产品「不问也给」的入口；后端 CRUD + 出站 + 通道都在，缺执行器与前端页。ScheduledTask / Outbound / Webhook
P0 止血修死链与假数据：用量端点、Admin 导航、25 条孤儿路由、硬编码采购与管理员的信任底线；假数据被发现的代价远大于补齐它的成本。页面已在，端点缺失
P1 信任反馈闭环：点踩带原因 → 待复核口径 → 发布 → 回会话提示用户纠正一次、下次不重犯，是「越用越顺手」的最小可验证形态。问答对 / 确认流 / 发布路径
P1 信任发布前体检 + 一键回滚已确认问答就是现成 golden set；阻断「自信地答错」，也让管理员敢放开使用。问题集 / draft-published 双态
P1 信任查看依据（按 20261105 提案落地） + 数据新鲜度已有完整设计与原型，缺的是服务端证据契约；建议与体检合并为一个「可信」里程碑。回执解析 / CSV / 引用面板 / 原型
P1 分发答案级分享与推送把一次性回答变成团队资产，最低成本的日活与自然传播。AgentAclService / ShareGrant / Outbound
P2 运营质量与成本看板：有效回答率、追问率、委派深度、按任务成本让团队有办法「持续运营」而不是靠人工验收报告；也是 P1 各闭环的效果度量。UsageEvent / ActivityEvent / 审计日志
P2 体验03 节六项：自动命名、澄清、失败出口、新鲜度、速度感、边界说明第一周留存的关键，单项成本低，可随各里程碑顺手带出。多数已有候选方案
P3 架构跨库问答、IM 内直接问数、跨会话 trace 产品化、本体价值高但改动大，建议等 P0/P1 跑出使用数据后再定，避免凭想象排期。部分后端能力存在
明确不建议现在做的。 ① 知识图谱（AGENTS.md 已注明链路停用，Controller 与 6 个 Entity 建议清理而非复活）；② 本体 / OntologyChatPage（孤儿页，且与 Wren-only 主线不一致）；③ 再做一份新的仪表盘原型（docs/design/ 已有 2 份）；④ 继续打磨 iOS 质感稿（已有 5 份，视觉已不是当前瓶颈）；⑤ 为了「看起来像 agent」而堆多智能体编排——subagents-enabled=false 的现状下，先把单 agent 的成长闭环做出来更有说服力。

05别用功能数量验收，用这三个问题

建议写进下一轮 spec 的验收条件，每个都能被真实使用数据回答。

  • 1
    第三周来，能不能感觉到它比第一周更懂自己？ 看得见学会了什么、能教、能撤、教完下次真的生效。这是「复利」，也是 README 那句「越用越顺手」唯一诚实的验收方式。
  • 2
    老板在会上问「这数准吗」，用户能不能在 10 秒内给出可复核的答案？ 口径、SQL / 条件、结果、数据截至时间、发布版本，一屏之内。做不到，再准也不敢进业务流程。
  • 3
    用户一周没打开，产品有没有主动给过他一次有价值的东西？ 一次异常提醒、一份条件触发的周报，就足以把「工具」变成「同事」。
快手周人均 55 次对话、NPS 73.5，不是靠界面好看，是靠两件事：同类问题第二次不用从头开始，以及它会在我需要之前找我。我们后端已经把最难的地基（语义层、私有 workspace、贡献审批、沙箱、HITL、事件流）都打好了——现在缺的，是让用户看得见、摸得着、并因此愿意把活交给它。
