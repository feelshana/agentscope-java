让每一次使用值得，也让每一次使用留下东西

另一份报告的主线是「一次使用是否值得」：知道怎么问、相信回答、方便追问、成果能用。我上一份的主线是「一个产品是否会自己长大」：能力触达、复利闭环、质量门禁。这两者不是竞争关系，而是同一个漏斗的上下游——前者决定用户会不会用第二次，后者决定用户会不会用第二个月。合并后的正确顺序不是「先做体验再加结构」，而是用第一批把证据地基一次做对，然后体验与结构并行生长。

评审对象：本仓 20261112 评审稿 + 用户提供的第二份分析 方法：逐条事实核对（源码）+ 归并去重 + 依赖排序 状态：决策讨论稿

01两份报告其实在回答两个不同的问题

先认清这一点，才不会把它们拼成一张 17 条的功能清单。

维度第二份报告（体验视角）我上一份（结构视角）
核心提问用户这一次用得顺不顺、敢不敢信？用户用了三周，产品有没有变得更强？
时间尺度分钟（单轮问答）周 / 月（跨会话积累）
落点回答旁的说明、结果布局、追问建议、失败恢复能力入口、资产沉淀、发布门禁、主动触达
最大贡献把「信任」拆成了可执行的一行说明与一次追问发现 25+ 能力已有的路由用户完全摸不到
最大盲区没回答「为什么下次还要来」，只回答了「这次别走」没回答「第一次用就拿到一个不敢信的数，结构再好也没用」
失效方式好用但没有护城河：每次都从头开始，换个工具无痛有愿景但首次流失：数字不可复核，用户回去写 SQL
所以「综合」不是取并集，而是排序。 体验层是漏斗最窄处，必须先过；结构层是留存曲线，决定天花板。而两者共用一个地基——可复核的证据。谁先建这个地基，谁的后续工作才不返工。

02我同意、并且要进一步加强的七点

这些是第二份报告真正的高价值判断。每条补一句它没说透的实现风险。

1 · 一行「数据与口径说明」，是全篇最高性价比的一条

它用最低的界面成本，解决了业务用户最不敢问出口的问题：这数能拿去汇报吗。而且它把「信任」从抽象态度变成了可检查的四个事实：时间范围、口径、数据截止、是否扣退款。

但它不是轻功能。要让这行字是真的，需要服务端证据契约：evidenceId、实际执行的发布版本、源数据更新时间、结果是否截断、NULL 是否保留。20261105 提案已核对：当前回执不记录发布版本与源数据更新时间，CSV 把 NULL 写成空单元格。所以这行字背后是后端改造，必须第一批一次做对，否则第二、三批全部返工。

2 · 明确区分「本次查询时间」与「源数据更新至何时」

这是最容易被产品忽略、也最容易被业务方抓住的坑。11 月 7 日跑出的「上周数据」，如果源表只同步到 11 月 6 日，结论就是错的——但界面看起来完全正常。Genie、Cortex Analyst 都把「数据新鲜度」当作答案的一等属性。

无法确认时必须显示「未知」，不能猜测。这与 20261105 提案的「不用虚构状态换好看」原则一致，也是最省事的诚实。

3 · 追问建议要「与当前结果直接相关」，而不只是「能做归因」

方向完全正确，而且我们已经有比想象中更好的基础：analysisSuggestions.ts 不是让模型自由发挥，而是规则判断当前结果能不能做归因 / 异常 / 预测（归因需数值指标 + ≥2 个时间点；异常需日/小时粒度 ≥7 点；预测需 14 天、8 周或 12 月）。这套「能力可用性判断」正是生成具体问法的前提。

正确做法不是新写一套推荐逻辑，而是把现有的「能不能做」升级成「做哪个」，并复用同一套判定：能拆维度就出「按渠道拆开」，有可比周期就出「和上周比」。建议与能力判断同源，才不会推荐一个数据支撑不了的问法。

4 · 「保存结果」与「保存分析」分开——全篇最聪明的一个区分

它把两种完全不同的资产说清楚了：证据快照（保留当时的数字、图、口径，用于汇报与追溯）与查询模板（保留问题与条件，下次换日期重跑）。这两者的存储、失效策略、权限、刷新语义都不同，混成一个「收藏」会在半年后爆炸。

快照会撞上一个尚未决策的问题：知识库撤权后，历史快照还能不能看。20261105 提案已把它列为待定策略。这个必须先定，否则快照功能上线即埋雷。

5 · 答案布局统一为「结论 → 图 → 明细 → 口径 → 操作」

这条的价值被低估了：它不只是一个页面排版，而是全产品的答案模板。聊天、例行任务结果、分享页、简报，只要都用同一个模板，用户在任何入口看到的答案结构都一样，认知成本立刻下降。

模板要一次定义、处处引用，不能各页面各写一套。建议落成组件而不是设计稿约定——否则三个月后必然分叉。

6 · 失败要给具体下一步，而不是「重试」

「查询已完成，图表生成失败 → 查看数据 / 重新生成图表」这种恢复路径，比一句「出错了请重试」高一个量级。我们已经有了 EChartsBlock 的错误恢复和工具结果下载，只是没有统一成一套恢复语汇。

长任务展示进度时，只显示能证实的事实（「查询完成，正在分析渠道贡献」），不显示百分比。第二份报告这点说得很对，值得写成硬约束。

7 · 用 30-50 个真实高频问题验证，而不是靠感觉验收

这是把「产品好不好」变成「可测量」的关键一步，也是两家顶级产品都在做的事（Genie Benchmarks 用固定问题集测准确率，含 Agent mode）。

我要把它再推一步：这批问题不该只做「观察样本」，应当直接成为发布门禁的 golden set。同一个资产两种用途——平时看健康度，发布时阻断回归。这才是「持续观察」和「质量门禁」的差别：观察是事后发现，门禁是事前拦截。

03我要修正与补充的五点

这些不是挑错，而是会直接影响排期与预期的地方。

修正 1 · 「我们已经能生成报告和文件」不成立

能下载查询结果 CSV、能保留 Python 产物，但没有报告模板生成器，report-writer 子代理默认未启用（subagents-enabled=false）。所以第 5 点「成果整理」不是「把分散入口整理清楚」，而是从 0 到 1 造一个简报编辑器：选择结论与图表 → 编排顺序 → 改标题文案 → 导出/分享 → 数字保留来源链接。工作量要按新功能估，别按「整理」估。

补充 1 · 缺「结构触达」这一整层

第二份报告完全没有提：25+ 已注册路由没有任何入口——技能、子代理、私有工作区、能力市场提交与审批、通道、用量、用户资料。而这恰恰是「下次还想来」最强的理由：用户记住的不该是「我保存过一个查询」，而是「我的 agent 记住了我」。只做常用分析，产品仍然是一个更顺手的查询工具；接回能力目录，产品才成为会长的 agent。

补充 2 · 缺「发布后的质量门禁」

第二份报告只有「持续观察」，没有「阻断」。差别很关键：语义层一改，可能批量打断已经答对的问题，这是 ChatBI 最常见的翻车方式，而且是静默的——没人报错，只是数字悄悄变了。所以必须在发布前跑一遍已确认问答，明确提示「本次改动影响 12 个已确认问题，2 个结果变化」，并支持一键回滚 vN-1（现在 published 只能只读查看，没有回滚入口）。

补充 3 · 缺「止血」这一批

这不是功能，是信任负债：用量页调用 /api/admin/usage/* 但后端无对应 Controller（页面本身是假数据）；侧栏高亮指向未注册路径 /admin/global-administrators；两套 Admin 导航并存；中英混排；ScheduledTaskController 里 createdBy 硬编码。用户一旦发现「这个页面是编的」，前面所有口径说明都会被怀疑。成本极低、收益极高，必须排在一切之前。

补充 4 · 反馈闭环缺一个关键分流：分析类回答目前不进沉淀

核对 AnswerFeedback.tsx:33 与 spec102：分析类回答的反馈只记录，不保存为问答样例。但分析类回答往往价值最高（归因、异常、预测的结论）。建议按反馈类型分流：口径类修正进语义模型，分析路径类进技能/记忆，展示类问题进模板改进。否则「越用越准」只覆盖了简单查数。

04整合框架：三层，三种时间尺度，一条地基

把两份报告的能力放进同一个结构里，并且明确依赖方向——这是本次评审最主要的产出。

L1 · 分钟
一次问答：可信且顺畅
决定会不会用第二次
证据契约（evidenceId / 发布版本 / 数据截止 / 截断 / NULL）· 一行口径说明 · 答案模板（结论→图→明细→口径→操作）· 上下文追问 · 失败恢复
L2 · 周
资产化：做过的事能复用、能交付
决定效率与口碑
我的工作台（常用分析 / 保存结果 / 保存分析 / 历史搜索与置顶）· 简报整理与导出 · 分享（快照 vs 可重跑，分别守权限）· 反馈原因分类
L3 · 月
复利与在场：它会自己变强，也会主动找你
决定天花板
例行任务执行器 + 「设为例行任务」入口 · 条件触发推送 · 发布前体检与回滚 · 我的 Agent（记忆 / 技能 / 能力市场）
依赖方向不能倒。 没有 L1 的 evidenceId，L2 的「保存结果」保存的只是一张不可复核的截图；没有 L2 保存的分析，L3 的「设为例行任务」没有对象可指；没有 L2 的已确认问答沉淀，L3 的「体检」没有 golden set。结论：L1 必须一次做对（它的成本是后两层的利息），L2 与 L3 可以并行推进。

05批次与取舍

融合两份排序：把第二份的「体验优先」接在我的「止血」之后，结构层不再等到最后。

0
止血（不可协商）　修假数据与死链、统一 Admin 导航与语言、孤儿路由显式标注或临时入口、清硬编码。理由：信任负债利息最高，且这部分几乎不占工程资源。唯一例外：能力市场的「发现 / 安装」可顺手接线，纯前端、独立于资产模型，是低成本高感知的窗口。
1
L1 可信的一次问答　证据契约 → 一行口径说明 → 答案模板 → 上下文追问 → 失败恢复。第二份报告排序正确：这是漏斗最窄处。要点是证据契约一次做对，别先做界面再补后端。
2
L2 资产化　我的工作台（合并入口）+ 保存结果 / 保存分析 + 历史搜索与置顶 + 简报导出 + 分享 + 反馈原因分类。先定「撤权后快照可见性」策略，再动工。
3
L3 复利与在场　例行任务执行器 + 设为例行任务 + 条件触发推送 + 发布前体检与回滚 + 我的 Agent（记忆 / 技能 / 市场）。例行任务要靠执行器兑现，不能只接前端；推送要「条件成立才发」，否则变成骚扰。
与两份原始排序的差异，以及为什么。 ① 我加了第 0 批止血——两份都漏了，但它是信任前提；② 我不同意把「我的 Agent / 能力市场」放到最后——它是差异化与留存锚点，且「发现 / 安装」零成本，应当提前；③ 我同意把「口径说明」放第一批第一位——但要明确它是后端契约工作，不是文案工作。

06两份报告唯一的实质分歧：入口该加几个

第二份说「首页保留现有布局，加一个轻量的常用分析入口」；我说「加一个我的 Agent 一级入口」。两边都对，但两边各加一个就会变成入口堆砌。

正确的是合并成一个「我的工作台」，内部三栏：

分栏放什么解决什么
我的分析历史会话（可搜索 / 重命名 / 置顶）、常用分析、保存的结果快照「我经常要看什么」+ 找回成本
我的 Agent学到的记忆与技能（标来源、可编辑、可停用、可删除）、子代理、教它一句自进化的可见与可撤销
能力市场共享能力浏览与安装、我的提名、审批状态经验自下而上流动

这样做有三个额外好处：把 25+ 孤儿路由收进一个有名字的地方；建立统一的「资产」心智（分析、结果、技能本质都是我的资产）；避免首页每来一个需求就加一个卡片。这是两份报告整合后我认为最重要的一条产品结构建议。

07度量：把「持续观察」升级为「门禁 + 健康度」

第二份报告提了 30-50 个真实问题，我建议把它们分成两种用途，配两套指标。

门禁指标（发布时阻断）

golden set 通过率、同一问题跨入口（聊天 / 例行任务 / 分享页）答案一致性。语义层、模型、模板任一变更即重跑，不通过不许发布。

健康指标（日常观察）

首问成功率、有效回答率、澄清触发率、追问率、委派深度、结果复用率（收藏 / 导出 / 分享）、反馈闭环率、例行任务存活率。

首问成功率值得当成最重要的单一指标——它同时受推荐问题、澄清、口径说明、答案布局四处影响，是新用户去留的总开关。委派深度是最早的流失预警：当用户开始只问「这表有几行」这类查表问题，说明 agent 已经退化成搜索框，这比使用量下降来得更早。
