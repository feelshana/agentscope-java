# 合并后全链路验收报告（2026-10-16）

**结论：主流程可以运行，但本轮未全部通过，暂不建议直接作为生产上线验收通过。** 已确认三类功能缺陷：原生图表跨用户读取、完播率业务口径错误、外联数据库断线后旧 Wren 实例不能自动恢复。另外存在明显的多实例内存容量风险，以及 Windows 发布快照切换偶发失败。

本轮只测试并记录问题，没有修改业务实现、合并分支或提交代码。此前工作区内的 MANAGE 修复、来源回归与发布工具改动均保留。以下为本轮真实服务结果；上一阶段 625 项单元/集成回归不充当本轮效果验收。

## 3. 需要优先处理的问题

### P1：原生 ECharts 图表缺少资源归属校验

真实调用 `render_chart` 创建图表后：创建者读取 `/api/charts/{id}` 返回 200；无该库权限的另一登录用户读取相同 ID 也返回 200，内容完全相同；未登录者返回 401。图表 option 内含业务数据，不能仅靠 ID 不易猜测保护。

代码核对：`DataAgentToolkit#renderChart` 保存 `ChartOptionEntity`，实体没有 owner；`ChartController#get` 按 ID 读取，没有当前用户和资源归属检查。全局登录认证不能代替该项授权。此问题与已经通过的 `/api/artifacts/.../content` 私有 PNG/CSV 检查属于不同路径。

**建议**：创建时从真实 RuntimeContext 取得操作者并持久化 owner；读取时执行 owner 校验。无归属的历史记录应拒绝访问或按可证明的会话归属回填，不能默认对所有登录用户开放。回归覆盖本人、无关用户、共享 QUERY/MANAGE 用户、全局管理员及旧记录，保持图表/会话私有边界。

证据：[跨用户读取结果](../../../.runtime/acceptance/native-chart-isolation.json)。复现使用本轮自有测试账号和图表，没有读取第三方实际业务资源。

### P1：业务文档定义的完播率被替换成标志字段

| 指标 | 文档规则下的独立真值 | 常规问法返回 |
|---|---:|---:|
| 音乐整体完播率 | `play_duration >= duration_seconds × 80%`：34.37% | `is_complete`：60.24% |
| 视频整体完播率 | 播放时长达到视频时长 90%：26.295% | `is_complete`：40.05% |

这些不是四舍五入误差。建模将两个业务阈值映射到随机生成且不等价的标志列，官方语法校验、编译和查询均可成功，错误口径还被保存到 memory；问数复用 Cube/样例后继续得到同一个错误结果。两个路径一致不能证明它们符合业务规则。

进一步明确要求音乐场景逐行按 80% 时长重算、不要复用标志字段或旧 Cube，实际返回 3,437/10,000 = **34.37%**，说明官方查询链路可以计算正确；缺陷集中在语义定义、验收和错误资产复用。

**建议**：先修复这两个工程的模型/Cube/knowledge 和错误 memory，再用独立阈值 SQL 对照；对这类派生指标保留业务公式及样本验收。只将用于正确最终答案且经确认的查询作为正样例。仍使用官方 Wren 契约和工具，不引入平台 SQL 回退、改写官方技能或自行重做查询路由。

证据：[音乐失败回合](../../../.runtime/acceptance/events/question-02-semantic.json)、[视频失败回合](../../../.runtime/acceptance/events/question-03-semantic.json)、[显式重算及财务预算诊断](../../../.runtime/acceptance/extra-numerical-cases.json)。这两项诊断均通过，单独记录，不覆盖原始失败。

### P1：外联恢复后，Wren 旧连接仍不可用

用本轮独立 TCP 代理制造断线，未停止用户的 SSH。断线前 `products` 为 100 条；断线后连接检查为 false，问数明确报告失败，没有伪造成功。恢复代理后，新 PyMySQL 连接可查 100 条、应用连接检查为 true，但旧 Wren MCP 查询继续报 MySQL 2006/2013 类连接错误。重新发布使 MCP 实例失效并重建后，同题恢复为 100。两轮测试均观察到此类问题。

**建议**：先确认官方 Wren 的数据库连接重连能力；平台对明确的连接失效类结果可受控使实例失效，并在只读、安全、重新鉴权的条件下做有界重建/重试。不能对语法、权限和所有业务错误一概重试，更不能改走物理 SQL 回退。回归应覆盖断线、恢复、并发等待者及撤权，避免重复执行。

代码入口：`WrenInstanceRegistry#doCall` 与 `invalidate`。当前按 MCP 传输失败淘汰实例，但数据库连接错误可能是 MCP 正常响应中的失败结果，仍复用失效引擎。

证据：[第二轮确认与恢复结果](../../../.runtime/acceptance/network-fault-confirmation.json)。其中 `recovered=false`、`recoveredAfterInstanceRebuild=true`，不能将人工重建成功写成自动恢复通过。

### 上线容量风险：ONNX 记忆实例的常驻内存较大

记忆召回后的 Wren Python 进程，多数工作集约 **944–952 MiB/实例**。本轮子进程工作集总和峰值 **9,193 MiB**，JVM 工作集峰值约 **830 MiB**。整机还有 IDE、Docker 等既有负载，约 31.73 GiB 机器的可用内存采样最低到 **41.3 MiB**；不能把整机压力全部归因于本应用，但这足以说明不能直接把默认 16 实例视为安全容量。

为继续验收，测试者曾显式重新发布已完成的库，触发 MCP 失效回收，释放内存。报告不把这次人工干预记为自动闲置回收，也不把多个实例的高内存直接判为泄漏。工作集相加可能重复计算共享页，仍应结合整机可用量做部署预算。

**建议**：按目标机可用内存实测设置 `dataagent.wren.max-instances`，先从较小的 2–4 实例预算开始压测，配合 `instance-idle-seconds` 和排队策略；该数字只是下一轮起点。核实官方 ONNX 运行时的线程/模型内存选项，测试建模 CLI 与 MCP 同时运行的总进程预算。不要只调整 JVM Xmx，因为主要压力在 Python 进程。

证据：[资源汇总](../../../.runtime/acceptance/resource-summary.json)、[显式释放记录](../../../.runtime/acceptance/resource-pressure-release.json)。没有在本轮擅自修改运行默认配置。

### P2：Windows 发布快照目录切换偶发失败

48 次有效文件上传中，06 游戏行为、08 员工两次返回 HTTP 500，业务码 `IMPORTED_MODEL_PENDING`，错误位于 `published.next -> published` 目录切换。数据与元数据已经保存，后续上传/重建恢复了完整模型，最终发布成功且行数正确。

**建议**：围绕 `MdlPublishService` 的快照切换及 `Files.move` 保留错误类型、检查占用与并发时序，在旧快照可用、数据已保存的前提下设计有界恢复和明确的“重建模型”入口；对 Windows 增加重复上传/发布压力复现。当前尚未证明具体是何种文件占用或杀毒行为，不能写成已定位根因。

证据：`scenario-06.json`、`scenario-08.json` 中对应失败响应。本轮最早四次中文 uploadId 的 400 是测试脚本参数错误，修正 UUID 后重测；它们不计入上述 48 次产品上传统计。

## 5. 速度、并发、取消与资源回收

### 延迟

83 个有效数值问题的端到端耗时：**最小 7.80 秒，中位数 11.25 秒，P95 26.99 秒，最大 36.26 秒**。该批测试与部分建模、记忆实例加载等混合运行，不能当作完全隔离的单请求基准。坏数据诊断复杂回合另有约 74 秒，预测回合约 45 秒，均不在上述有效数值统计中。

另外对简单 COUNT 做控制测量：重新发布后新 MCP/新会话约 8.58 秒；热 MCP/新会话约 6.88 秒；同会话重复约 4.28–4.69 秒。所谓“冷”只指该 MCP/会话，并非全机、模型文件缓存和 ONNX 全部冷启动。首 token 包含过程说明，不能视为首个有效答案时间。热新会话曾猜错英文表名并自纠正，也说明延迟会受到 Agent 工具选择影响。

建模按同一工程各次对话用时相加，约 **104–257 秒/库**；电商约 246 秒，其中包含澄清与后续继续完成。自动处理真实文件授权卡，未计人工等待和批次之间停顿；不能承诺用户手动审批也在同样时间内完成。

### 准入与取消

- 33 个不同用户同时发起真实模型简短对话：32 完成、1 被容量拒绝；观察到运行峰值 16、等待峰值 16；最长约 29.57 秒。
- 同一用户同时 20 请求：2 运行、1 等待，最终 3 完成、17 拒绝；最长约 8.65 秒。所有接收的请求均完成，没有把拒绝算成成功。
- 此项负载是无选库短对话，用于核对聊天预算，**不能证明支持 16 路复杂 Wren/ONNX 问数**。同库 Wren 门锁、跨库实例、建模 CLI 和外部数据库连接池的联合容量仍需专项压测。
- 真正启动沙箱 Python，观察 ready 文件后断开 SSE；等待超过其后续写入时间，late 文件未出现；同会话下一轮 3.398 秒恢复。此项验证了执行中取消，不只是取消尚未开始的任务。
- 默认空闲阈值及轮询后观察到 16 次沙箱闲置驱逐，只有最近活动用户容器保留；与显式 MCP 发布失效回收分开记录。

### 内存观察的实际边界

约 67.7 分钟、792 个资源采样点。业务操作后，再做三轮各 500 次、8 并发的知识库列表请求，每轮后显式 GC：堆使用约 81,479 → 81,650 → 81,613 → 83,119 KiB；最后收尾 GC 约 84,031 KiB。后三轮工作集约 712 MiB，线程/句柄未持续单调增长，未观察该请求路径的线性泄漏。此 GET 压力的 P95 约 23–29 ms，与 LLM 问答耗时没有可比性。

这不是 24 小时/多天稳态证明，也未证明所有异步、发布、长期海量会话路径都无泄漏。最显著的已测风险是前述多 Wren ONNX 进程内存，而非 Java 堆持续膨胀。

证据：[独立延迟样本](../../../.runtime/acceptance/latency-results.json)、[全局负载](../../../.runtime/acceptance/load-global33.json)、[单用户负载](../../../.runtime/acceptance/load-same-user20.json)、[取消](../../../.runtime/acceptance/cancellation-results.json)、[GC 观察](../../../.runtime/acceptance/memory-probe.json)、[闲置驱逐](../../../.runtime/acceptance/idle-sandbox-recovery.json)。

## 6. 测试数据质量与外联范围

原财务 8,000 行报销的 `category/amount/status/invoice_type`、生成 IT 5,000 行工单的 `category/priority/status/satisfaction` 都存在每单元格为数组字符串的生成器问题。这会使“已付款金额”“工单状态”等筛选失去正常业务含义，不能把 SQL 得到 NULL/0 就当成正确业务值。独立修复对照确保正常标量输入也走过财务、IT 完整链路。财务额外预算执行率为 **70.01%**，分子、分母分别预聚合后计算，未因多对多连接重复累计。

云 MySQL、Doris 均通过用户现有 SSH 隧道访问，只用只读账号。最终复查两边 customers/products/orders/order_items 仍为 200/100/1,500/4,339。Doris 本次只验证已配置测试集的 MySQL 协议接入与这些查询；协议 `SELECT VERSION()` 返回值不作为实际 Doris 产品版本，不能扩大为所有 Doris 版本/方言/规模均已兼容。

证据：[源质量问题](../../../.runtime/acceptance/source-data-quality.json)、[云正常链路](../../../.runtime/acceptance/external-results.json)、[云题集](../../../.runtime/acceptance/cloud-benchmark.json)。
