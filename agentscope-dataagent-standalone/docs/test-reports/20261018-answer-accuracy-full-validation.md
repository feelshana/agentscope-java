# 问数准确性专项实测：215次问答与错误归因

日期：2026-10-18。基于当前工作区的实际可执行包、10.17隔离测试资产和`test_data`，通过真实HTTP/SSE调用问数助手。用户授权补充测试与分析；本轮没有修改问答代码、官方技能、业务模型或发布版本，没有自动提交。

## 一、结论

**以前77道固定题不足以证明产品准确性。本轮也不能得出“准确率100%”。**

215次由198次主评估和17次诊断补题组成。主评估中，192次数值题可以明确评分，另有5次合理拒答/范围行为题、1次题意有歧义而排除。重复问、共享账号重问、历史题回归均按“尝试”记录，不能称215道独立盲题。

| 统计口径 | 本次结果 | 含义及限制 |
|---|---:|---|
| 数值题：关键指标与核心统计口径都通过 | 179/192，**93.23%** | 包含7次源不可达、1次模型连接失败；是本题集首次尝试成功率，不是生产总体正确率 |
| 仅限源和模型可用的数值题 | 179/184，**97.28%** | 仍有4次复购过滤未遵从、1次月度去重粒度不符；4次复购来自同一问题族，不是4类根因 |
| 若只核对关键数值是否相等 | 183/184，99.46% | 会误放过上述4次碰巧一致，因此不采用它作为业务准确率 |
| 合理拒答/零选库行为首次完成 | 4/5 | 1次模型连接超时；拒绝凭坏数据猜金额属于正确行为 |
| 澄清题 | 2/2 | 月度唯一人数、包含非在职的部门人数；不覆盖首次失误 |
| 指定Cube的日期边界诊断 | 6/6 | 电商/彩铃/阅读各2次，均使用下月1日排他上界；历史漏末日问题本次未复现，不等于所有日期问法已根治 |
| 故障恢复重问 | 8/9 | 1次Doris商品数题在查询前遇到模型5分钟超时；不能说所有恢复题通过 |

这里的“通过”限定**用户要求的关键指标、核心过滤、分母、粒度及查询证据**。附加解释、因果归因、文字排序、每一句业务断言没有全部建立金标，已发现反例，**完整答案事实准确率仍未知**。不能将179次通过理解成179篇答案完全无误。

非故障主评估189次的整轮耗时：p50 **11.914秒**、p95 **26.589秒**、最长 **41.470秒**。故障题没有被删掉，而是单列；这些耗时不含故障题、不是首字延迟，也不是10用户并发或生产SLA。

- 复用10.17隔离元数据库/上传库、已发布11个本地场景，以及云MySQL和Doris只读源。不是重新上传、从零自动建模；既有资产在10.17经过正常建模对话及HITL纠正。
- 本轮重新读取46个XLSX、202293行建立独立SQLite参考库；保留文本ID前导零，数值和日期按源类型读取。没有用Wren答案反推金标。
- 新问题的参考SQL/答案只保存在测试侧，不发给待测模型、不写入示例或发布资产。模型仍能访问既有业务规则和已核验基线，所以新题只是未提前写入资产的测试题，不是严格独立、无历史知识污染的学术盲测。
- 实际调用`/api/agents/data-agent/chat/stream`，保存token、工具输入、工具回执、error和done；普通题使用新会话，3组追问共6次保留上下文。两工作线程按知识库分组执行，不是负载测试。
- 运行日志确认本次活动模型是OpenAI兼容客户端、配置模型名`deepseek-flash`；另一个配置中的模型不是本次活动模型。供应商别名对应的实际权重未独立核验，没有做多模型受控A/B。
- 使用当前安装版Wren 0.15.0官方MCP/CLI/skills、ONNX/LanceDB链路；参考查询不经过它，产品查询仍只经Wren，无物理SQL回退。
- 自动匹配仅产生候选：对非直接匹配逐题复核等价、单位、派生计算和空集；结合查询及最终回答核对核心口径。对重复/复购/时间/共享/多库等重点题再查实际过滤和粒度，单独记录附加文字错误。没有把HTTP200、工具执行成功或“答案中出现数字”当作通过。
- 允许合理等价：SQL返回分子分母、回答正确计算比例；秒/万元/百分比正确换算；空分组结果对应记录数0；两次查询正确合并名单。仍须有相应查询证据。
- 前后哈希核对：**46份源XLSX未变；13个工程published/workspace共863文件内容、文件集合均未变**。不点赞注入新例子，不改模型纠错后覆盖首次成绩。

## 三、业务错误：数字对不代表口径对

### 1. 复购过滤被知识库默认口径覆盖：4次，属于同一问题族

用例`base-01-repeat`、两次repeat及`shared-base-01-repeat`明确要求排除已取消订单、至少2笔不同订单、分母为客户表全部客户。实际回答沿用全量订单次数的Cube/规则；其中一次SQL只保证“有一笔有效订单”，没有保证“至少两笔有效订单”。分母也有沿订单表客户去重、却标成全部客户表的情况。

当前数据恰好使两种算法都是199/200=99.5%；独立参考SQL再次核对，两种分子均199。因而只比较数字会通过，但改变一点数据就可能错。例如一客户1笔有效+1笔已取消，按本题不复购，全量次数算法却判复购。

现发布工程的`knowledge/rules/general.md`把全量复购及分母假设写成默认口径；模型据此压过用户的显式筛选，甚至把“需要排除取消可再算”当作可选追问。原始业务文档与生成规则并非完全等价。

**归因：语义资产/规则质量，加上问答模型的意图与冲突处理。** Wren执行的正是所给Cube/SQL，没有看到引擎把正确过滤算错的证据。不是当前用户角色不同导致，owner与reader均出现。

反证也保留：3道新月度复购/分母题通过；1月有效复购37人，除全部200人为18.50%，除当月有效下单112人为33.04%，1/2月有效下单交集55人。说明不是所有复购都不能算，而是部分问法被既有规则/例子带偏。

### 2. 月度唯一人数答成每日人数：1次

`new-08-date-feb`询问2025年2月整月考勤去重员工数，包含全部状态。应对整月`emp_id`一次去重得到**492**。

模型执行每日去重、返回28天结果及相加的**1961人次**，说明月度唯一人数需要另一次查询，但没有完成它。本题未把1961明确冒充月度唯一人数，仍属于没有回答用户所需指标，不能算通过。

单独澄清“整个2月只去重一次，不按天不相加”后返回492。**归因：问法理解、统计粒度和回答完成度检查。** 不是数据库对DISTINCT做错计算；澄清成功不覆盖首次失败。

### 3. 金标本身也可能不严谨：1次排除

`new-08-dept-count`预期包含所有500名员工，但题目没有明确包括非在职，库内默认员工数是462名在职员工；模型明确标注采用在职口径。不能因其与测试预设不同就判产品错误。

该题从准确率分母排除。澄清包含非在职、不筛`is_active`后20部门合计500，正确通过。金标须记录全部/在职、时间字段、分母、单位和粒度，不能仅有一个数字。

## 四、附加解释错误：主指标通过也要记录

| 用例/现象 | 核对发现 | 归因及边界 |
|---|---|---|
| `shared-new-01-channel` | 表中线上商城288单、小程序290单，却说“小程序订单最少” | 模型对自己已查询表格的总结错误；不是Wren结果错 |
| `new-08-weighted-pay-repeat1` | 两种平均工资数值正确，却说只有部门人数完全相等时两种均值才能相等 | 数学解释错误；人数不等但各部门均值相同也可相等 |
| `new-01-monthly`、`follow-0-b` | 将月份变化解释为春节/季节性、主要由天数变化造成 | 描述统计不足以建立因果；部分是可能解释，但措辞过于确定 |
| `new-04-setting-denominator` | 两类去重数2885/2821相差64，不能据此推出只有64人设置但未订购 | 独立集合查询为仅设置171、仅订购107，净差64；集合差与人数差不能混同 |
| 多个电商金额回答 | 断言“amount已含折扣” | 生成规则存在该断言，原始业务文档未证明；4339行均满足amount=quantity×unit_price也不能证明成交单价是否已折扣。应将已批准SUM(amount)口径与未证实的折扣生成假设分开 |
| `new-01-channel` | 数字正确，输出重排后声称按拼音升序，该拼音顺序也不成立 | 展示/指令遵循问题；不纳入本报告“核心指标口径”的数值通过率，仍须记录 |
| `base-cloudDoris-count`故障解释 | 把Windows错误码10061说成连接端口10061 | 故障原因解释不实；实际配置的本地转发端口19030。拒绝猜数正确，不代表错误诊断正确 |

这些是已确认或明确标注依据不足的实例，**不是所有附加解释的完整错误数，不能用实例数量计算整篇答案准确率**。其他答案也常出现重复读规则、过长过程描述、展示内部group_id等体验问题，本轮不据此改前端/提示。

## 五、可用性失败：保留首次结果，独立统计恢复

### 云源7次

6次MySQL、1次Doris固定题在本次SSH隧道断开后失败。现场`ssh.log`记录connection reset，13306/19030均无监听。真实回执包含连接拒绝；回答未伪造业务数值，空集题也没有把不可达说成0。

重连本轮隧道后，后续云题恢复，不重启应用。6道MySQL恢复题全部通过。Doris商品数恢复题没有执行到业务SQL，活动模型请求`PT5M`超时，所以本轮不能声称该恢复题已通过；其他Doris题有实际成功查询。本次现象不证明10.17“旧MCP恢复”P1已经修好，生命周期/场景不同。

### 模型首次2次、诊断1次

`new-08-performance-fanout`和`quality-dirty-amount`首次出现OpenAI兼容HTTP客户端连接超时，SSE有error但无正常完成；恢复重问前者得到正确7333403.61及488人，后者正确解释坏数组字符串不能算金额。

另有上述Doris恢复题5分钟模型超时。不能把这3次归为Wren的SQL错算，也不能把短暂几字的过程文本称为正常完成答案。模型请求/网络的底层原因未进一步分解，未武断断言是供应商限流。

## 六、Wren、向量、大模型与平台分别承担什么

| 层 | 本次能确认 | 不能据此断言 |
|---|---|---|
| 数据及业务文档 | 部分财务/IT列在源文件已是混合数组字符串，模型能据规则拒绝无依据计算 | 不能一律怪导入转换，也不能把合理拒答算作答错 |
| 建模资产/示例 | 规则中的复购/折扣假设会影响多个问法；历史错误示例确实被召回 | 编译/查询成功不证明业务定义正确；修一条聊天答案也不修资产 |
| 问答大模型 | 明确过滤被覆盖、月度粒度答偏、表格总结/数学解释错误，另有请求超时 | 没有A/B，无法证明换模型就能解决，也不能量化模型占全部错误的百分比 |
| Wren执行/向量召回 | 本次已核对的失败没有发现“正确SQL被错误执行”的证据；错误相关资产会被模型使用 | 不能宣称Wren无bug；向量检索相关性不等于业务真值，也未测出独立检索precision/recall或向量瓶颈占比 |
| 平台及产品机制 | 技术发布、执行回执、点赞都没有业务真值判定；范围守卫在零选库时有效 | 不能把准确性完全归责第三方；也没有证据认定上述错误由平台暗改SQL造成 |
| 环境/供应链 | 隧道断开、模型连接超时/请求超时真实发生 | 应影响端到端成功率，不与静默业务错误混算，也不能外推成生产可用性百分比 |

## 七、下一步建议：先讨论再实施

1. **先选首发关键指标，确认业务金标。** 复购/有效订单/月活/完播/收入等逐一确认粒度、排除状态、分母、单位、时间字段；把批准定义与模型推断分开。当前复购规则及折扣假设优先处理。
2. **修资产与通用冲突处理。** 用户明确临时改筛选/分母时，应按本题计算并标明与默认口径差异；真正不能混用或定义不清时澄清，不自作主张套默认。修正源规则、Cube及错误memory后显式发布/重建官方索引，不逐题硬编码，不静默改写官方SQL。
3. **补最小反例数据及答案验收。** 单客户1有效+1取消、单订单多明细、无订单客户、月内同一人多天出现、人数不等但均值相同、两集合有进有出。当前分子/分母碰巧一致掩盖错误，原数据不变不足以检出所有回归。改测试数据需隔离新建，不污染现有资产。
4. **控制回答越界。** 核对用户所需指标是否实际返回，排序/最值与表一致；事实和假设分开，非必要的因果、折扣、数学定理不靠自由发挥。优先复用现有通用提示/框架能力，具体实现范围另议。
5. **冻结后再比较模型与可用性。** 同一资产、例子、参数和题集做候选模型A/B及重复稳定性；保留首次失败，另测LLM连接与源恢复，不靠多重重试粉饰准确率。向量性能按冷索引、热召回、命中质量、LLM和SQL耗时分开测。

以上均为待确认方案，尚未改问答/建模业务实现。用户此前要求建模问题先记录，该边界继续有效。
