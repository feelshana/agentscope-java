# 合成业务数据的真实 Agent 能力验收

日期：2026-11-14，Asia/Shanghai。分支：`codex/architecture-phase1`，HEAD `bfb202b8`，包含本地尚未提交的 spec138 撤回修改。

## 结论

用户提供的测试数据足够开展第一轮验证，不需要另造数据。现有 Agent 已能完成基础汇总、多轮筛选、两期多维比较、作图与普通口径修改，下一步不应重复开发这些能力。

本次9个实际问答任务中，6个达到本轮标准，2个部分通过，1个未通过。发现两类直接影响信任和交付的缺口：**报告声称成功但实际文件不对；查询数字正确，正文派生计算和新旧口径解释却不一致。** 建议优先讨论这两项可靠性改进，暂不扩展历史整理、任务调度或新分析入口。

这是一次有明确业务口径、小规模、单用户的实测，不是通用准确率、并发/容量测试或生产验收。未改变产品代码、原始Excel及现有业务数据库，未提交/push/合并/部署。

本轮无须修改原始数据。日后覆盖财务、IT场景时，应先修复其生成器或生成一份有明确来源的修正版，而不是直接把异常类别当作业务值。

1. 最新工作区执行 `mvn -q clean package -DskipTests -Dskip.npm=true -Dskip.installnodenpm=true` 成功；使用之前已构建的最新静态资源。本条是打包，不冒充测试执行。
2. 独立临时MySQL8.4.5、独立平台库/上传库、随机loopback端口Java17应用及任务专用Docker沙箱。只读取现用模型配置并重新加密复制进临时库，未改原配置；运行凭据留在忽略目录，不进入证据文件。
3. 经真实上传API导入7张表。通过已有草稿编辑API明确模型关系及口径，正常Wren校验并发布v1；没有直接写数据库冒充产品问数，也没有物理SQL回退。
4. **此次评价“已正确建模后的问数”**，关系及规则为人工验收夹具，未测试自动建模是否能自行发现这些规则。Q4的因果边界也已在库规则中声明，不能把其通过推广为所有无规则场景都不会编造。

6. 逐条比较真实Wren SQL返回值；实际下载附件核对HTTP、文件类型与PNG签名。Playwright重开真实会话检查图片，并实际点击声称的HTML报告链接。

## 真实缺口与代码证据

### A. 报告交付没有完成，却给出了成功承诺

Q5第一次Python尝试直接打开上一轮`outputs/*.png`，出现FileNotFoundError；模型随后重绘图片，并写出158,579字节的HTML文件，Python退出码为0。

但`RunPythonTool#executePython`仅收集PNG/JPG/JPEG/SVG/CSV/TXT/MD，**没有HTML**。每次调用使用独立run输出目录，注册产物后清理该目录。因此第二次调用只登记了112,061字节的PNG，HTML未成为持久附件。模型却把该PNG的artifact ID写在名为`.html`的下载链接上，并声称单文件HTML已生成。

浏览器实际点击结果：

- 链接标签：`2025年8月与9月同期全渠道销售经营复盘.html`。
- 实际下载名：`2025年8月与9月同期销售额增减拆解.png`。
- HTTP200，`Content-Type: image/png`，文件签名也为PNG。
- 原来Q2/Q3两张图片在历史中正常显示，所以这不是所有附件都失效。

原run目录隔离/清理是现有生命周期设计，不应为复用图片而随意取消。系统已有`restore_artifact`，本次模型未使用，反而误称“图片未保留”；应区分持久附件仍在与临时相对路径不存在。

**建议讨论的最小改造**：明确支持的报告格式；如支持HTML，通过现有附件存储登记、下载而不嵌入应用DOM执行；成功交付以真实注册产物的名称/类型/ID为准；需要复用旧图时恢复持久附件。失败或不支持时如实说明，不把图片冒充报告。沿用现有附件系统，暂不需要另造报告平台或新数据库表。实施范围仍待用户决定。

### B. 数字来源正确，派生计算及解释不可靠

Q3前三分类增量为337,242.74、303,061.17、219,464.32元，总增量984,197.41元，贡献应为87.36%；正文却写约86%。

Q9新销售额、去重订单数及退款金额SQL均正确，但SQL没有直接返回新旧客单价。模型正文把8月整月客单价48,798.93混作8月1–28日基准，又把9月新客单价47,672.72混作旧值；客单价差额写成−73.40 / −999.58，均不正确。还说“客单价由上升转为下降”，实际上旧、新两种口径的9月客单价都低于8月。

**建议讨论的最小改造**：比率、贡献率、新旧差额尽量在SQL/已有Python计算中明确生成，统一区间与分母后再用于正文；让关键数字绑定到这次实际返回值，避免凭上下文拼算。先用本批题目验收，不增加重复证据面板或大量业务专用计算规则。两处错误仅为本次观测，不推断所有回答都有问题。

## 下一步建议及尚未覆盖

优先把“分析结果能放心使用、报告真能交付”做扎实。Q8已经说明现有通用Agent能给出有价值的渠道分析；Q9也说明无需再造一个口径修改入口，真正缺的是修改后数值解释的一致性。

第一步建议聚焦A的报告产物链路，再处理B的数值一致性。每项完成后重跑同题及相邻变体；暂不需要为此重构整个Agent框架。尚未授权实施，本轮只记录证据。

未覆盖：其余9场景的问答、自动建模、极大表/大量会话、多人并发、线上66环境、跨用户附件权限回归、PDF/DOCX格式及连续多次随机采样。模型、口径或数据变化后都需重测，不能承诺通用正确率。
