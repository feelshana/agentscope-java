## 本轮发现及归因

1. **本机测试目录的挂载选择错误，已纠正。** Docker虚拟机的`/tmp`实际为约1.6GiB tmpfs，模型/JAR占用后仅余51MiB，触发附件默认保留2GiB磁盘的保护。SQL/Python成功，永久附件失败。迁至磁盘并释放本轮旧tmpfs文件后27/27通过，未降低保护阈值。66已选用`/data`，不能把此现象归因成容器必然慢或生产磁盘不足。
2. **提取运行库的原生对照缺认证插件路径，已纠正。** 同镜像的MariaDB动态库在新目录找不到MySQL8认证插件，首次查询失败。复制依赖和设置专属插件路径后恢复；不修改宿主全局系统库，也未更换生产认证方式。这是测试对照准备问题，原始证据保留。
3. **两种模式都存在并发调度等待。** 原生5用户通过，10用户6/10，独立有界15用户0/15；容器5用户通过，10用户0/10在有界测试内达标。原生首次采用较长客户端期限，其余有界批次采用120秒，不能直接以两批成功率评判Docker差距。线程转储显示同库门闩内等待MCP、其他请求排队；MySQL连接为Sleep，Python端等待输入，内存未耗尽，无OOM。代码及同依赖最小实验发现两处在同一boundedElastic线程池阻塞等待内层调度：同步MCP调用，以及作用域Toolkit注册。最小实验同步0/2、异步2/2；下文隔离诊断进一步验证，不能将生产实现写成已修复。
4. **答案内容存在既有类型的问题。** 例如音乐02-10把“全量Top5”错误沿用前半问的1–2月过滤；HR08-10对“全员”擅加在职过滤。HR08-05的`is_late`和`attendance_status`在源数据中不一致，现有预期与选列口径不同，须标作口径歧义而非工具算错。表格行形、秒转分钟、拆分查询导致的自动匹配失败已逐项核对，不能直接当错误计分。整份回答额外推断不因主SQL正确而通过。
