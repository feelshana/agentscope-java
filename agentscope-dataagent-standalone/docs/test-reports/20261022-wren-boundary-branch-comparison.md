# 2026-10-22 远程 Wren 分支与当前分支综合评估

状态：仅分析，未采纳新的产品边界，未执行工作区合并、切分支、提交或部署。

后续澄清：共同起点已支持多库问答，远程 ADR0081 也明确多库绑定方案，因此当前单库限制是实现与既有能力/设计未对齐，不能认定同事故意取消。用户说明尚未上线、旧测试数据可考虑重建；若确定不保留，旧 Cube/单文档的数据迁移不作为必做项，仍需确认新版本工具边界。首次上线应补完整初始化 SQL，不强求为可丢弃测试数据做升级迁移。面向同事分支的整合讨论见[讨论清单](../plans/20261022-branch-integration-discussion.md)，尚未执行合并或清理。

结论：远程分支有值得整合的建模工作台、草稿审阅与检索准备实现，但它不是单独的性能补丁。需要先确认建模确认方式、Cube/View 和多库问数的取舍，修复已复现的交付与兼容缺口，再考虑整合。不能任选一边覆盖另一边。

## 3. 已核实的缺陷与兼容缺口

### P1：干净检出测试依赖未跟踪的 CLAUDE.md

`DocsConsistencyTest#documentsEveryAgentReadsHaveNoBrokenRelativeLinks` 无条件读取项目根 `CLAUDE.md`，并要求正文为 `@AGENTS.md`。远程 Git 树中没有这个文件。

本轮只从 Git 导出的快照执行 Java 测试，实测 770 项，749 通过、20 跳过、1 错误；唯一错误是读取 CLAUDE.md 的 NoSuchFileException。编译及 Spotless 已通过。

为定位原因，只在隔离快照补了内容为 `@AGENTS.md` 的诊断占位，再单独执行 DocsConsistencyTest，5 项通过。这个文件没有提交到任何分支，不能因此把原候选记成测试全绿。

建议：把要求的最小桥接文件及必要忽略例外交付到 Git，或调整测试对可选本地文件的依赖，确保新检出无需补私有文件即可验证。

### P1：前端保留多选/全选，后端新工具只接受单库

- 远程 `ChatPanel` 仍显示“可多选”和“全部可用知识库”，发送 groupIds/allGroups。
- `WrenScopedToolkitMiddleware#createScopedToolkit` 在选中数不是 1 时直接抛出“一次只能绑定一个知识库”。
- 本轮受控单测确认：两个库的 DatasetScope 在工具发现前被拒绝。

因此这是远程分支自身的前后端能力不一致，同时也是与我们现有零/单/多/全选问数的兼容问题。全选有效库数大于 1 也会触发。

建议：先明确产品保留多库问数还是收紧为单库；保留多库时要设计受权限约束的工具寻址和上下文隔离，不能直接把同名工具叠加在共享 Toolkit。暂不采用“自动取第一个库”等静默降级。

### P1：新查询通道没有接上已有 CSV 数据文件传递

现有 `WrenMcpToolkit#callTool` 会调用结果导出 helper 的 `dataFileNote`，把真实查询结果持久化并提供 `data/<...>.csv` 给后续 Python。

远程主通道改为 `WrenScopedMcpClient#callTool`，只返回官方 JSON 和查询回执；客户端没有接附件/CSV 导出路径。旧 WrenMcpToolkit 源码仍存在，但主 Agent 已不注册该工具，文件存在不能证明这条链路还在生效。

受控测试返回带 columns/rows 的结果，确认新结果有 WREN_QUERY_RECEIPT、无数据文件交接。这个测试没有调用 Docker 或模型，不能解释为所有 Python 都会报错；实际风险是原有“真实 SQL 结果文件→Python→分析产物”流程缺了一环，模型可能转为抄写数据，违背现有工具指引并影响大结果处理。

建议：将纯结果文件导出复用到新通道，保持当前用户归属与恢复能力；再跑真实查询、Python 读取、图表/CSV下载及跨用户保护。保留官方 schema，不需要恢复物理 SQL 或旧业务路由。

### P1：query_cube 不经过新增时间门禁

`WrenScopedMcpClient.READ_TOOLS` 仍提供 query_cube；时间检查只在 run_sql/dry_run/dry_plan 分支调用。受控测试已确认 query_cube 到达 gateway，而配置的 FactQueryWindowPolicy 没有被调用。

基础建模关闭 Cube/View 不代表存量发布资产没有 Cube；其 CLI build 仍读取存量资产。不能用“不新建 Cube”代替查询入口约束。

建议：结合是否保留 Cube 查询做统一决策。保留时必须覆盖底层受限事实表窗口；暂不支持时应一致收口工具和页面，并说明存量能力变化。此次只是控制流验证，没有向真实业务库发无日期查询。

### P2：新增数据结构缺完整生产迁移

新增 `FactQueryWindowEntity` 需要 `dataagent_fact_query_window` 表；仓库新增迁移只找到 `0093-modeling-revision-mysql.sql` 的两个 revision 列，未发现新窗口表的可交付 DDL。

与我们 production 的 ddl-auto=validate 整合后，需要正式迁移和空库/升级库验证；不能用同事开发环境 update 启动成功替代。此前导出的 36 表测试结构也不能作为合并后完整初始化脚本。

### P2：新前端测试与我们现有门禁不兼容

远程四份 Node 脚本单独执行共 19 项通过；前端 TypeScript/Vite 构建也通过。但其 package.json 没有 npm test，也没有我们后续加入的 Vite 回归门禁。

另在隔离副本用我们当前 runner 运行其新增的 `fact-window-setup.test.mjs`、`wren-presentation.test.mjs`，两文件均模块加载失败：它们仍自行从文件读取 TypeScript、transpile 后 data URL 导入，临时执行目录无法解析其 typescript 包；路径读取方式也依赖原 tests 目录。

建议：保留我们当前 npm/Maven 门禁，并把两份新增测试改为真实 TS 模块 import，保留其八项新增断言，双前缀复验。不要把“分别跑过”视作合并后的门禁已接通。

## 4. 需要先确认的设计取舍

| 主题 | 当前分支 | 同事分支 | 评估建议，尚未采纳 |
|---|---|---|---|
| 文件写确认 | 原生文件/CLI写授权，HITL中断 | 直接进入共享草稿，统一显式发布 | 可评审新流程的易用性；需要同时验安全边界、并发写/发布和归属记录，不只改前端隐藏确认卡 |
| Cube/View | 按官方契约支持 | 基础 Agent 不读不写，存量仍参与编译 | 区分“不默认生成”与“禁止用户显式维护”；保留哪些能力须明确 |
| 选库 | 零/单/多/全选 | UI多选，原生工具实际单库 | 先修前后端不一致，再决定完整多库方案 |
| 日期限制 | 本分支没有这套已交付门禁 | 外部受限事实表的未缓存 SQL 由模型逐表判断，门禁放行结论缓存一小时 | 是额外模型调用与产品约束，不应描述为纯性能优化 |
| 问答样例 | 已有点赞保存、SQL样例结构化维护 | 强调试问后由用户确认；基础建模不写问答 | 复用现有 memory 和编辑能力，核对旧样例是否仍可见/编辑，避免旧面板成为无入口代码 |
| 业务文档 | 数据库单文档并同步 raw/business-document.md | raw/docs 多文档，原方案明确不迁移历史 | 当前已有试用资产，不能直接沿用“无历史数据”假设 |

时间门禁需要特别注意：真正接线的是工具内 SqlWindowGate；不能因为 QuestionDateGate 类存在就认定它每问必跑。SqlWindowGate 针对未缓存、受限库 SQL 可能增加一次模型往返，超时为 20 秒。其 parse 校验的是模型返回的逐表明细，表匹配仍依赖模型，提示词明确“名称不匹配的视图跳过”，并非确定性的 SQL 血缘证明。应补别名、ref_sql/存量视图、OR/CTE/子查询和遗漏表覆盖，不能把它当成数据库级硬隔离。

## 5. 我们当前分支必须保留的能力

远程基于更早起点，本来就不包含以下后续交付；这是分支独立演进，并不表示同事故意删除了功能：

- BI 免登、prod 入口策略、sessionStorage、同源部署前缀适配；相关迁移与真实模拟验收。
- 全局管理员模型服务管理、加密存储、测试/应用分离和在途轮次固定。
- MySQL Agent 状态持久化及删除/重置生命周期。
- 图表请求用户归属、SQL样例结构化往返编辑。
- Wren MySQL/Doris明确断链的一次重建重试与失败冷却。
- 新数据源管理页面、更多页模型入口、导航/面包屑和现有 UI。
- 本轮浏览器夹具修正、发布指引与全流程证据；前端双前缀测试门禁。

尤其要注意两个容易被 Git 自动合并掩盖的问题：

1. `DataAgentConfig` 文本可以自动合并，不等于新 SqlWindowGate 已遵守 SwitchingModel 的同轮快照。门禁内部同步 `.block()` 发起独立订阅，需要专项验证切换发生在本轮工具执行时的模型选择；当前只是组合风险，未在合并服务复现。
2. `WrenInstanceRegistry` 同事的 instructions 缓存/预热/阶段日志要与我们的断链恢复、冷却和 MCP类加载器处理一起保留；双方都修改了实际调用生命周期，不能单选整文件。

## 6. 合并冲突与文档问题

用 `git merge-tree --write-tree --name-only --messages <ours> <theirs>` 仅进行对象级模拟，未创建 merge commit、未改 HEAD、索引或工作区。它列出 **28 个冲突路径**，不计本轮尚未提交文件；这不是“28处都选某一边”就能处理的任务。

- 后端内容冲突：ProcessWrenCli、WrenPublishedProject、WrenInstanceRegistry、OfficialWrenToolkit。
- 前端内容冲突：AppShell、SessionsSidebar、ToolInspector。
- 文档/记忆/位置冲突：AGENTS、ARCHITECTURE、README、共享记忆、部署手册、规划及原型路径等。
- 静态散列资源冲突：应在源码完成整合后按实际前缀重新构建，不手工拼两个 JS/CSS 包。
- ADR `0081–0088` 两边分别指代不同主题，Git 对不同文件名不一定报错，仍须调整编号与引用；不能按数字直接认定是同一个决策。
- 同事将原型/规划/旧记录移入 archive，我们有仍在使用的原型与后续规划；应逐项确定归属与链接，不自动把它们当过期内容归档。
- 远程 CURRENT_TASK 仍写“所有修改未提交”，与本次实际 Git 提交冲突；它只能说明历史阶段，不代表最新提交状态，更不能覆盖我们当前记录。

本轮没有采纳远程 AGENTS 中与当前不同的 Cube/View、HITL或文档限制，它们是被评估的分支规则。正式整合前需要形成共同规则。
