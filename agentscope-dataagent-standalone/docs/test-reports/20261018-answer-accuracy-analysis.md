### 评分仍不够严格

- 历史benchmark#matches是候选匹配：容忍列顺序、附加列与数值类型差异，按每行包含目标值匹配；不能单靠它验证字段含义、单位、业务口径和全部文字。直接命中71条不是自动证明71篇完整答案都正确，6条人工等价也需保留理由。
- 10.17客单价题01-avg的数值47,697.07元正确，回答却断言“amount已含折扣”。原始业务规则只规定SUM(amount)，参考表4339条均满足amount=quantity×unit_price，非1折扣样本也未乘discount_rate；这些数据不能证明“已折扣成交额”。本题关键结果通过，附加解释仍不可靠。
- 10.17答案还引用模型中的基线数值；有真实查询回执不等于测试问题与知识资产完全隔离。后续应加入未参与建模、未写入示例的盲题和数据变化测试。
- 目前没有对全部最终回答逐句事实核查，没有生产随机题、同题多次/多种说法的稳定性统计，因此**完整回答准确率、生产首次正确率都未知**。

## 二、已证实的失败链路

| 案例 | 正确值 | 错误值 | 原始证据与归因 |
|---|---:|---:|---|
| 01-time：2025年1月有效订单 | 158 | 154 | 模型传query_cube的time_dimension终点2025-01-31；SQL用小于该日，漏掉31日 |
| 04-time：1月已订购收入 | 8,137 | 7,874 | 同上，SQL漏整个月最后一天 |
| 05-time：1月去重阅读用户 | 1,472 | 1,469 | 同上，自然月被误翻译成半开区间末日 |
| 01-repeat：复购率 | 199/200=99.5% | 200/200=100% | 错误官方memory样例在订单明细上COUNT(*)，问数沿用；客户19实际1笔有效订单、2条明细，被当成复购 |
| 11-tiny：极小表全部指标名 | 应查询三条名称 | 名单恰好正确，但未查名称 | 只实际COUNT(*)=3，名称取字段描述中的样本，不能证明本次全量结果；按证据不足处理 |

本轮只读重放保存的独立SQLite参考SQL，得到158、0.995、8137、1472及三个名称，和原金标一致；客户19的1笔订单/2条明细也实际核对。不是仅重复报告中的结论。

### 日期：模型调用契约误用，当前无证据证明Wren算术错误

原始调用明确包含`time_dimension: 下单日期:month:2025-01-01,2025-01-31`，阅读/彩铃同模式。本机安装版官方usage/references/wren-sql.md明确示例dateRange的end exclusive；Wren按约定生成`>= 2025-01-01 AND < 2025-01-31`，执行结果与错误区间一致。平台WrenMcpToolkit#callTool不改日期参数。

因此现有证据支持：模型没有正确把自然月翻译成官方参数；官方MCP工具描述只突出start,end格式，没有在这一层醒目标注排他上界，也存在可改善的契约可见性。不能把错误终点归为Wren数据库聚合算错，更不能用平台静默改SQL处理。

10.17上述三题改走run_sql且明确下月1日上界后正确。**成功路径发生变化，不表示query_cube边界误用已回归修复。**

### 复购：错误资产被召回并放大，模型自检没有独立性

原始recall_queries确实返回“复购客户数和客户总数”的错误SQL，包含在有效订单明细上COUNT(*)>=2。问数按该样例计算100%，觉得异常后仍用明细COUNT(*)自检，又把客户19的两条明细称为两笔订单，最终自信地解释100%合理。

问题同时涉及建模/样例口径、问数模型推理、资产验收。向量检索确实找到了语义相关示例，它并不判断SQL业务是否正确；“提高召回率”可能放大错误资产。当前无法把根因定成向量库性能或Wren执行器问题，也不能把所有错误只归咎当前问答模型。

### 解释和采样：数字对不等于答案可信

极小表有正常查询总数，却未查询用户要求的名称。现有DatasetSampleDocuments#POLICY和WrenQueryContextMiddleware已提醒精确数据不能用样本替代，说明提示存在但不足以保证每次遵守。金额附加解释也是同类风险：结论混入没有证据的业务事实。

## 三、按层看责任

| 层 | 现有证据 | 判断 |
|---|---|---|
| 原始数据/文档 | 财务和IT数组字符串坏列、文档与状态枚举/空FK比例不一致 | 数据可用性问题，要识别并解释不可算；不能乱转数填0，也不能都计作模型答错 |
| 语义模型/知识/样例 | 已存在错误复购SQL、历史完播定义与源标记冲突 | 最重要的质量基础；同一错误可影响所有用户，不是一次随机回答 |
| 大模型 | 日期参数错误、错误grain自检、采样当全量、额外事实断言 | 有真实错误证据；但未做相同资产/题集的多模型A/B，无法量化更换模型收益 |
| Wren及向量 | 参数/SQL按既有契约执行，相关错误示例被实际召回 | 这些数值错未找到Wren引擎错算证据，不等于整个Wren永远无bug；模型/视图/类型兼容问题与业务答案错误分开 |
| 平台代码/产品机制 | 原样调用/只读/授权/发布技术检查已存在，未对错误复购业务定义作有效拦截；可点赞成功但业务错误的示例 | 业务质量不能外包给模型或Wren。平台需要证据与语义验收闭环；SQL编辑损坏已修，但不自动纠正错误业务SQL |
| 状态与可用性 | 重启上下文丢失、外联旧实例恢复、Docker未就绪 | 会降低用户成功获得答案的比例，应计入整体成功率，但与静默返回错误数字分开统计 |

MdlPublishService的技术校验/编译/视图和Cube检查，能证明结构和执行能力，不能证明复购定义符合订单粒度。DataAgentConfig已有固定过滤检查/业务正确性提醒；问题是这些约束尚未形成对所有关键指标有效的验收证据。AnswerQueryMemory#feedback对点赞成功查询存memory，candidates校验执行回执和归属，没有业务真值判定；点赞不能视作数学证明，点踩也不自动撤回已入库样例。

当前主链挂载安装版官方Wren技能。仓库旧shared/skills/sql-analysis不是当前主问数契约，不能只改旧文件就声称改善线上准确率。

## 四、建议顺序（待用户确认，未实施）

1. **先冻结可核验基线。** 保留77题及现有错误，分开记录首次问答、澄清后、修改资产后；冻结数据/MDL/模型标识/提示/示例/工具版本，不用人工修正后的成绩覆盖首次失败。
2. **优先修复系统性风险。** 自然月/时间边界、订单与明细粒度、错误样例/指标治理、全量证据与附加解释。修正源资产并显式发布/重建官方索引，不能只改一条聊天答案；遵守用户先讨论建模改造的边界。
3. **把业务金标纳入关键指标验收。** 对首发重点库，业务人员确认定义及独立参考SQL；覆盖月末/年末/闰日、同客户单订单多明细、JOIN扇出、分母/状态/空值等反例。保留正常建模主链，不另建平台SQL路由或逐题硬编码。
4. **再做准确性专项复测。** 77题扩充未入示例盲题、近义问法、追问切库、跨来源合并口径及数据更新；同题重复多轮，分别覆盖Cube/run_sql。失败后重问不抵消首次失败，不向待评模型提供参考答案；同题可以访问已批准的业务规则。
5. **最后评估是否更换/升级模型。** 相同资产和题集比较当前模型与候选模型的首次正确率/稳定性/耗时/费用；若主因是错误资产，换模型不能替代清理治理。

建议后续指标分开：有答案率、首次业务正确率、证据完整率、完整答案事实一致率、重复稳定性、合理拒答/澄清率及正确回答耗时。不要以单个“准确率”掩盖各类失败，也不把有依据的不可计算当作胡答错误。
