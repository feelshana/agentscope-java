# 2026-11-03 spec113 实施前实测：只写规则的默认过滤、查询模板的 MySQL 兼容性

环境：本地 8080，Wren 0.15.0，MySQL 数据集库。测试账号 newuser10，新建知识库"spec109实测"（`e71fc858`），上传 `data/demo-samples` 中的报表访问明细、用户列表，基线模型直接发布，未做自动建模，也没有加工表或查询模板干扰。

## 实测 1：只写规则时，问数能否稳定加上过滤（部分完成）

建模对话（普通轮次）输入："统计报表访问时，默认排除测试账号：访问账号在用户列表里找不到的就是测试账号；我明确说包含测试账号时才算进去。"

- 助手只写了业务规则，没有建资产，没有写 `views/` 或加工表文件 ✅
- 规则写在助手自建的小节 `## 测试账号口径` 下，不是官方 `## Default filters` ⚠️（spec113 提示词需要明确写到官方小节）

发布后问数（都不提过滤）：

| 问题 | 工具调用 | 是否加了排除条件 |
|---|---|---|
| 总共有多少次报表访问 | get_instructions → recall_queries → run_sql | ✅ `EXISTS (SELECT 1 FROM 用户列表 u WHERE u.account = t.user_account)` |
| 每天的报表访问次数 | 同上 | ✅ `EXISTS` 子查询 |
| 访问次数最多的 5 张报表 | 同上 | ✅ `INNER JOIN 用户列表`（account 全表唯一，不放大行数） |
| 各公司的访问次数 | 同上 | ✅ `JOIN 用户列表`，答案注明按规则排除；合计 98,806 与此前加工表结果一致 |
| 有多少人访问过报表 | 同上 | ✅ `JOIN 用户列表` |
| 包含测试账号在内的访问次数 | 同上 | ✅ 不加过滤，直接查原表 |

结论：5/5 个不提过滤的问题都按规则加上了过滤（写法有 EXISTS、INNER JOIN、JOIN，结果一致）；明确要求包含时正确放开。只写规则可以替代"排除测试账号"类加工表。

补测说明：第 5、6 题最初因模型服务 402 未完成。排查发现权益包额度对 `qwen/deepseek-v4.1-flash` 不可用（最小请求也返回 `B.Balance.FrozenHeldException`），对 `qwen/deepseek-v4.1-flash-1017` 可用；已把本地 `.claude/launch.json` 的模型名改为后者，重启后补测完成。

## 实测 2：查询模板在 MySQL 上能否使用（完成，通过）

手工保存查询模板"访问函数实测"，使用 `DATE_FORMAT`、`IFNULL`、`ROW_NUMBER() OVER (PARTITION BY … ORDER BY …)`，左关联用户列表：

- 官方 `context validate --strict` 通过 ✅
- 草稿上执行两条验证 SQL（按天按公司访问次数；窗口函数取首次访问）均返回正确结果 ✅
- 判定通过后发布 v3，发布前对查询模板的 dry-run 检查通过 ✅

- 问数助手通过官方 MCP 查询该查询模板：`get_instructions` → `recall_queries` → `describe_schema` → `run_sql`，SQL 直接查"访问函数实测"，执行成功 ✅

结论：ADR0042 记录的"View 走 DuckDB 函数绑定、MySQL 专有函数报错"在 Wren 0.15.0 上不再出现；查询模板在建模校验、草稿执行、发布检查和问数中都能使用这些 MySQL 函数和窗口函数。

## 补测发现的新问题（影响 spec113 的起草规则）

问数助手在查询模板上应用"排除测试账号"规则时，用 `公司 <> '未知公司'` 代替"账号在用户列表中存在"。但查询模板用 `IFNULL(u.company, '未知公司')` 把"匹配不上的账号"和"匹配上但公司为空的账号"（前次统计约 656 次访问）合成了同一个值，后者会被误排除。另外，回答把 `第几次访问 = 1` 解释为"本期首次访问"，实际是全量数据中的首次访问。

对起草规则的要求：
- 查询模板要保留应用已有默认过滤所需的列（本例为用户列表的账号列），不要用 `IFNULL` 等默认值掩盖空值的含义；
- 窗口函数的统计范围要写进列描述（例如"按全量数据计算的第几次访问"）。
