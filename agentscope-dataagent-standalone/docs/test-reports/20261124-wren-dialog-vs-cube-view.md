# 2026-11-24 对话建模 vs Cube+View（类本体）问数对比

状态：本地真实 LLM 验收，供决策是否引入"类本体"建模方式；未改代码。

## 输入与环境

- 数据：`E:\总部常规性分析\hhweb_video_vip_more_dimension_m.sql`（327 行，仅账期 202610，全国，渠道/支付均为"全部"），转 UTF-8 CSV 上传。
- 业务文档：同目录 `业务规则-月.md`（会员口径六级表；文末截断，未定义 `cnt_*` 指标含义）。
- 本地 Windows、MySQL 8.4、Wren 0.18.0，dev profile，admin 账号；JVM 加 `-Dfile.encoding=UTF-8` 绕过 CSV 乱码（见问题 1）。
- 标准答案（cnt_zd）：足球通 10,548,714；足球整体（4 级=足球、5/6 级=全部）12,984,895；篮球通 3,283,751；只有一个月，无趋势。

## 两种方式

| | A：对话建模 | B：对话建模 + View + Cube |
|---|---|---|
| 建模产物 | 模型、字段说明、术语与规则（自动建模 11 步） | 同 A 的基础建模（14 步），另加 View `vip_member_scale`（14 段 UNION，每段一个文档口径）与 Cube `vip_member_metrics`（度量 members/new/net_new/unsub，维度 member/member_system/level_condition，时间维 month） |
| 人工成本 | 确认卡片 + 发布 | 额外：View 人工核查 + 问题验证（ADR0128）；口径变更须维护 View |
| 问数取数方式 | LLM 写 `run_sql` | LLM 选 Cube 参数调 `query_cube`，SQL 由引擎生成 |

## 问数结果

| 问题 | A | B |
|---|---|---|
| 1 会员体系 | 16s，2 次 run_sql；首条 SQL 因 0.18 LIMIT 叠加报错后恢复。罗列层级取值，把 2 级公网/专网说成"渠道"，附无业务意义的"组合数"表 | 11s，无 SQL，`describe_cube` 后按 3 大体系 14 个口径组织，提示钻石/黄金合并待确认、跨口径不可相加 |
| 2 26年10月足球会员数 | 16s，3 次 run_sql；答 12,984,895（足球整体），未提示"足球通"歧义，靠模型从 6 行中挑一行 | 11s，1 次 query_cube；答足球通 10,548,714；同样未提示"足球整体"歧义（View 中无此口径） |
| 3 篮球通月趋势 | 16s，3 次 run_sql；首条把"不限"写成字面值 `vip_type_1='不限'` 查空后修正；答 3,283,751，说明仅一月 | 9s，1 次 query_cube；答 3,283,751 及新增/净新增/退订，说明仅一月 |

结论：两者最终数值都"能对上"，但 A 每题 2–3 条 SQL、都有一次自纠；B 每题 0–1 次确定性调用、口径直接来自文档表格。Q2 两边各自选了不同口径，暴露的是口径歧义而非方式优劣：B 的答案取决于 View 收录了哪些口径。

## 观察到的差异

1. **运行间稳定性**：同表同文档两次自动建模规则明显不同；B 那次写出 `vip_type_6='足球通'`（实际值"足球通会员"），匹配不到行。A 规则只写"按业务文档对应条件取行"，口径表未落盘。口径越依赖 LLM 现场推导，结果越不稳定。
2. **确定性**：B 把口径固化在 View，问数只选 member，SQL 不再由 LLM 拼六级条件。
3. **代价**：B 需要人工写/核查/验证 View；Cube 的 SUM 对有包含关系的口径无意义，只能靠描述约束"必须按 member 筛选"，引擎不强制。
4. **歧义处理**：两种方式都没有反问"足球会员"指哪个口径。B 若要支持需把"足球整体"也列为口径或加术语规则。

## 发现的平台问题（未修）

1. `DatasetImportService` 读 CSV 用 EasyExcel 默认字符集（JVM 默认，Windows 为 cp1252）导致中文乱码，且未去 BOM（列名出现 `ï»¿id`）；`CsvParser` 有 UTF-8/BOM 处理但上传不走它。
2. AI 字段筛选把 `province_name/channel_type/pay_type*` 标"技术"默认排除，而口径必须按它们取汇总行，否则多省份数据会重复计数。
3. 同一文件两次上传列名不一致（`pay_type_1` vs `pay_type1`）；`cnt_jxz` 被猜为"将新增"、`qcj` 为"全串联"并写进模型。
4. 确认表后刷新页面，"开始自动建模"入口消失，需 `?start=1`。
5. Wren 0.18：`run_sql` 叠加 `LIMIT 1001` 报 MySQL 语法错（平台 LIMIT 补丁只针对 0.15）；Cube 维度名与底层列同名时加过滤规划失败（"missing source schemas"），改名绕过。
6. **问题验证通过了不存在列的 SQL**：B 视图验证确认的问答 SQL 为 `SELECT ... member_cnt FROM vip_member_scale WHERE stat_date >= ...`，视图实际列是 `member_count/period_month`。验证只做展开不执行，仍判"符合预期"并存为已确认问答，之后被 `recall_queries` 召回给问数（本次模型未照抄）。
7. 业务文档截断、未定义指标含义；两种方式都只能假设"会员数=cnt_zd"。

## 建议（待用户决策）

- 是否引入类本体：对"预统计宽表 + 文档化口径"这类场景，View+Cube 明显更稳；但建议作为**可选资产**而非替代对话建模，由文档口径表生成 View 草稿、人核查后发布。
- 不论是否引入，问题 1、2、6 建议优先修。

- 选表规则生效：三问都先读到 `calibers.md`，取数都走 `query_cube` 且按口径名筛选，没有拼六级条件，门禁未被触发。
- Q2 根因：Wren `query_cube` 的时间范围为左闭右开，模型传 `period:month:2026-10-01,2026-10-01`，展开为 `period_date >= '2026-10-01' AND period_date < '2026-10-01'`，范围为空；查 10 月应传 `2026-10-01,2026-11-01`。已修：`query_cube` 执行前拒绝空时间范围并给出正确写法，生成指标的时间维度说明写明左闭右开。重启后重问 Q2，模型首次仍传空范围，被拒后改为 `2026-10-01,2026-11-01`，答足球通 10,548,714（含新增 2,472,345、净新增 1,847,142、退订 1,219,506），与此前 B 结果一致。时间维度说明要等 B 下次发布才更新。
- 歧义：门禁只拦清单外的口径名；模型自行把"足球会员"映射到存在的口径时，不会触发，"先问"仅靠规则约束。
