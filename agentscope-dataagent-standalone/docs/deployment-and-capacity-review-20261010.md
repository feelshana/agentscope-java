# 单服务器部署与 10 并发容量评估

日期：2026-10-10。状态：部署位置已确认；容量目标待测，不代表性能承诺。

## 部署选择

选择 65：前后端、Docker 沙箱和项目 Wren 环境本机运行，开通业务数据库访问。已有 MySQL 可复用，但应用元数据、上传数据落库和关联业务数据库需明确各自配置及账号权限。宿主机已有 Python 不等于已经安装 Wren 依赖或构建分析镜像。

按打包上传、登录服务器运行启停脚本的方式规划。生产配置、持久数据及日志放在独立于发布版本的固定目录，更新包不覆盖。上线需准备 JDK、分析镜像、Wren 依赖、模型网络、数据库初始化、Docker 权限和 BI 嵌入/代理配置。发布脚本与配置拆分需单独实施。

## 当前代码限制

| 部分 | 当前事实 | 对 10 并发的影响 |
| --- | --- | --- |
| Python 沙箱 | application.yml 默认总数 8、每容器内存上限 1024 MiB、CPU 配额 1；UserSandboxRegistry 容量不足时 tryAcquire 失败 | 10 个不同用户同时需要新沙箱可能拒绝，空闲沙箱也占预算 |
| Wren | WrenInstanceRegistry 按 groupId 串行调用，实例集合没有统一数量预算 | 同库并发排队，不同库并发增加进程资源 |
| 问答准入 | 缺少统一问答准入和资源预算 | 只提高容器数不能保证 10 并发 |
| 外部依赖 | 模型限额、数据库连接和 SQL 耗时需实际确认 | 可能先受到 QPS/Token 限额或慢查询限制 |

来自代码阅读，未在 65 测量。同库 Wren 串行门用于避免当前客户端并发调用故障，不能直接删锁作为优化。

10 人在线浏览、10 人同时问答、10 个 Python 重分析是不同负载。建议目标为 10 个问答可接入，资源不足时有限排队并明确告知用户；不承诺所有分析立即完成。

## 上线前完善顺序（待排期）

1. 确认可分配 CPU/内存、共用服务占用、模型限额及数据库连接预算。峰值内存包含 JVM、Wren、Python、共用服务和系统余量。
2. 设置问答准入、有限队列/等待超时、Wren 实例预算和沙箱总数/空闲回收。按实际容量定参数，不直接把 8 改 10 就宣称完成。
3. 确认列表不启动计算资源，阻塞操作不占 WebFlux 事件线程，取消/超时能释放资源。页面日志区分浏览器 Stalled、代理等待、服务端和数据库耗时。
4. 知识库列表和授权选人服务端分页，上传与结果设合理大小预算。
5. 在真实 65 环境验证容量后确定上线参数及可承诺范围。

## 后续验证方案（本次未执行）

- 分别验证 10 人页面浏览、同库问答、不同库问答、10 个不同用户 Python 分析，涵盖冷启动、热运行和空闲容器占用场景。
- 固定问题和数据规模，观察持续负载、错误及全部请求结束后的资源回收。
- 记录列表 P50/P95、首响应、问答时长、排队、错误率、模型限流、CPU/内存、容器和 Wren 进程数、数据库连接使用。
- 列表接口 P95 ≤ 1 秒可作为初始建议（不含浏览器/网络），尚未确认或测得；分析按模型/SQL/Python 阶段及工作量定目标。
- 超出预算应返回明确排队/繁忙状态，不能拖慢列表或造成内存失控。
