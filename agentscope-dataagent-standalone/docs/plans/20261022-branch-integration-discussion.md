## 2. 优先讨论的关键问题

| 优先顺序与性质 | 已确认事实 | 建议与需要同事确认的事项 |
| --- | --- | --- |
| 1：多库问答，实现缺口 | 共同起点已支持零/单/多/全选；同事界面仍支持多选/全选，但新作用域工具要求只能一个库；其 ADR0081 也明确计划多库工具绑定 | 确认是否暂时只完成单库；建议保留现有多库能力，补原生工具的库寻址与权限隔离。单次工具针对一个工程，不等于整轮只能查询一个库，也不是跨库 SQL JOIN |
| 2：真实查询结果交接，实现缺口 | 旧通道把查询结果导出 CSV 给 Python；新原生通道返回 JSON 和回执，没有接原导出路径。未找到明确废弃这项能力的文档 | 确认是后续待补还是另有替代；建议复用结果导出，保留私有归属，验 SQL→CSV→Python→图表/下载。不意味着 Python 全部不能运行 |
| 3：建模写确认，产品取舍 | 我的流程有逐次文件写 HITL；同事改成写入共享草稿、集中审阅、显式发布 | 讨论采用何种体验；倾向评审同事的新工作台，但必须共同决定写确认边界，验证多人编辑、作者归属及运行中发布/撤销。最终发布依旧明确确认 |
| 4：Cube/View 与时间限制，产品取舍和条件性缺口 | 同事 ADR0107 明确基础建模不读写 Cube/View，但已有文件仍可编译、问数仍可使用；query_cube 未经过新时间检查 | 用户说明尚未上线，旧测试资产可考虑重建，不要求专门迁移。先明确首发保留哪些能力：若保留 Cube 查询，应统一限制边界；若不保留，应一致收口。没有 Cube 的新环境中，不把旧资产迁移列成上线阻断 |
| 5：干净检出验证，交付问题 | 远程 DocsConsistencyTest 要求 CLAUDE.md，但该文件未在提交中，导致一项测试错误 | 同事确认是漏交文件还是本地可选文件；交付最小桥接文件或修正测试依赖，保证其他人直接检出可验证 |
| 6：数据库 SQL，发布准备 | 新增时间窗口表缺可交付建表 SQL；两个建模版本字段已有独立 ALTER 脚本 | 首次上线补最终版本的完整平台库初始化 SQL，空库验证后用 prod validate 启动。若测试库重建，无须强行做旧数据升级；上传 ds_ 物理表仍由上传动态创建 |
| 7：前端测试入口，整合适配 | 同事新增两份测试单独可跑，与我方真实 TS 模块/Vite runner 组合时加载失败 | 保留我方 npm/Maven 测试入口，将两份脚本改成直接 import 源码，保留 8 个断言，双部署前缀验证。这是测试适配，不是业务重做 |
| 8：性能与时间检查，组合验证 | 同事确实实现了索引前移、实际 MCP 预热等；受限 SQL 的未缓存检查又会额外调用模型，超时上限 20 秒 | 同机器/同模型/同问题分别测冷首问、准备后首问和暖问；日期检查适用表、失败行为和可靠性须共同确认，不能承诺每问更快或等同数据库硬隔离 |

说明：“测试门禁”指 npm/Maven 自动检查；“时间门禁”指 SQL 时间范围检查，两者不同。第 1、2 项的缺口已由受控测试验证，但没有证据推断同事的主观意图。

旧测试数据如确定不保留，还可免做旧 `raw/business-document.md` 到新 `raw/docs/` 的兼容迁移；若保留某些演示库或云端试用资产，需单独列出。本文没有执行任何清理。
